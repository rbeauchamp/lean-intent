# The blind formalization's inputs, prompts and results

## The directory

Make a new directory outside the repository and put in it only:

- `owner-words.md`: the owner's words, exactly as given, with nothing of yours added: those at the level step 1 started from, and, where the owner adopted a statement, that statement exactly as adopted, with nothing of the proposal's reasoning;
- `types.lean`: the source of the definitions of the types the subject is stated over, copied without the implementation or any other definition that is not a type;
- `Record.lean`: lean-intent's `LeanIntent/Record.lean`, from the commit the project pins.

Where the subject's type or domain is itself what is in question (step 3), the directory instead holds `owner-words.md`, `types.lean` where the input already has a Lean type, and `input-format.md`: the input's own format from that format's owner, such as the section of a tool's documentation that says what its configuration holds, with nothing that says what is wanted and nothing about your record.

Start the second model in a fresh session or context whose only material is that directory's contents: no earlier conversation, and nothing of your account, record, reasoning or the implementation in anything it can read (its workspace, memory, attached files or system prompt). Give it the prompt below that fits what you ask for, and save the prompt and its reply.
Through a command line, for example `codex exec` as the next section gives it, or `claude -p "<prompt>"` run from `<dir>` with the isolation of step 3 found in that tool's own help; through a desktop app, a new conversation whose workspace is `<dir>`; through an API, a request that carries only the prompt and the directory's files. Use a model of another provider than the one that wrote your record, and check the interface's own help for how to start it that way.
Take its reply as a blind reading only when what the session could read at all was limited below the interface, never on what a transcript, a tool log or the model's own list of files says: a session can read what none of them shows, as [the observations of Codex below](#what-the-event-log-shows) found. One of two conditions must hold, and your report names which, with the evidence for it:

- **(a) No tool and no stored state.** The request gives the model no tool and no stored state, so it can read nothing beyond what the request carries: for example an API request that carries only the prompt and the directory's files, with no tools and no earlier conversation or stored response.
- **(b) A read restriction below the tool.** The whole process of the tool that runs the model, every child included, runs under an operating-system restriction that refuses every file read except a closed list of paths, none of which holds, or is a directory above, your record (the first formalization) or your account, reasoning, implementation, notes or session transcripts; and before the run, with the run's own command, flags and restriction, you observed at the version in use that the restriction refuses a read of a canary file beside your record, both through a plain command and through the tool's own in-process file read, each read having first been observed to succeed without the restriction. [The section on that restriction](#under-a-restriction-on-what-codex-can-read) sets this out for Codex.

A session whose model has tools, or that carries memory, a workspace or an earlier conversation, as a command-line or desktop session usually does, does not meet (a), and meets (b) only when it runs under such a restriction with those observations made through it.
A transcript, a tool log or the model's list of files may still be recorded, and each can discard a reading: anything in them outside the directory's files, or a log item that [the Codex form](#under-a-restriction-on-what-codex-can-read) does not admit, means the formalization is not blind, so discard it and start a fresh session. None of them establishes a reading.
A reading that meets neither condition is unconfirmed, and step 3 does not accept it: discard it, and either use a route that meets a condition or report step 3 as blocked, as its item 2 says for a model that cannot be reached.
Keep your record unpublished until the reading is done: committed locally, as step 3's item 1 asks, and pushed nowhere the second model's provider could reach by web search, since a restriction on file reads does not limit a web search.
The directory and the session stay outside the repository; what the project keeps of the result, and where, is set out in [the last section](#where-the-formalization-and-the-comparison-live).

## The Codex command

Keep the prompt, the reply and the event log in a second directory outside `<dir>`, so that the session's only material stays the directory's files.

```sh
codex exec -C <dir> --skip-git-repo-check \
  --ephemeral --ignore-user-config -s read-only \
  --disable memories --disable hooks --disable view_image \
  -m <model> -c model_reasoning_effort=<effort> \
  --json -o <outside>/reply.md \
  "$(cat <outside>/prompt.txt)" < /dev/null > <outside>/events.jsonl
```

Each flag was read from the help of codex-cli 0.166.0 (`codex exec --help`, and `codex features list` for the three feature names); if your version differs, read them again, and where a flag has gone find its current equivalent rather than dropping it.
Run it only in [the form below](#under-a-restriction-on-what-codex-can-read), under the restriction of condition (b): Codex's own sandbox limits the commands the model runs, not the reads Codex makes itself, and where that sandbox starts, the model's commands run, and [the event log does not show everything they read](#what-the-event-log-shows).
The Acorn pilot of this method, then called spec-first, ran a session of this kind at 0.165.0 (rbeauchamp/acorn PR 188, `docs/spec-first-pilot.md`), and [the sessions below](#what-the-event-log-shows) ran it at 0.166.0 from a session already sandboxed, some with `-s danger-full-access` in place of `-s read-only`, with short prompts of their own rather than a formalization's, and none under the restriction of condition (b); so treat your first run as the check of it.

| Part | What it does |
|---|---|
| `< /dev/null` | Closes the command's input; the Acorn pilot observed Codex otherwise waiting on stdin, and the help says piped stdin is appended to the prompt. |
| `--ephemeral` | Persists no session files. |
| `-C`, `--skip-git-repo-check` | Make `<dir>` the working root and allow it not to be a Git repository. |
| `--ignore-user-config` | Does not load `$CODEX_HOME/config.toml`, so what that file configures stays out; auth still uses `CODEX_HOME`. That includes the configured model and effort, so name them with `-m` and `-c`. |
| `-s read-only` | Runs the model's commands in the read-only sandbox. Its permission text limits writes and network, not which files may be read, so treat reads as unconfined: blindness rests on the restriction of condition (b), not on this flag. |
| `--disable memories`, `--disable hooks`, `--disable view_image` | Turn those three features off (`-c features.<name>=false`). The third removes the tool that shows the model an image file by its path, which Codex registers only while that feature is on (`codex-rs/core/src/tools/spec_plan.rs` line 1440) and whose use the event log does not list (below). |
| `--json` | Prints the events to stdout. With `--ephemeral` no session file is kept, so this stream is the interface's only record of the session, and it does not list everything the session reads (below), so it can discard a reading but never establish one. |
| `-o` | Writes the final message to a file. |

These options do not switch off Codex's global instruction file (`$CODEX_HOME/AGENTS.md`): `--ignore-user-config` covers `config.toml` only, and the file still loads.
`codex debug prompt-input --disable memories --disable hooks --disable view_image`, run from `<dir>`, shows what reaches the model without calling one: at 0.166.0 it showed that file and, beside it, the list of installed skills, though that subcommand does not take `--ignore-user-config` and so renders with the user's configuration.
Check that what it shows carries nothing of your account or record, and name the global instruction file in your report as loaded.

### What the event log shows

`events.jsonl` cannot confirm what a session read, because at 0.166.0 it does not list every read.
Its mapping keeps agent messages, reasoning, command executions, file changes, MCP tool calls, some sub-agent calls and web searches, and drops every other kind of item (`codex-rs/exec/src/event_processor_with_jsonl_output.rs` lines 143-325, `_ => None` at line 323), among them `ImageView`, which carries the path of a file the model viewed (`codex-rs/app-server-protocol/src/protocol/v2/item.rs` line 473).
The model reaches its tools through a code-mode `exec` tool, which runs JavaScript that calls the others: Codex takes the tool mode from the model's catalogue entry first (`codex-rs/core/src/tools/mod.rs` lines 66-67), and the entry Codex had cached for `gpt-6-astra` gave `code_mode_only`.
On 2026-11-05, on macOS 27.2 at codex-cli 0.166.0, sessions of `gpt-6-astra` at low effort were run with the command above, without `--disable view_image` except where said, in a scratch directory holding only a text file that carried a random token and a small image, of one colour at first and of two later.
They ran from an agent session that was already sandboxed, so the four sessions below in which a read was to succeed used `-s danger-full-access`, for this observation only: under it Codex applies no sandbox of its own, and the commands ran under that session's sandbox.

- Asked to run `cat` on the text file, a session replied with the token, and the log listed the command, `/bin/zsh -lc 'cat note.txt'`, with exit code 0: a command that runs inside the code-mode tool is listed.
- Asked to view the image, a session named its colour, and the log held agent messages and nothing else; so it did with the flags of the form below, where a session named both colours of the second image.
- Asked to have a sub-agent read the text file, a session replied with the token, and the log listed a wait on a sub-agent and no command.
- Asked to start a shell and type `cat` on the text file into it through `write_stdin`, a session replied with the token, and the log listed the shell, `/bin/zsh -lc sh`, as started, and nothing typed into it.

Codex also reads files itself, outside its command sandbox, so that sandbox does not bound what a session reads even where no command runs. At `rust-v0.166.0` its local filesystem routes a read through the sandbox only when the sandbox context asks for that, and otherwise reads unsandboxed (`codex-rs/exec-server/src/local_file_system.rs` lines 91-105); and `apply_patch` reads each file its patch names while preparing the patch, before the file-change event is emitted (`codex-rs/core/src/tools/handlers/apply_patch.rs` lines 464-590, `emitter.begin` at line 590; the read itself in `codex-rs/apply-patch/src/file_update.rs` lines 32-43), so its error can tell the model whether a file could be read and whether lines the patch quotes are in it, with nothing in the log. And a session with the flags of the form below viewed an image while Codex's sandbox could not start (the second observation above).

So a session can open files that the log never shows, through a command that runs or through a read Codex makes itself, and a confirmation read from the log would pass such a session as blind.
Without `--ephemeral`, Codex keeps a session file, but keeping it breaks step 3's requirement that the session keep nothing behind, and no positive control has shown that it lists each kind of read.
So neither a record Codex keeps nor its command sandbox establishes what a session read: run Codex under the restriction of condition (b), as the next section says, or use a route that meets condition (a).

## Under a restriction on what Codex can read

Condition (b) asks that the whole Codex process, every child included, run under an operating-system restriction that refuses every file read except a closed list of paths, none of which holds, or is a directory above, your record or your account, reasoning, implementation, notes or session transcripts. On macOS one way to build it is to start `codex` under `sandbox-exec` with a profile that denies `file-read*` and then allows the closed list. Which paths Codex needs on that list was not established, and no such restriction was observed when this was written: the observations below, made before your run with its own command, flags and restriction, decide whether yours meets the condition. They cannot judge the paths the list admits outside the canary's directory, `$CODEX_HOME` among them: that each holds none of your material is your own check, so name each admitted path in your report; a path you misjudge is a risk this reference accepts, not one it closes.

Codex runs the model's commands under its own sandbox, which on macOS it applies with `sandbox-exec`, and a process already inside a macOS sandbox could not apply a second one wherever this was tried. This rests on observation, not on documentation: on 2026-11-05, from an agent session confined that way on macOS 27.2, `/usr/bin/sandbox-exec -p '(version 1)(allow default)' /usr/bin/true`, whose profile allows everything, and `codex sandbox -- /usr/bin/true` at codex-cli 0.166.0 both exited 71 with `sandbox-exec: sandbox_apply: Operation not permitted`; and in an adopting project's runs of this step from such a session, the command above returned replies saying that every read of the directory's files failed with that message, and no formalization.

So a Codex session started from a session that is already sandboxed meets neither condition at codex-cli 0.166.0: no further operating-system restriction can be applied there, and Codex reads files itself outside its command sandbox ([above](#what-the-event-log-shows)), so nothing below the tool keeps it from what your own session may read, your repository and record included. Its reading is unconfirmed, and step 3 does not accept it: use a route that meets condition (a), or report step 3 as blocked, as its item 2 says for a model that cannot be reached.

Tell which case you are in before the run, from the session that will start Codex, with the sandbox probe `codex sandbox -- /usr/bin/true`, which runs a command under Codex's own sandbox (`codex sandbox --help`), and keep its output. Exit status 71 with `sandbox_apply: Operation not permitted`: your session is already sandboxed, so the paragraph above applies. Exit status 0: build the restriction, and run the probe again inside it, where it must exit 71 the same way, which shows that Codex's own sandbox cannot start there and so that no command the model asks for runs (below). Anything else, from either probe: find out why before going on.

**The canary.** Before the run, with the run's own command, flags and restriction, observe at the version in use that the restriction refuses a read beside your record, both ways:

1. Write a file holding a random token in the directory that holds your record, outside version control: untracked, and never committed.
2. Read it through a plain command, `cat <canary>`: without the restriction it must print the token, and under the restriction it must be refused.
3. Read it through Codex's own in-process read: run the command of the form with a prompt asking the model to call `apply_patch` with an update to the canary, by its absolute path, whose patch quotes a line the canary does not hold, and to reply with the tool's error exactly. Without the restriction the error must be `Failed to find expected lines`, which shows that Codex read the file (`codex-rs/apply-patch/src/file_update.rs` line 156), and under the restriction it must be `Failed to read file to update` (line 38); both texts are read from Codex's source at `rust-v0.166.0`, not observed.
4. Delete the canary.

Each read without the restriction is the positive control: a read that does not succeed there shows nothing when it fails under the restriction. If any of these observations differs, the restriction is not shown to meet condition (b): do not run the form under it. An in-process read by a Codex tool not named here is refused by the operating system whichever tool makes it; but Codex may hand work to a process the restriction does not cover, such as a daemon started earlier, and the `apply_patch` observation, made through the run's own command, flags and restriction, is what detects that.

**The form.** Run the command above under the restriction, with one flag added before the prompt argument, `-c 'approval_policy="never"'`, and otherwise as it stands, `-s read-only` and `--disable view_image` included; besides that flag, change only the prompt: after the prompt that fits, unchanged, put a blank line, then the line

```text
This session cannot open files, so the contents of the directory's files are given here, each exactly as it stands, between the lines that name it; read nothing else.
```

and then each of the directory's files between a line `----- begin <name> -----` and a line `----- end <name> -----`. Build it from the files by a script, never by retyping them, so that each block is its file exactly.

Codex also adds material of its own to the model's input before the model starts, and in this form the embedded files are part of the input it reads for that. At `rust-v0.166.0`, a `$name` or a linked `[$name](path)` in them makes Codex load the installed skill or app of that name (`codex-rs/skills/src/mentions.rs` lines 84-148; selection and injection in `codex-rs/core/src/session/turn.rs` lines 1177-1211), and Codex reads a selected skill's body without a sandbox (`codex-rs/ext/skills/src/host_outcome.rs` lines 116-127, `/*sandbox*/ None` at line 124); a linked `[@name](plugin://...)` selects a plugin (`codex-rs/core/src/plugins/mentions.rs` lines 99-101); and Codex's extensions may add further items computed from the input (`codex-rs/core/src/session/turn.rs` lines 1276-1329). The log shows none of these, since its mapping drops them (below), and `codex debug prompt-input` does not either: it builds the input without entering the turn ("Prompt debugging builds a standalone request without entering run_turn", `codex-rs/core/src/prompt_debug.rs` line 89), so its rendering of `"probe"` exercises no mention. So step 3's check of whatever the interface loads by itself reaches here. Before the run, confirm that nothing under `$CODEX_HOME` and no skill, plugin or app installed for Codex carries anything of your account, record, reasoning or implementation, and record that check. The skills are those `codex debug prompt-input` lists from `<dir>`, plus any skill your user configuration disables: that command loads the user configuration while the run ignores it, so a skill disabled there may be missing from its list and still load in the run. That Codex adds nothing by itself from anywhere else is an assumption: which extensions a build carries was not established.

Keep `-s read-only`. Under it the model's commands go through Codex's sandbox (`-s` selects "the sandbox policy to use when executing model-generated shell commands", `codex exec --help`), which cannot start here, so none runs. Two things in Codex's source at `rust-v0.166.0` bear on that. A command that a rule of Codex's exec policy allows outright runs outside the sandbox (`codex-rs/core/src/exec_policy.rs` lines 442-451), so check before the run that no rules file in Codex's configuration folders allows one (`$CODEX_HOME/rules`; `<dir>` holds none). And an approval can let one run outside it, which the approval policy `never` rules out: under it Codex rejects every request to run a command with escalated permissions ("you cannot ask for escalated permissions if the approval policy is", `codex-rs/core/src/tools/handlers/unified_exec/preparation.rs` lines 274-282), grants nothing that a request for permissions asks (`codex-rs/core/src/session/mod.rs` lines 3245-3251), and does not retry without the sandbox a command the sandbox refused (`codex-rs/core/src/tools/orchestrator.rs` lines 439-442, `codex-rs/core/src/tools/sandboxing.rs` lines 347-353). `codex exec` sets `never` by default (`codex-rs/exec/src/lib.rs` lines 595-597) but drops it when a configuration it still loads, such as one your machine manages, routes approvals to automatic review (lines 785-816), which is why the form adds the flag. A session flag yields only to the legacy managed configuration layers (`codex-rs/config/src/config_layer_source.rs` lines 33-50), so establish the effective policy before the run: from `<dir>`, `codex debug prompt-input --disable memories --disable hooks --disable view_image -c 'approval_policy="never"' "probe"` calls no model and renders what would reach it, and its output must contain `Approval policy is currently never.`, the text Codex renders for `never` (`codex-rs/prompts/templates/permissions/approval_policy/never.md`, chosen at `codex-rs/prompts/src/permissions_instructions.rs` line 324; observed at 0.166.0, and not rendered for `on-request`), and must not contain `view_image`, the name of the tool the flag removes (observed at 0.166.0: three times in that rendering without the flag, never with it). If it fails either, do not run the form. Do not reach for `-s danger-full-access` or `--dangerously-bypass-approvals-and-sandbox`, which the help offers for "environments that are externally sandboxed": under either, the model's commands run, writing wherever your own session may, and the evidence below no longer shows that the session ran no command or changed nothing.

**That the whole prompt arrived.** The prompt goes on the command line, so it must fit the argument list with the environment (`getconf ARG_MAX`, 1048576 bytes on the machine observed), and Codex takes at most 1,048,576 characters in one input (`MAX_USER_INPUT_TEXT_CHARS`, `codex-rs/protocol/src/user_input.rs` line 10). Each refuses a longer input rather than cutting it: `execve(2)` fails with `E2BIG`, and `codex exec` sends the prompt in one `turn/start` request (`codex-rs/exec/src/lib.rs` lines 1236-1274), which the app server refuses with "Input exceeds the maximum length" before the turn starts (`codex-rs/app-server/src/request_processors/turn_processor.rs` lines 524-552). So record the prompt's size in bytes and in characters (`wc -c`, `wc -m`), and a log holding `turn.started` and `turn.completed` shows that Codex took the whole prompt. Nothing at 0.166.0 reports a later cut, such as a compaction of a context longer than the model's window (the log drops that kind of item, below): keep the prompt well inside that window, and treat it as an assumption that nothing else shortens it.

**The evidence to record**, beside the prompt and the reply: the sandbox probe's output from your session and inside the restriction; the restriction, with each path its closed list admits and your check that none holds your material; the canary observations, each with its positive control, and the canary's deletion; that no rules file allowed a command; the approval line that `codex debug prompt-input` rendered, and that it rendered no `view_image`; the check of `$CODEX_HOME` and of the skills, plugins and apps installed for Codex; the prompt's two sizes; `events.jsonl`, in which every item must be an `agent_message` or a `reasoning` item, since an item of any other kind, such as a web search, means the session was not what this form assumes, so discard its reply and find out why; and the reply's part 3. Read them for what each shows:

- That nothing of your account, record, reasoning or implementation reached the model beyond the prompt rests on the restriction, the canary observations and your own check of each admitted path, with the risk named above: the operating system refuses every read outside the closed list, whether a command makes it or Codex makes it itself, through `apply_patch`, an image view or a tool not named here, and the observations show, through the run's own command, flags and restriction, that it refused a read beside your record both ways. The model's input is not the prompt alone: Codex adds its own instructions, the list of installed skills and whatever a mention selects, which the check of what Codex loads by itself covers, with the assumption named there. Neither the log, nor the reply's part 3, nor any check below establishes it.
- That the session ran no command rests on the sandbox probe inside the restriction, the rules check and the approval check: each command Codex runs under its sandbox fails to start inside the restriction, no rule let one run outside it, and under `never` a request to run one with escalated permissions is refused and a command the sandbox refused is not retried without it. A sub-agent the model starts is a thread the same Codex process starts (`codex-rs/core/src/agent/control/spawn.rs` line 188), whose configuration is the parent's, features included, with the parent turn's approval policy and permission profile copied onto it (`codex-rs/core/src/agent/child_config.rs` lines 132-134 and 179-200); and `spawn_agent` takes no setting that changes either: its parameters, in the tool list `codex debug prompt-input` renders at 0.166.0, are its task, its name, a model, an effort and whether it inherits the parent's history.
- The log alone does not show it. At 0.166.0 the log reports, of what the session does, only commands, file changes, MCP tool calls, some sub-agent calls and web searches, and drops every other kind of item (`codex-rs/exec/src/event_processor_with_jsonl_output.rs` lines 143-325, `_ => None` at line 323), among them an image the model views by path and a compaction of the context; and, as [the observations above](#what-the-event-log-shows) show, it lists neither a command a sub-agent runs nor what is typed into a running command. Nor did it list commands refused before they start: in the adopting project's refused sessions, whose replies say that each read was attempted and refused, it held nothing but agent messages.
- What the log adds is that it logged none of the kinds it reports: no command, web search, MCP call, file change or wait on a sub-agent. That can discard a reading, never establish one.
- That the session changed nothing rests on no command having run, as the second point shows, on `-s read-only`, whose permission text limits writes, and on `--ephemeral`, which keeps no session files.
- That the session viewed no image rests on `--disable view_image` and on the check that `codex debug prompt-input` rendered no tool of that name, not on the log, which drops an image view, nor on the probe: Codex reads the image itself, and with this form's other flags, from the already sandboxed session of [the observations above](#what-the-event-log-shows), a session asked to view the image without the flag named both its colours. With the flag, a session asked the same replied that it had no such tool; and a sub-agent, started without the parent's history and asked to view it, named both colours without the flag and had no such tool with it.

## The prompt for a record

Fill in the subject line, keep the rest as written, and add nothing about what you think the owner wants.

```text
You are formalizing what an owner wants from one deliverable, as a Lean 4 intent record. Work independently: another formalization exists, and you must neither look for it nor guess at it.

Read only the three files in this directory: owner-words.md (the owner's words, exactly as given), types.lean (the definitions of the types the subject is stated over) and Record.lean (the lean-intent library's intent record). Read nothing else, on this machine or online.

The subject is <its name> : <its Lean type>, or, where this line gives no type, a subject whose type you choose and state.

Reply with three parts.

1. A Lean file that imports LeanIntent.Record and declares one LeanIntent.IntentRecord for the subject:
   - a property for each thing the owner's words require of the subject, named so that the owner can read it;
   - a domain hypothesis for each fact about the world that those properties rely on;
   - the predicates the properties are written in, in vocab;
   - the shape that fits what the subject is, as Shape in Record.lean describes.

2. In plain words: each property and hypothesis; each point where the owner's words left you a choice, with the choice you made and why; and each requirement you inferred rather than read in the words.

3. Every file you read, by its path.

Formalize what the words require, as their owner would mean them, at full strength: no property weaker or stronger than the words support, and none they do not support.
```

## The prompt for cases

Use this where the subject's type or domain is itself what is in question, because a record can take that type or predicate as a parameter and so compare nothing.
Fill in the three lines in angle brackets from the owner's words and the input's format, in their terms and never in your record's, keep the rest as written, and add nothing about what you think the owner wants.
No number of cases is required: rbeauchamp/regula PR 524's second reading gave 76, and what counts is that they reach each distinction.

```text
You are reading what an owner wants from one deliverable, and you will answer with concrete cases and verdicts. Work independently: another reading exists, and you must neither look for it nor guess at it.

Read only the files in this directory: owner-words.md (the owner's words, exactly as given), input-format.md (what an input is, which says nothing of what the owner wants) and types.lean, where it is present (the input's Lean type). Read nothing else, on this machine or online.

The deliverable is <its name>.
An input is <what one input is>.
The verdict on an input is one of <the outcomes the owner's words name>, or "the words do not settle this".

Reply with three parts.

1. A numbered list of inputs, each with its verdict and the words it rests on:
   - write each input out in full, in its own format, with no free variable or placeholder and no reference to a predicate, so that a reader with only that case can tell what the input is;
   - give one verdict for each, resting on nothing left undefined: where you would say "it depends", write each alternative as an input of its own;
   - choose the inputs yourself, as many as it takes to reach each distinction you can find in the words: ordinary inputs, unusual inputs the words still cover, ordinary-looking inputs the words exclude, and for each distinction a pair of inputs that differ in that one respect and get different verdicts.

2. In plain words: each point where the owner's words left you a choice, with the choice you made and why; and each requirement you inferred rather than read in the words.

3. Every file you read, by its path.

Give no Lean record and no general rule in place of the cases. Judge what the words require, as their owner would mean them, at full strength: no verdict that the words do not support.
```

## Where the formalization and the comparison live

The step exists so that a machine checks the comparison between the second model's formalization and your record, and a comparison that the project's proof check never builds is checked by nothing, however finished it reads: in an adopting project, the second model's record and the theorems comparing it with the intent record sat in an uncommitted scratch file that the proof check never ran, and the step read as done. By the proof check this section means the check the project runs on every change to establish its proofs, such as the build its validation gate or CI runs. So what the step proves is committed in the project, in modules that check builds, and is checked on every run of it:

- **The second model's formalization**, in a module of its own beside your record: its record, elaborated, or, where it gave cases, each case written in your input's type. The module imports only what defines the types the subject is stated over, as your record's module does (step 1), and lean-intent's `LeanIntent.Record` where it holds a record; it never imports your record, so nothing of yours can enter it. Correct only what Lean refuses to elaborate, without changing the meaning, and note each correction in a comment beside it, with what the reply had. Where it holds a record, declare that record as a record only, never as a deliverable: lean-intent's confirmation check asks about every deliverable it finds as one the owner must confirm (`docs/confirmation.md`, under what is trusted).
- **Every theorem comparing it with your record**, in a module of its own that imports both: each direction proved (`∀ w, mine.Meets w → theirs.Meets w`), each subject exhibited as meeting one record and failing the other, and, where it gave cases, your record's verdict on each case. Prove each with no `sorry`, audited as the project audits axioms, as step 2 asks of the obligations. A direction you can neither prove nor refute stays a difference stated in plain words and labelled unproved, never a theorem left with `sorry`.

Committing a module does not make the check build it. A check that builds declared targets builds only the modules those targets reach: in Lake, a library's built-in `leanArts` facet builds the modules its `globs` name, which default to one for each of its `roots`, and, recursively, every module of the workspace they import, its `roots` defaulting to the library's own name, and `lake build` with no argument builds the package's default targets and nothing else (Lake's README, `Lake/Config/LeanLibConfig.lean` and `resolveDefaultPackageTarget` in `Lake/CLI/Build.lean`, at Lean v4.35.0). So a module under the library's directory that no root imports and no glob names is not built. Reach every such module from a target whose selected facets compile it, following the project's own rules for where its files go: for example, import the comparison module, which imports the formalization's, from a root of a library whose built-in `leanArts` facet the check builds, or name each module in that library's `globs`.

Then confirm, from Lake's own account of what the check builds, that it builds them, once every such module is committed and `git status` shows none of them untracked or changed, since a glob also finds a file that is not committed. Find the targets and facets the check builds from the command the project runs on every change: a bare `lake build` builds the package's default targets (`defaultTargets` in `lakefile.toml`, `@[default_target]` in `lakefile.lean`), and `lake build <target>` the targets it names. For each Lean library among them, first establish from its configuration and the selected facets' build definitions that the check reaches its built-in `leanArts` facet. An unqualified library target selects `default`, which builds the library's `defaultFacets`, normally `#[LeanLib.leanArtsFacet]`; an empty array builds nothing (`resolveConfigDeclTarget` in `Lake/CLI/Build.lean`, `LeanLibConfig.defaultFacets` in `Lake/Config/LeanLibConfig.lean` and `LeanLib.recBuildDefaultFacets` in `Lake/Build/Library.lean`, at Lean v4.35.0). If that linkage is absent, have the routine proof check build `@/<library>:leanArts` before accepting the listing; merely naming a library or listing its modules establishes no compilation. For each library with that linkage established, `lake query @/<library>:modules` prints, one per line, the modules its built-in `leanArts` facet builds: those its `globs` name and, recursively, the modules of the same library that they import (`LeanLib.recCollectLocalModules`, and `LeanLib.recBuildLean`, which builds each module that facet lists, in `Lake/Build/Library.lean` at Lean v4.35.0); the query builds nothing. Each module holding the formalization or the comparison must appear in that output for a library whose built-in `leanArts` facet the check builds. A module that appears in none is not confirmed by it, even where a module the check builds imports it from another library: move it into a library whose built-in `leanArts` facet the check builds, or name it in that library's `globs`, and list again. A proof check that is not a Lake build of named targets gives the same account from its own definition, such as the list of files it compiles; say in the report how you read it. Lean stops reading a file at `#exit` and reports only a warning, so a module the check builds checks nothing written after one: keep no `#exit` in these modules. Building a module by name, such as `lake build <Module>`, shows only that the module builds, not that the check builds it. Keep the check's command, the facet linkage and the listings for the report.

The step is not done until every such module is committed and that confirmation has passed for each. A later change that makes any of them fail the check, such as a revision of your record, is a failing proof of the project like any other: prove it again, or, where the revision changed what holds, state the difference it now shows and settle it as step 3 says of each difference; never delete the module or take it out of what the check builds to make the check pass.

What may stay private to the project's agents, outside the repository, is the sessions themselves: each prompt you sent, the reply as the model gave it, each session's logs, such as Codex's event log, and the other evidence this reference has you record. The report draws on them; the check needs none of them, since the modules carry the formalization, each correction made to it and the comparison.
