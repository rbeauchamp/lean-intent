# The blind formalization's inputs, prompts and results

## The directory

Make a new directory outside the repository and put in it only:

- `owner-words.md`: the owner's words, exactly as given, with nothing of yours added: those at the level step 1 started from, and, where the owner adopted a statement, that statement exactly as adopted, with nothing of the proposal's reasoning;
- `types.lean`: the source of the definitions of the types the subject is stated over, copied without the implementation or any other definition that is not a type;
- `Record.lean`: lean-intent's `LeanIntent/Record.lean`, from the commit the project pins.

Where the subject's type or domain is itself what is in question (step 3), the directory instead holds `owner-words.md`, `types.lean` where the input already has a Lean type, and `input-format.md`: the input's own format from that format's owner, such as the section of a tool's documentation that says what its configuration holds, with nothing that says what is wanted and nothing about your record.

Start the second model in a fresh session or context whose only material is that directory's contents: no earlier conversation, and nothing of your account, record, reasoning or the implementation in anything it can read (its workspace, memory, attached files or system prompt). Give it the prompt below that fits what you ask for, and save the prompt and its reply.
Through a command line, for example `codex exec` as [the Codex section](#the-codex-command) gives it, or `claude -p "<prompt>"` run from `<dir>` with the isolation of step 3 found in that tool's own help; through a desktop app, a new conversation whose workspace is `<dir>`; through an API, a request that carries only the prompt and the directory's files. Use a model of another provider than the one that wrote your record, and check the interface's own help for how to start it that way.
Whichever interface it is, take its reply as a blind reading only as [the next section](#what-makes-a-reading-blind) says, which also says what each of these interfaces needs.
The directory and the session stay outside the repository; what the project keeps of the result, and where, is set out in [the last section](#where-the-formalization-and-the-comparison-live).

## What makes a reading blind

A reading is blind when the session could obtain nothing of your material by any route. Your material is your record (the first formalization), your account, reasoning, implementation, notes and session transcripts, and anything made from them. A route is any way a byte that the prompt did not carry can reach the model, and every such byte arrives in one of four ways, told apart by who supplies it:

1. **The interface adds it to the model's input by itself**: its own instructions, an instruction file, a list of skills, plugins or apps, a memory of earlier sessions, an earlier conversation, or whatever a mention in the prompt selects.
2. **A tool the model can call returns it**, whoever runs the tool: the interface on your machine (a file read, a command, a patch, a sub-agent, a configured server) or the provider (a web search, a connected app, any other hosted tool).
3. **The provider adds it by itself**: state it stores for the account or the conversation, or retrieval that a model or an endpoint applies with no tool in the request.
4. **The model already holds it** from its training.

These are every case, because a reply depends only on the model's weights and its input, only the interface and the provider put anything in that input, and what either puts there is the prompt, the result of a tool call, or something it adds by itself.

**List the routes from the interface, never from the ones you have in mind.** Before the run, at the version in use, ask the interface itself what the session can reach: the tools the session has, as the session itself reports them, nested and deferred tools included, through the interface's own listing of them where it has one; what the interface adds to the input, from its own rendering of that input; each feature or setting that adds a tool or an input, from its own list of them; and whatever is configured that a tool of the session can reach, such as a server, from the interface's own account of its effective configuration, never from a listing of what configured things offer, which comes back empty for one that offers nothing and still answers when addressed. Give each observation of an absence a positive control: the same observation made where the thing is known to be present and found to show it, since a listing never seen to list anything shows nothing when it comes back empty. This reference once stated its second condition for file reads alone, from the one route its author had in mind and from a rendering that does not show the tools nested under Codex's code tool, and a session that met it had a web tool, an image tool and connected apps (rbeauchamp/lean-intent#79).

**What evidence closes, and what it cannot.** Evidence you can gather closes the first way, for whatever the interface takes from your machine, and, of the second, every tool the session reports. No observation available to you establishes the rest, under either condition below: what the provider adds by itself beyond what the request declares, whether it reaches the model directly or in something the interface fetches from it; a hosted tool that the session leaves out of its own report; and what the model holds from training. All three lie on the provider's side of the request, where nothing you run can look, and only a model run on your own machine would remove them. So they are trusted, not shown: neither condition, and nothing this reference has you record, shows that the provider adds nothing, and your report names the three as trusted. A capability that an interface's own report does show, at whatever version, is no part of this: it is evidence to gather. The three can carry nothing of your material while it is nowhere they could reach. That is what step 3's item 1 secures for your record, which you keep unpublished until the reading is done: committed on your machine and sent nowhere else, to no host, public or private, and to no session of the second model's provider. [When the record is already public](#when-the-record-is-already-public) says what to do where that no longer holds.

Take a reply as a blind reading only when one of two conditions holds, and name in your report which, with the evidence for it and with what stays trusted:

- **(a) No tool and no stored state.** You build the whole request, it gives the model no tool and names no stored state, and nothing stands between you and the provider that could add to it: for example an API request that carries only the prompt and the directory's files, with no tools and no earlier conversation or stored response. The evidence is the request exactly as you sent it, in which the list of tools is empty, hosted tools included, and no field names a conversation, a stored response, a file or a memory; the response as returned, in which no item reports a tool call or a retrieval; and the provider's documentation of that model and endpoint at the time, read for whatever either applies by default, with each thing it says can be turned off turned off in the request; a model or endpoint that it says retrieves or stores with no way to turn that off does not meet this condition. That closes the first way, since no interface adds to your request, and the reported part of the second, since the request declares no tool. Prefer this condition where you can reach it: it closes the tools by building a request without them, where (b) closes them by observations that hold for one version of one tool.
- **(b) A read restriction below the tool, and a closed list of tools.** Each of the following holds, observed at the version in use, and with the run's own command, flags and restriction unless the item says otherwise:
  - The whole process of the tool that runs the model, every child included, runs under an operating-system restriction that refuses every file read except a closed list of paths, none of which holds, or is a directory above, your material.
  - Before the run, the restriction refuses a read of a canary file beside your record, both through a plain command and through the tool's own in-process file read, each read having first been observed to succeed without the restriction.
  - The session's own report of its tools equals a closed list, each tool of which is shown to return nothing but what the prompt carries, what the closed list of paths holds, or what cannot carry your material, such as the time. The report is made before the run and again by the run's own session. Before the run, the same report, made where a tool outside the list is known to be present, shows that tool. A tool outside the list, a tool on the list that the report lacks, or a report that fails that positive control refuses the reading.
  - Where a tool on the closed list returns what something configured offers, as a tool that reads the resources of a configured server does, the interface's own account of its effective configuration, over every layer it reads, shows that nothing of that kind is in effect for the session, and the same account, made where such a thing is known to be configured, shows it. That account is taken with the run's own settings, and may be taken without the restriction where it then reads every layer the run reads. An empty listing of what configured things offer is never that account: a configured thing may list nothing and still answer when addressed.
  - What the interface adds to the input by itself from your machine is read from its own rendering and holds nothing of your material, or cannot load because the restriction refuses the read.

  That closes the first way, for whatever the interface takes from your machine, and the reported part of the second, for the tools the interface runs on your machine and the tools the provider runs alike: no local rule on files or on the network reaches a tool the provider runs, and only the session's report shows whether it has one. [The section on that restriction](#under-a-restriction-on-what-codex-can-read) sets all of this out for Codex.

What each interface named above needs:

- **An API request** can meet (a) as it stands.
- **`codex exec`** gives the model tools, so it does not meet (a); it meets (b) only in [the form below](#under-a-restriction-on-what-codex-can-read), with every observation that section asks for.
- **Another command-line tool**, such as `claude -p`: this reference gives no form for one. It meets (a) only if its own help gives a way to start a session with no tool and no stored state and the session's own report then shows none, and (b) only once you have built for it, at its version, what the Codex section builds: the restriction with both canary observations, the settings that remove its tools, the session's report of what remains with its positive control, for each remaining tool what it can return, and, where one returns what something configured offers, the tool's own account of its effective configuration with its positive control.
- **A desktop app** meets (b) only if its whole process can be started under such a restriction and its session's tools reported and bounded the same way, and (a) only if you can show that the conversation gives the model no tool and no stored state. Where you cannot see all of its settings and all of what its account stores, you can show neither.

A session whose model has tools, or that carries memory, a workspace or an earlier conversation, as a command-line or desktop session usually does, does not meet (a), and meets (b) only when each part of it was observed through that session's own command, flags and restriction.
A transcript, a tool log or the model's own list of files may still be recorded, and each can discard a reading: anything in them outside the directory's files, or a log item that [the Codex form](#under-a-restriction-on-what-codex-can-read) does not admit, means the formalization is not blind, so discard it and start a fresh session. None of them establishes a reading: a session can read what none of them shows, as [the observations of Codex below](#what-the-event-log-shows) found.
A reading that meets neither condition is unconfirmed, and step 3 does not accept it: discard it, and either use a route that meets a condition or report step 3 as blocked, as its item 2 says for a model that cannot be reached.

**A reading accepted before condition (b) named the tools.** Until the change that closed rbeauchamp/lean-intent#79, condition (b) asked for the restriction and the canary alone. A reading accepted under it then is unconfirmed: its evidence covers file reads and says nothing of the session's other tools. That is not a finding that it was contaminated, since nothing shows that such a session used one. Say so wherever a report or a record of the project calls that reading blind, or take the reading again under the conditions above. The theorems that compare the two formalizations stand as proved either way; what is unconfirmed is only that the second was made without sight of the first.

## When the record is already public

Step 3 has you keep your record unpublished until the reading is done, which is what leaves the trusted part above with nothing of it to return. Sometimes that no longer holds when the reading is due: the record, in this or an earlier version, was pushed before the reading, or a session of the second model's provider was given it, for example to review a change. Then:

- Do not try to undo it: deleting what was pushed does not show that no copy remains where a search or a provider could reach it.
- The evidence of the condition you use is still owed, unchanged: it is what shows that the session had no web tool, no connected app and no other reported tool that could fetch what is public.
- The three trusted things are now live, since each could return the published record: what the provider adds by itself, a hosted tool that the session leaves out of its report, and what the model holds from training. Name each in your report as trusted and not shown, with what was published or given, where and when.
- Of the three, training is the one that dates can settle. Compare the day the record first became reachable with the model's training cutoff as its provider documents it, and record both, with where you read the cutoff. If the record became reachable later than the cutoff, take the reading, with the other two named as trusted. If it became reachable earlier, or the provider documents no cutoff for that model, the reading is unconfirmed: use a model whose documented cutoff is earlier than the publication, or report step 3 as blocked, as its item 2 says for a model that cannot be reached.
- The same three could return other material of yours that was never kept unpublished, such as an implementation that a public repository already holds. This reference gives no rule for that beyond naming it: say in your report what was public and since when, as something the model may hold from training.

## The Codex command

Keep the prompt, the reply and the event log in a second directory outside `<dir>`, so that the session's only material stays the directory's files.

```sh
codex exec -C <dir> --skip-git-repo-check \
  --ephemeral --ignore-user-config -s read-only \
  --disable memories --disable hooks --disable view_image \
  -c 'web_search="disabled"' --disable apps --disable plugins --disable image_generation \
  --disable shell_tool --disable goals --disable sleep_tool \
  -c agents.enabled=false -c tools.experimental_request_user_input.enabled=false \
  -m <model> -c model_reasoning_effort=<effort> \
  --json -o <outside>/reply.md \
  "$(cat <outside>/prompt.txt)" < /dev/null > <outside>/events.jsonl
```

Each flag was read from the help of codex-cli 0.166.0 and again at 0.170.0 (`codex exec --help`, and `codex features list` for the feature names). Of the `-c` keys of the fourth and sixth lines, `agents.enabled` and `tools.experimental_request_user_input.enabled` were read from Codex's source at `rust-v0.170.0` (`codex-rs/core/src/config/mod.rs` lines 4111-4115 and 2803-2809), and `web_search` rests on its observed effect ([below](#what-the-session-can-call)). If your version differs, read them again, and where a flag has gone find its current equivalent rather than dropping it.
The tool settings of the fourth to sixth lines are the means and never the evidence: a version, a model or an account may give the session a tool that none of them removes, so what decides is [the session's own report of its tools](#what-the-session-can-call).
Run it only in [the form below](#under-a-restriction-on-what-codex-can-read), under the restriction of condition (b): Codex's own sandbox limits the commands the model runs, not the reads Codex makes itself, and where that sandbox starts, the model's commands run, and [the event log does not show everything they read](#what-the-event-log-shows).
The Acorn pilot of this method, then called spec-first, ran a session of this kind at 0.165.0 (rbeauchamp/acorn PR 188, `docs/spec-first-pilot.md`), and [the sessions below](#what-the-event-log-shows) ran the command as it then stood, without the tool settings of its fourth to sixth lines, at 0.166.0 from a session already sandboxed, some with `-s danger-full-access` in place of `-s read-only`, with short prompts of their own rather than a formalization's, and none under the restriction of condition (b). On 2026-11-18, at 0.170.0, sessions ran the command as it stands here, again with short prompts of their own, under such a restriction ([below](#what-the-session-can-call)). No formalization was run with it, so treat your first run as the check of it.

| Part | What it does |
|---|---|
| `< /dev/null` | Closes the command's input; the Acorn pilot observed Codex otherwise waiting on stdin, and the help says piped stdin is appended to the prompt. |
| `--ephemeral` | Persists no session files. |
| `-C`, `--skip-git-repo-check` | Make `<dir>` the working root and allow it not to be a Git repository. |
| `--ignore-user-config` | Does not load `$CODEX_HOME/config.toml`, so what that file configures stays out; auth still uses `CODEX_HOME`. That includes the configured model and effort, so name them with `-m` and `-c`. It drops that one layer of Codex's configuration, with a selected profile's file, and no other: the servers and settings of every other layer stay in, so the flag does not show that the session has no server ([the paragraph on the session's servers](#what-the-session-can-call)). |
| `-s read-only` | Runs the model's commands in the read-only sandbox. Its permission text limits writes and network, not which files may be read, so treat reads as unconfined: blindness rests on the restriction of condition (b), not on this flag. |
| `--disable memories`, `--disable hooks`, `--disable view_image` | Turn those three features off (`-c features.<name>=false`). The flags are the means: what shows each off for your session is Codex's own listing of its features, the fourth observation [before the run](#what-the-session-can-call). The third removes the tool that shows the model an image file by its path, which Codex registers only while that feature is on (`codex-rs/core/src/tools/spec_plan.rs` line 1440 at `rust-v0.166.0`, line 1491 at `rust-v0.170.0`) and whose use the event log does not list (below). |
| `-c 'web_search="disabled"'`, `--disable apps`, `--disable plugins`, `--disable image_generation` | Remove the tools that reach beyond the machine: the web tool, the tools of the account's connected apps, the tools of installed plugins and the image tool. [The table below](#what-the-session-can-call) gives the tools each was observed to remove. |
| `--disable shell_tool`, `--disable goals`, `--disable sleep_tool`, `-c agents.enabled=false`, `-c tools.experimental_request_user_input.enabled=false` | Remove tools the reading does not need, so that fewer remain to account for: the two that run a command and type into one, the three that keep a goal, the one that sleeps, the six that start and steer sub-agents, and the two that ask the user. The same table gives each. |
| `--json` | Prints the events to stdout. With `--ephemeral` no session file is kept, so this stream is the interface's only record of the session, and it does not list everything the session reads (below), so it can discard a reading but never establish one. |
| `-o` | Writes the final message to a file. |

These options do not switch off Codex's global instruction file (`$CODEX_HOME/AGENTS.md`): `--ignore-user-config` covers `config.toml` only, and without a restriction the file still loads.
Under the restriction of condition (b) it loads only where the closed list of paths admits it. At 0.170.0, with the file outside that list, each session's event log held one `error` item, `Failed to read global AGENTS.md instructions from <path>: Operation not permitted (os error 1)`, and the session's standard error said of each directory of installed skills that it could not be walked, with the same reason. Keep both outside the list, and say in your report that neither loaded, with that item and those lines as the evidence.
`codex debug prompt-input --disable memories --disable hooks --disable view_image`, run from `<dir>` without the restriction, shows what reaches the model without calling one: at 0.166.0 it showed that file and, beside it, the list of installed skills, though that subcommand does not take `--ignore-user-config` and so renders with the user's configuration; for the same reason it cannot run inside the restriction, where at 0.170.0 it exited 1 with `Failed to read config file`, the configuration file being outside the closed list of paths.
Check that what it shows carries nothing of your account or record.
It is no list of the session's tools. It renders the tools declared to the model directly and the description of the code tool, and that description may leave out tools nested under the code tool (below): at 0.170.0, with the flags this command had before the tool settings were added, the rendering named no `web__run`, a tool that a session with those flags reported.

### What the event log shows

`events.jsonl` cannot confirm what a session read, because at 0.166.0 it does not list every read.
Its mapping keeps agent messages, reasoning, command executions, file changes, MCP tool calls, some sub-agent calls and web searches, and drops every other kind of item (`codex-rs/exec/src/event_processor_with_jsonl_output.rs` lines 143-325, `_ => None` at line 323), among them `ImageView`, which carries the path of a file the model viewed (`codex-rs/app-server-protocol/src/protocol/v2/item.rs` line 473).
At `rust-v0.170.0` the mapping keeps the same kinds and drops the rest the same way (lines 144-326, `_ => None` at line 324), and a warning or notice from Codex is written as an item of kind `error` (lines 412-422 and 430-510).
The model reaches its tools through a code-mode `exec` tool, which runs JavaScript that calls the others: Codex takes the tool mode from the model's catalogue entry first (`codex-rs/core/src/tools/mod.rs` lines 66-67), and the entry Codex had cached for `gpt-6-astra` gave `code_mode_only`.
On 2026-11-05, on macOS 27.2 at codex-cli 0.166.0, sessions of `gpt-6-astra` at low effort were run with the command above as it then stood, with none of the tool settings of its fourth to sixth lines and without `--disable view_image` except where said, in a scratch directory holding only a text file that carried a random token and a small image, of one colour at first and of two later.
They ran from an agent session that was already sandboxed, so the four sessions below in which a read was to succeed used `-s danger-full-access`, for this observation only: under it Codex applies no sandbox of its own, and the commands ran under that session's sandbox.

- Asked to run `cat` on the text file, a session replied with the token, and the log listed the command, `/bin/zsh -lc 'cat note.txt'`, with exit code 0: a command that runs inside the code-mode tool is listed.
- Asked to view the image, a session named its colour, and the log held agent messages and nothing else; so it did with the flags the form below then had, where a session named both colours of the second image.
- Asked to have a sub-agent read the text file, a session replied with the token, and the log listed a wait on a sub-agent and no command.
- Asked to start a shell and type `cat` on the text file into it through `write_stdin`, a session replied with the token, and the log listed the shell, `/bin/zsh -lc sh`, as started, and nothing typed into it.

Codex also reads files itself, outside its command sandbox, so that sandbox does not bound what a session reads even where no command runs. At `rust-v0.166.0` its local filesystem routes a read through the sandbox only when the sandbox context asks for that, and otherwise reads unsandboxed (`codex-rs/exec-server/src/local_file_system.rs` lines 91-105); and `apply_patch` reads each file its patch names while preparing the patch, before the file-change event is emitted (`codex-rs/core/src/tools/handlers/apply_patch.rs` lines 464-590, `emitter.begin` at line 590; the read itself in `codex-rs/apply-patch/src/file_update.rs` lines 32-43), so its error can tell the model whether a file could be read and whether lines the patch quotes are in it, with nothing in the log. And a session with the flags the form below then had viewed an image while Codex's sandbox could not start (the second observation above).

So a session can open files that the log never shows, through a command that runs or through a read Codex makes itself, and a confirmation read from the log would pass such a session as blind.
Nor does the log show each tool call: at 0.170.0, sessions that ran the code tool twice ([below](#what-the-session-can-call)) logged nothing for the code tool itself, and logged the two calls it made to tools that list a server's resources as `mcp_tool_call` items.
Without `--ephemeral`, Codex keeps a session file, but keeping it breaks step 3's requirement that the session keep nothing behind, and no positive control has shown that it lists each kind of read.
So neither a record Codex keeps nor its command sandbox establishes what a session read: run Codex under the restriction of condition (b), as [the section on it](#under-a-restriction-on-what-codex-can-read) says, or use a route that meets condition (a).

### What the session can call

A tool is declared to the model in one of two ways: directly, or nested under the code tool, `functions.exec`, which runs JavaScript that calls the nested ones ([above](#what-the-event-log-shows)). At `rust-v0.170.0` the code tool's runtime builds the object that nested tools are called on, `tools`, and a list of them, `ALL_TOOLS`, from one and the same list (`codex-rs/code-mode-runtime/src/runtime/globals.rs` lines 26-27, 65-78 and 80-109), so `ALL_TOOLS` names each nested tool the session can call. The code tool's description, which is what `codex debug prompt-input` renders, may leave some of them out (`codex-rs/code-mode-protocol/src/description.rs` lines 17-18). A web search that the provider runs is declared directly and is never nested (`codex-rs/core/src/tools/spec_plan.rs` lines 724-754, line 686 and lines 1031-1033), so no listing by the code tool shows one, and for the directly declared tools there is no listing but the model's own account of them.

**The tool report** asks the session for both. Sent by itself, it follows the line `Report your tools, in the three parts A, B and C below, and reply with nothing else.` and a blank line; [the form](#under-a-restriction-on-what-codex-can-read) also puts it at the end of the run's own prompt.

```text
A. Every tool declared to you directly, that is, every tool you can call without going through another tool, hosted tools such as a web search included: one per line, as its namespace, a dot and its name.

B. Call your code tool once with exactly this JavaScript, and give its output exactly as it was returned, changing nothing:

text(JSON.stringify(ALL_TOOLS.map(t => t.name).sort()))

C. Call your code tool once with exactly this JavaScript, and give its output exactly as it was returned, changing nothing:

text(JSON.stringify([await tools.list_mcp_resources({}), await tools.list_mcp_resource_templates({})]))

If you have no code tool, write "no code tool" as parts B and C.
```

**The closed list.** On 2026-11-18, on macOS 27.2.1 at codex-cli 0.170.0, a session of `gpt-6-astra` at low effort, started from a shell that was not sandboxed with the command above and the one flag that [the form](#under-a-restriction-on-what-codex-can-read) adds, under a restriction of condition (b), gave this report: in part A, `functions.exec` and `functions.wait`; in part B, `["apply_patch","clock__curr_time","list_mcp_resource_templates","list_mcp_resources","read_mcp_resource"]`; in part C, `["{\"resources\":[]}","{\"resourceTemplates\":[]}"]`. Its event log listed the two calls of part C as `mcp_tool_call` items of a server named `codex`, with those two results, and listed nothing for the calls of the code tool itself. Those seven tools are the closed list, and what each can return is:

| Tool | What it can return |
|---|---|
| `functions.exec` | What the nested tools below return. By its own description it runs "raw JavaScript -- no Node, no file system, no network access, no console", and keeps a stored value only "for later `exec` calls in the same session". That description was read, not tested. |
| `functions.wait` | By its description, the "new output or completion" of a call of the code tool that is still running. |
| `apply_patch` | Whether a file could be read, and whether lines the patch quotes are in it ([above](#what-the-event-log-shows)): so what the closed list of paths holds, for which the canary's third observation is the evidence. |
| `clock__curr_time` | By its description, "the current time in UTC". |
| `list_mcp_resources`, `list_mcp_resource_templates`, `read_mcp_resource` | By their descriptions, what the session's servers offer; `read_mcp_resource` reads by a server's name and an address, whether or not anything was listed. So they return nothing only while the session has no server. Part C does not show that. A server may list nothing and still serve a read by address, since the read goes to the named server's client whatever was listed (`codex-rs/codex-mcp/src/binding_clients.rs` lines 89-102 at `rust-v0.170.0`); a listing call that fails is logged and dropped, so it reads as empty (lines 104-164 and 167-186); and a session started with a server configured gave this same report, part C empty (the paragraph on the session's servers, below). Part C can only refuse: a resource or a template listed means a server, as with the flags the command had before its tool settings were added, where the same two calls listed resources of a server named `codex_apps`. That the session has no server rests on Codex's own account of its servers, which that paragraph and the third and fourth observations before the run set out. |

No setting of the command removes the last five: at `rust-v0.170.0` Codex adds the three resource tools whenever the model takes its tools through the code tool alone (`codex-rs/core/src/tools/spec_plan.rs` lines 1323-1343), and adds `apply_patch` and the clock from the model's catalogue entry (lines 1477-1480 and 1433-1441). So the list holds for the model observed, as its catalogue entry stood that day, and another model may give another.

**What each setting removes.** The same day, at the same version and with the same model, from a session already sandboxed and so under no restriction, one session was run for each tool setting of the command, with that setting left out, all the others kept and the form's flag added, and asked for the listings of parts A and B:

| Setting left out | What the report then held beyond the closed list |
|---|---|
| `-c 'web_search="disabled"'` | `web__run`, nested |

## The prompt for a record

Fill in the subject line, keep the rest as written, and add nothing about what you think the owner wants.

```text
You are formalizing what an owner wants from one deliverable, as a Lean 4 intent record. Work independently: another formalization exists, and you must neither look for it nor guess at it.

Read only the three files in this directory: owner-words.md (the owner's words, exactly as given), types.lean (the definitions of the types the subject is stated over) and Record.lean (the lean-intent library's intent record). Read nothing else, on this machine or online.

The subject is <its name> : <its Lean type>, or, where this line gives no type, a subject whose type you choose and state.

Reply with three parts.

1. A Lean file that imports LeanIntent.Record and declares one LeanIntent.IntentRecord for the subject:
   - a property for each thing the owner's words require of the subject, named so that the owner can read it;
   - a domain hypothesis for each fact about the world that those properties rely on;
   - the predicates the properties are written in, in vocab;
   - the shape that fits what the subject is, as Shape in Record.lean describes.

2. In plain words: each property and hypothesis; each point where the owner's words left you a choice, with the choice you made and why; and each requirement you inferred rather than read in the words.

3. Every file you read, by its path.

Formalize what the words require, as their owner would mean them, at full strength: no property weaker or stronger than the words support, and none they do not support.
```

## The prompt for cases

Use this where the subject's type or domain is itself what is in question, because a record can take that type or predicate as a parameter and so compare nothing.
Fill in the three lines in angle brackets from the owner's words and the input's format, in their terms and never in your record's, keep the rest as written, and add nothing about what you think the owner wants.
No number of cases is required: rbeauchamp/regula PR 524's second reading gave 76, and what counts is that they reach each distinction.

```text
You are reading what an owner wants from one deliverable, and you will answer with concrete cases and verdicts. Work independently: another reading exists, and you must neither look for it nor guess at it.

Read only the files in this directory: owner-words.md (the owner's words, exactly as given), input-format.md (what an input is, which says nothing of what the owner wants) and types.lean, where it is present (the input's Lean type). Read nothing else, on this machine or online.

The deliverable is <its name>.
An input is <what one input is>.
The verdict on an input is one of <the outcomes the owner's words name>, or "the words do not settle this".

Reply with three parts.

1. A numbered list of inputs, each with its verdict and the words it rests on:
   - write each input out in full, in its own format, with no free variable or placeholder and no reference to a predicate, so that a reader with only that case can tell what the input is;
   - give one verdict for each, resting on nothing left undefined: where you would say "it depends", write each alternative as an input of its own;
   - choose the inputs yourself, as many as it takes to reach each distinction you can find in the words: ordinary inputs, unusual inputs the words still cover, ordinary-looking inputs the words exclude, and for each distinction a pair of inputs that differ in that one respect and get different verdicts.

2. In plain words: each point where the owner's words left you a choice, with the choice you made and why; and each requirement you inferred rather than read in the words.

3. Every file you read, by its path.

Give no Lean record and no general rule in place of the cases. Judge what the words require, as their owner would mean them, at full strength: no verdict that the words do not support.
```

## Where the formalization and the comparison live

The step exists so that a machine checks the comparison between the second model's formalization and your record, and a comparison that the project's proof check never builds is checked by nothing, however finished it reads: in an adopting project, the second model's record and the theorems comparing it with the intent record sat in an uncommitted scratch file that the proof check never ran, and the step read as done. By the proof check this section means the check the project runs on every change to establish its proofs, such as the build its validation gate or CI runs. So what the step proves is committed in the project, in modules that check builds, and is checked on every run of it:

- **The second model's formalization**, in a module of its own beside your record: its record, elaborated, or, where it gave cases, each case written in your input's type. The module imports only what defines the types the subject is stated over, as your record's module does (step 1), and lean-intent's `LeanIntent.Record` where it holds a record; it never imports your record, so nothing of yours can enter it. Correct only what Lean refuses to elaborate, without changing the meaning, and note each correction in a comment beside it, with what the reply had. Where it holds a record, declare that record as a record only, never as a deliverable: lean-intent's confirmation check asks about every deliverable it finds as one the owner must confirm (`docs/confirmation.md`, under what is trusted).
- **Every theorem comparing it with your record**, in a module of its own that imports both: each direction proved (`∀ w, mine.Meets w → theirs.Meets w`), each subject exhibited as meeting one record and failing the other, and, where it gave cases, your record's verdict on each case. Prove each with no `sorry`, audited as the project audits axioms, as step 2 asks of the obligations. A direction you can neither prove nor refute stays a difference stated in plain words and labelled unproved, never a theorem left with `sorry`.

Committing a module does not make the check build it. A check that builds declared targets builds only the modules those targets reach: in Lake, a library's built-in `leanArts` facet builds the modules its `globs` name, which default to one for each of its `roots`, and, recursively, every module of the workspace they import, its `roots` defaulting to the library's own name, and `lake build` with no argument builds the package's default targets and nothing else (Lake's README, `Lake/Config/LeanLibConfig.lean` and `resolveDefaultPackageTarget` in `Lake/CLI/Build.lean`, at Lean v4.35.0). So a module under the library's directory that no root imports and no glob names is not built. Reach every such module from a target whose selected facets compile it, following the project's own rules for where its files go: for example, import the comparison module, which imports the formalization's, from a root of a library whose built-in `leanArts` facet the check builds, or name each module in that library's `globs`.

Then confirm, from Lake's own account of what the check builds, that it builds them, once every such module is committed and `git status` shows none of them untracked or changed, since a glob also finds a file that is not committed. Find the targets and facets the check builds from the command the project runs on every change: a bare `lake build` builds the package's default targets (`defaultTargets` in `lakefile.toml`, `@[default_target]` in `lakefile.lean`), and `lake build <target>` the targets it names. For each Lean library among them, first establish from its configuration and the selected facets' build definitions that the check reaches its built-in `leanArts` facet. An unqualified library target selects `default`, which builds the library's `defaultFacets`, normally `#[LeanLib.leanArtsFacet]`; an empty array builds nothing (`resolveConfigDeclTarget` in `Lake/CLI/Build.lean`, `LeanLibConfig.defaultFacets` in `Lake/Config/LeanLibConfig.lean` and `LeanLib.recBuildDefaultFacets` in `Lake/Build/Library.lean`, at Lean v4.35.0). If that linkage is absent, have the routine proof check build `@/<library>:leanArts` before accepting the listing; merely naming a library or listing its modules establishes no compilation. For each library with that linkage established, `lake query @/<library>:modules` prints, one per line, the modules its built-in `leanArts` facet builds: those its `globs` name and, recursively, the modules of the same library that they import (`LeanLib.recCollectLocalModules`, and `LeanLib.recBuildLean`, which builds each module that facet lists, in `Lake/Build/Library.lean` at Lean v4.35.0); the query builds nothing. Each module holding the formalization or the comparison must appear in that output for a library whose built-in `leanArts` facet the check builds. A module that appears in none is not confirmed by it, even where a module the check builds imports it from another library: move it into a library whose built-in `leanArts` facet the check builds, or name it in that library's `globs`, and list again. A proof check that is not a Lake build of named targets gives the same account from its own definition, such as the list of files it compiles; say in the report how you read it. Lean stops reading a file at `#exit` and reports only a warning, so a module the check builds checks nothing written after one: keep no `#exit` in these modules. Building a module by name, such as `lake build <Module>`, shows only that the module builds, not that the check builds it. Keep the check's command, the facet linkage and the listings for the report.

The step is not done until every such module is committed and that confirmation has passed for each. A later change that makes any of them fail the check, such as a revision of your record, is a failing proof of the project like any other: prove it again, or, where the revision changed what holds, state the difference it now shows and settle it as step 3 says of each difference; never delete the module or take it out of what the check builds to make the check pass.

What may stay private to the project's agents, outside the repository, is the sessions themselves: each prompt you sent, the reply as the model gave it, each session's logs, such as Codex's event log, and the other evidence this reference has you record. The report draws on them; the check needs none of them, since the modules carry the formalization, each correction made to it and the comparison.
