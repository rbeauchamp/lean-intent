# Instructions for agents

These instructions are for any coding agent that works on lean-intent itself, under any harness. They are not for an agent working in a project that depends on lean-intent. The method the library serves is in [`skills/`](skills/), and the library is described from [`README.md`](README.md). This file says only how a change to this repository is validated and landed when the session that makes it, or lands it, runs in the cloud, and one rule for every commit on `main`, on co-author lines, under Landing a pull request.

Each part says whose it is: what the owner said, what the repository's own files say, or what the session that wrote this file did and how it reads the owner's words. The owner has confirmed none of the last kind as a rule.

## The merge gate

From the repository's files and its rules on GitHub. Every change lands through a pull request: `main` refuses a direct push, a force-push, and a commit without a verified signature, and requires the GitHub Actions `lean` check from [`.github/workflows/check.yml`](.github/workflows/check.yml) (alongside `Analyze (actions)` and `CodeQL`, with the branch up to date). Both [`.github/workflows/check.yml`](.github/workflows/check.yml) (CI on pull requests, pushes to `main`, `workflow_call` from [`.github/workflows/release.yml`](.github/workflows/release.yml) on `v*` tag pushes, and `workflow_dispatch`) and the local no-mistakes pipeline (configured in [`.no-mistakes.yaml`](.no-mistakes.yaml)) run `lean --run tools/check.lean` and verify that `lean --run tools/check.lean --tests` prints nothing.

## In a cloud session

A cloud session cannot run the pipeline, which lives on the owner's machine.

**The message of 2026-11-18.** On that day the session that wrote this file received, as a message from the owner, a text that says of itself that the owner's delegated agent wrote it and that it is sent with the owner's approval. Where this file calls something in it the owner's, it is on that footing. The message says that the owner is moving the work on this repository to the machine that runs the pipeline, asks for the handoff that is #75, and gives the rule on co-author lines that is under Landing a pull request. Its count of fifteen squash commits that carry such a line since 2026-11-07 is not this repository's, whose `main` had one, `3db11da`; it may count more than this repository. What follows is for a session that cannot run the pipeline.

**The owner's instruction**, given on 2026-11-17 in these words: "When running on the cloud, and since we don't have no mistakes installed, you should probably ensure that an independent adversarial review is performed on future PRs."

**How the session that wrote this file reads it.** The owner's words say that the review is independent, that it is adversarial and that it is of future pull requests. Everything below is that session's reading, from what went wrong the same day. #68 merged before its review had reported: the owner, told that the review was running, asked for the merge. The review then found three defects in what had merged, the commit `3db11da`. At that commit `deriving LeanIntent.HasCode` fails in a `module` file for a type that is not public there (`LeanIntent/Declared/Handler.lean`); `LeanIntent.Confirmation.Read` and `LeanIntent.CodeAudit` do not bring what an import of theirs brought before it, the commands that show a rendering and the deriving handler; and the README's section Module files says that without `allowImportAll` a project cannot import the library's private scope, which Lake at v4.35.0 does not enforce. All three were on `main` when this file was first written; #70 fixed them.

For each pull request a cloud session opens or changes:

- An agent that did not write the change reviews it before it merges and before the session calls it ready. A review that reports after the merge is not this review.
- The reviewer is given the change and the pull request's description, the description as claims to attack and not as guidance, and is asked to find what is wrong: defects, claims the change does not establish, text the change makes false, and ways the change could be followed or used to a bad outcome.
- Each finding is fixed, or answered with the reason it does not hold. The description records every finding with what was done about it, so that the owner, not the author alone, can judge the answers.
- The review is of what merges. A change to the tree after a review, a fix for a finding included, goes back to a reviewer before the merge.

**What that session did beside it.** Five pull requests merged from it on 2026-11-17, each on the owner's word and none with a run of the pipeline on the commit that landed:

- #66 merged at the head the pipeline had pushed to its branch, on the `main` it stood on.
- #65's branch the session rewrote as one commit of the same tree, to carry the description, and merged onto the `main` after #66 though it stood on the `main` before it, with no rebase and no new run. The tree that landed was one nothing had checked.
- #64 and #60 were rebased from the cloud, each after the merge before it, and #68 was made in the cloud. For these three the session put the steps below in the pipeline's place: all of them for #60 and #68, and for #64 the workflow on its own tree and the local check only on the tree with #60 added. No agent reviewed how #60's rebase settled its conflicts, as its description says, and #68's review reported after its merge.

The owner had given the session word to rewrite and rebase the four branches that were open, #66, #65, #64 and #60.

The next session should do the same for every pull request it opens or changes, before it calls it ready, unless the owner says otherwise:

1. **The repository's check, from a fresh checkout that holds no `.lake` directory.** `lean --run tools/check.lean` must exit with status 0, and `lean --run tools/check.lean --tests` must exit with status 0 and print nothing to standard output. Run both whatever the change touches, as the pipeline does.
2. **The `check` workflow on GitHub's machines.** [`.github/workflows/check.yml`](.github/workflows/check.yml) runs the same two commands automatically on pull requests, pushes to `main`, and `workflow_call` runs (such as from [`.github/workflows/release.yml`](.github/workflows/release.yml) on `v*` tag pushes), and can also be started manually with `workflow_dispatch`; GitHub records its result against the commit it ran on.
3. **The description says what was done.** Under Accepted risk, the pull request's description says that the pipeline did not run and what stood in its place: the commit checked, the two commands with their results and the workflow run, as #68's does, and, since the owner's instruction, who reviewed and what was left unchecked. A result goes into the description once it has been observed, not before. Where the commit checked is the one that carries the description, the result cannot be in it: record it where the owner will read it, and say in the description where. For #70 that was #75.
4. **The owner decides the merge.** Merge a pull request only when the owner asks for that pull request to be merged. If the owner asks while something here is not done or has failed, because the review has not reported, a step is still running or failed on the commit that would land, or `main` has moved since, say in the reply which, and merge only if the owner, told so, still asks. Write it into the description, under Accepted risk, before the merge: the description becomes the commit, and nothing written afterwards reaches it. What a review finds after such a merge goes to the owner when it reports.

What steps 1 and 2 establish holds for the commit they ran on and for the commit of `main` it stands on:

- If the head's tree changes, do them again, bring the description up to date, and send the change to a reviewer as the review above says.
- If `main` has moved, rebase onto it; #65 is the case this is for. A rebase changes the tree, so everything the item above asks follows, and the reviewer is told what the rebase had to settle. A rebase also rewrites the branch, which needs the owner's word: on a branch the session did not push always, and since the message of 2026-11-18 on its own branch too.
- A rewrite of the branch's commits that keeps both the tree and the commit of `main` they stand on needed none of them again in the session's practice for #60 and #68: the description named the commit that was checked, and the merged one had its tree. The message of 2026-11-18 asks, for the rewrite that removes co-author lines, to "re-run the gate on the new head". The session, which cannot run the pipeline, read that as steps 1 and 2 again on the new head, and did them for #70; whether it also means a new review of an unchanged tree is that session's reading, which was no. For a rewrite that keeps tree and base and removes no such line, the session would again repeat none of them.

## Landing a pull request

From the repository's files: a pull request's description, written from [`.github/pull_request_template.md`](.github/pull_request_template.md), becomes its squash commit (`.no-mistakes.yaml`, the comment on `pr.template`), so the commit on `main` is the pull request's title with its number, `Title (#N)`, a blank line and the description.

**The owner's rule**, from the message of 2026-11-18 described above: "Commits on main must not carry a co-author line that names a model or an assistant." The message says that the commits that already carry one stay. For anything a session merges from then on, it asks that each commit of the pull request's branch whose message carries such a line be replaced, before the merge, by one whose message lacks it and that changes no file; that the new head's tree be confirmed the same as the old one's; that the gate be run again on the new head; that the squash message have no such line; and that the landed commit be read to confirm it has none. It allows the force-push of the session's own pull request branch "for this purpose only".

Observed on 2026-11-17 and 2026-11-18, and what the session did about it:

- **GitHub's default message is not the description.** A squash merge that named no message took, for a pull request with several commits, the list of their messages (#66, #64), and for one with a single commit, that commit's message (#65, #60, #68). The repository's setting for that default is the owner's to change. A reviewer of this file read it, after #68 had merged, as the commits' messages, so the change the owner reported before #64 merged was not in effect; the session did not read the setting itself. Set to the pull request's title and description, it may make the default message the right one, which no merge has yet shown. `main` refuses the rewrite that would correct a message afterwards, so the message has to be right when the merge is made.
- **Give the description as the message, exactly.** The route the session used is the single commit of the next item. A tool that takes the message from a file would be simpler and was not tried: no merge that day named a title or a body, so what GitHub does with either, the number included, is not observed. Do not retype a description into a merge: a slip lands on `main`.
- **Make the branch one commit that carries it.** This rewrites the branch. The session did it on its own branch for #68, having told the owner that it would, and on the owner's branches for #65 and #60 on the owner's word. The message of 2026-11-18 allows a force-push of a session's own pull request branch for removing co-author lines only, so since then any other rewrite of it, this one included where it removes no such line, needs the owner's word, as the rebase of this file's pull request had. One commit, with the same tree, on the same commit of `main` the branch already stands on, whose message is the pull request's title without its number, a blank line and its description, and after them whatever lines the session's commits must end with, none of them a co-author line. Its author is the one `main`'s commits carry and its committer the session: the next item says why, and it is the session's device, which the owner's message neither asks for nor mentions. Write the message verbatim (`git commit-tree -F`, or `git commit --cleanup=verbatim -F`): Git's cleanup otherwise changes it: a message from a file loses trailing spaces and has each run of blank lines made one, and a message from an editor also loses every line that begins with `#`, which the template's headings do. Compare the commit's message, up to those last lines, with the title and description byte for byte before the merge. GitHub then adds ` (#N)` to the first line; the rest landed as written, apart from what the next item says of #68.
- **GitHub writes a co-author line of its own.** #68's single commit had the session as its author and a co-author line among the last lines of its message. On `main` (`3db11da`) that line is gone, and one that GitHub wrote, naming the commit's author, stands at the end. #65's and #60's single commits had the author that `main`'s commits carry, with the session only as committer, and no such line in their messages; they landed with none. Whether GitHub goes by the commit's author, by the message or by both was not separated. So, to meet the owner's rule, the session built #70's landing commit as #65's and #60's were, with the author of `main`'s commits and no co-author line in its message, and it landed with none (`0747d62`).
- **Read the commit on `main` after the merge**: its message, and that its tree is the one that was checked. If either is not what it should be, tell the owner in the same turn, with what landed and what should have; `main` cannot be rewritten, so what follows, a correcting pull request or leaving it, is the owner's to decide.
- **Close the issue by hand.** An issue that a merged pull request names with `Closes` stayed open (#51, #56, #67). Close it as completed after the merge.

## Building in a cloud environment

Observed on 2026-11-17 (updated 2026-11-21). [`lean-toolchain`](lean-toolchain) pins the Lean release (`v4.36.0`). [`.github/workflows/check.yml`](.github/workflows/check.yml) installs the SHA-256-verified Linux release archive matching [`lean-toolchain`](lean-toolchain) directly from GitHub Releases; a cloud environment using `elan` instead needs network access to `release.lean-lang.org` and `releases.lean-lang.org`. The check and the listing together took about eighteen minutes from a fresh checkout on a four-core cloud machine, and eleven to thirteen on GitHub's.
