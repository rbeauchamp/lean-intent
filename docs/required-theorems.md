# The theorems a deliverable relies on, where the proof check builds them

**The theorems a deliverable relies on** (`LeanIntent.Required`, `LeanIntent.O2RunProof`, `LeanIntent.ComparisonDirection`, `LeanIntent.BlindComparison`, `LeanIntent.Proof`, `LeanIntent.Required.Read`): a value a project declares for one deliverable whose type fixes the presence of its adequacy obligations (`O2`, `O2Run`, `O3`, `O4`, `O5`) and its blind-formalization comparison alongside any additional shape-dependent or consequence proofs; and the decision a project's gate runs, with the confirmation and implementation checks, that reads every such value in every module the gate's environment holds and, once there is one, refuses the project unless each deliverable has exactly one such value and each such value, each required theorem it carries, its blind record, each deliverable and each value recording an implementation is declared in a module its build lists, read from Lean's environment and from Lake's own list of the modules the build compiles, with theorems stating what it decides.

Modules: `LeanIntent/Required.lean` (the typed structures, the decision and its theorems, which import no more of Lean than the rest of the core), `LeanIntent/Required/ModuleName.lean` (the closed form of module names the reader of Lake's list accepts, with its theorems) and `LeanIntent/Required/Read.lean` (reading the build and Lake's list of its modules, which imports all of Lean).

**Complete in this version:** the typed `Required` structure (`O2`, `O2RunProof`, `O3`, `O4`, `Freedom` + `O5`, `BlindComparison`, and `additional : List Proof`), the decision with its theorems, and the reader a gate calls, with the reader of Lake's list. Presence of `O2`, `O2Run`, `O3`, `O4`, `O5`, and a non-empty blind comparison is enforced by Lean's type checker at declaration time (closing rbeauchamp/lean-intent#77); extra shape-dependent theorems (`Verdicts`, `MachineVerdicts`, `OPair`, `WitnessVerdicts`) are listed in `additional`, and a value in a source file that no module the gate imports reaches is not read. See [What is trusted](#what-is-trusted).

The intent-first procedure has a project prove theorems it then relies on: a record's adequacy obligations, the comparison between an independent blind formalization and the record, the answers a deliverable keeps and the proof that its implementation meets the record. A theorem is checked only where the project's proof check, the check it runs on every change to establish its proofs, builds the module that declares it. In an adopting project the comparison theorems sat in an uncommitted scratch file that its proof check never ran, so the step read as done while nothing was checked. A written rule to commit them where the check builds them depends on whoever follows it; this check makes both omitting core obligations/comparison proofs and placing required theorems outside the build into refusals.

## What a project declares

For each deliverable, exactly one value of `LeanIntent.Required d`, in a module the proof check builds that imports the deliverable, its obligations, its blind formalization and comparison theorems, and any additional required theorems:

```lean
import LeanIntent.Required

def sortingRequired : LeanIntent.Required sortingDeliverable where
  o2 := sorting_o2
  o2Run := .proved sorting_o2Run
  o3 := sorting_o3
  o4 := sorting_o4
  freedom := .eq
  o5 := sorting_o5_eq
  comparison := .records sortedOnly (.implies sorting_narrower) (.separates nilSort nilSort_separates)
  additional := [⟨sorting_verdicts⟩]
```

Each obligation field has the exact proposition Lean checks at declaration time:

- `o2 : O2 d.record`, `o3 : O3 d.record`, `o4 : O4 d.record`, and `freedom : Freedom W` with `o5 : O5 d.record freedom` are required of every deliverable.
- `o2Run : O2RunProof d.record` is either `.proved (proof : O2Run d.record)` or `.deferred (reason : String) (stated : ...)` (whose reason cannot be blank, checked by `decide +kernel`; `blankDeferred_unrepresentable` in the worked example). Deferral is permitted only while a deliverable awaits its implementation (`Report.deferredO2Run` surfaces every deferred entry); once an `Implementation d` exists, `Required.findings` refuses `.deferred` (`o2RunDeferred`) because `Implementation.o2Run` directly witnesses `O2Run d.record`.
- `comparison : BlindComparison d.record` is either:
  - `.records blind forward backward` for a same-type blind record `blind : IntentRecord W`, where each direction (`ComparisonDirection`) is `.implies (∀ w, r₁.Meets w → r₂.Meets w)`, `.separates witness (r₁.Meets witness ∧ ¬ r₂.Meets witness)`, or `.unproved reason` (non-blank, surfaced in `Report.unprovedComparisons`), and `hasProof : forward.isProved || backward.isProved = true := by rfl` makes leaving both directions unproved unrepresentable (`bothUnproved_unrepresentable`); or
  - `.cases theorems nonempty reason stated` for concrete-case verdicts when the subject's type or domain was in question, requiring `theorems ≠ []` (`emptyCases_unrepresentable`) and a non-blank `reason` (surfaced in `Report.casesComparisons`).
- `additional : List Proof := []` holds any additional shape-dependent or consequence theorems (`Verdicts`, `MachineVerdicts`, `OPair`, `WitnessVerdicts`, `Healthy`, refusal classification, etc.), each written `⟨name⟩` (or `⟨@name⟩` where the theorem's first arguments are implicit).

Lean checks at declaration time that every field is a well-typed proof of the exact obligation or comparison for `d.record` and that every named constant is imported. The answers a deliverable keeps, and the proof that its implementation meets the record, need no entry: the deliverable and the value of `LeanIntent.Implementation` hold them, and the decision reads where each of those is declared.

### Migrating from untyped `Required`

Projects migrating from the pre-`v0.3.0` untyped `Required d` (`theorems : List Proof`) move to typed `Required d` by:

1. Combining multiple `Required d` values for the same deliverable into a single `Required d` value in a module importing the deliverable, its obligations, its blind formalization and comparison theorems, and any extra theorems.
2. Assigning each obligation theorem (`o2`, `o2Run := .proved ...` or `.deferred "..."` if awaiting implementation, `o3`, `o4`, `freedom`, `o5`) to its typed field.
3. Moving the blind-formalization comparison into `comparison := .records blindRecord forward backward` (using `.implies`, `.separates`, or `.unproved`) or `comparison := .cases [...] "..."`.
4. Placing any remaining theorems (such as `Verdicts`, `MachineVerdicts`, `OPair`, `WitnessVerdicts`, or consequence theorems) in `additional := [...]`.

## What it decides

The decision (`Required.findings`) reads the module names the build lists, the deliverables (`Required.DeliverableEntry`: module, name, and optional record name), the values recording implementations (`Required.ImplEntry`: module, name, and optional deliverable name), and, for each value of `Required` (`Required.Entry`), the module that declares it, the deliverable its type names, its `o2`, `o2Run`, `o3`, `o4`, `o5` proofs, its `comparison` entry, and its `additional` proofs, each cited proof read as a theorem by its module and its name, a constant that is not a theorem, or a term (`Required.Cited`). The reader gives it these from every module the gate's environment holds, not from a list of modules a caller chooses. Its verdict depends only on those declarations and on the module names given as built, never on which package a module belongs to, which the reader does not consult (#78). Where no value of `Required` is read, the project is refused nothing, whatever deliverables and implementations are read and whatever the build lists (`findings_nothing`): a project's first such value is how it adopts the check, so a project that adopted lean-intent before it, and whose gate reads none, passes it unchanged until then. Once one is read, the project's own or another package's, the decision lists what is wrong, and `Finding.message` says, for each, what the project declares, moves or gives to clear it:

- **A deliverable declared in a module the build does not list** (`deliverableUnbuilt`), naming it and the module: the proof that its record keeps its answers is checked where that module is built.
- **A value recording an implementation declared in a module the build does not list** (`implementationUnbuilt`), naming it and the module: likewise, for the proof that the implementation meets the record.
- **A deliverable no value of `Required` names, where one is read** (`undeclared`), naming it: the refusal says to declare one value of `LeanIntent.Required` for it carrying its typed obligations and comparison.
- **A deliverable several values of `Required` name** (`several`), naming it and them: each deliverable has exactly one `Required` value carrying its obligations and comparison.
- **A value of `Required` declared in a module the build does not list** (`requiredUnbuilt`), naming it and the module: the proof check never checked its proofs, so it is refused whatever it carries, and so is each theorem it names that lies in such a module.
- **A value whose type names no deliverable of the project** (`untied`), naming it.
- **A deferred `O2Run` on an already implemented deliverable** (`o2RunDeferred`), naming the `Required` value and the deliverable: once an `Implementation` exists, `O2Run` must be `.proved`.
- **A blind formalization record that is not a declared constant** (`blindNotConstant`), naming the value.
- **A blind formalization record declared in a module the build does not list** (`blindUnbuilt`), naming the value, the blind record, and its module.
- **A comparison against the deliverable's own record** (`selfComparison`), naming the value and the record.
- **A comparison with no proof** (`noComparisonProof`), naming the value (already unrepresentable by `BlindComparison`'s type, and also refused at the pure decision level).
- **A proof that is a term rather than a constant** (`notConstant`), naming the value: a term names no declaration whose module can be read.
- **A proof that is a constant but not a theorem** (`notTheorem`), naming the value, the constant and the module recorded as declaring it, such as a definition or an axiom; what counts is that module's own declaration, so an axiom there is refused whatever another module proves under its name.
- **A theorem declared in a module the build does not list** (`unbuilt`), naming the value, the theorem and the module: the proof check does not check it.

| Theorem | What it establishes |
|---|---|
| `findings_eq_nil_iff` | for every list of module names, deliverables, implementation entries and `Required` entries, the decision finds nothing exactly when there is no entry, or each deliverable, each implementation entry and each `Required` entry is declared in a module the list holds, each deliverable has count `1` among `rs`, each entry names a deliverable, no implemented deliverable leaves `O2Run` deferred, each comparison is valid (`ComparisonEntry.Valid`: constant built blind record distinct from the deliverable's own record with at least one proved direction, or non-empty cases), and every cited proof in `Entry.allCited` is a theorem declared in a module the list holds (`Located`, stated over the lists and sharing no definition with the decision) |
| `findings_nothing` | where there is no entry, so no value of `Required` is read, the decision finds nothing, whatever deliverables and implementation entries there are and whatever the build lists |
| `undeclared_mem`, `several_mem`, `requiredUnbuilt_mem`, `unbuilt_mem`, `o2RunDeferred_mem`, `selfComparison_mem`, `blindUnbuilt_mem` | each refusal condition directly produces its named finding in `findings` |
| `findings_sound` | each finding holds of the lists, and names the deliverable, value, blind record, theorem or module it is about |
| `mem_theorems` | the report lists a theorem with a value exactly when that value's entry cites it as a theorem in `allCited` |
| `mem_deferredO2Run`, `mem_unprovedComparisons`, `mem_casesComparisons` | the report surfaces every deferred `O2Run` reason, every unproved comparison direction, and every concrete-cases comparison reason |
| `moduleName?_inj` | for every two strings, if the decoding of module names gives both the same name, they are the same string: distinct accepted strings give distinct modules |
| `moduleName?_chars`, `moduleName?_isPart` | a string the decoding accepts holds only dots, ASCII letters and digits, `_` and `'`, and each stretch between its dots is an ASCII letter followed by such characters other than the dot; so every other string, one holding `«` or `»` among them, is given no name |
| `moduleName?_parts` | the name the decoding gives has exactly the string's stretches between dots as its components, each a string component |

The decisions, each made on the owner's behalf, which a later change can reverse:

- **The check starts with the first value of `Required` it reads, and from then on every deliverable names its theorems.** A project in whose gate environment no such value is read keeps the verdict it had: one that adopted lean-intent before this check, with deliverables and implementations but no value of `Required`, is refused nothing by it (`findings_nothing`), even where its deliverable lies outside the build's list (`undeclaredProject_accepted` in the worked example). Once one is read, the procedure requires each deliverable's obligations and comparison before it is confirmed, and a theorem nothing names is one no check finds, so a deliverable no value names is refused, and the refusal says what to declare. The procedure's skill has a project declare a value for each deliverable, so a project that follows it adopts the check with its first deliverable.
- **Every value of `Required` the gate's environment holds is read, and one outside the build's list is refused.** The reader takes no list of modules to read: it reads every module the environment holds, so a value cannot be hidden by leaving its module out of a list. A value in a module the build does not list, such as a scratch file that a module the gate imports happens to import, is refused by name with its module, and so is each theorem it lists there (`scratchValue_refused` in the worked example); it does not count as naming its deliverable for the proof check, since the proof check never built it. Deliverables and values recording implementations are read the same way, so one declared in a module the build does not list is refused too.
- **A declaration another package makes is read like the project's own.** The check cannot tell another package's module from the project's own unbuilt one: both are modules outside the names given as built, and an exemption the caller lists would let a scratch module named in it pass unseen. So where a module the gate imports reaches a module of a dependency that declares a deliverable, a value recording an implementation or a value of `Required`, each is refused by name with its module, whoever declared it, until the project gives that module among the built ones, where its proof check builds it: the list Lake prints for that library, when the gate imports all of it, or the modules it names itself, which is then its own claim that the proof check builds them. And since a value of `Required` is then read, the project is held to name each of its own deliverables too, even if it had declared no value itself. This holds for a project with no declaration of its own: what its imports hold decides, not what it wrote. Telling the two kinds of module apart by each module's package, as Lake records it, is rbeauchamp/lean-intent#78.
- **Where a theorem lies is the module Lean's environment records as declaring it, and only where that module itself declares it as a theorem**, never its name. Lean refuses to import two modules that declare one name (`throwAlreadyImported` in Lean v4.36.0's `src/Lean/Environment.lean`, lines 2433 to 2436, called at line 2708), except where the two declarations have the same name, type and universe parameters and are two theorems of the same mutual group, a theorem outside any mutual group and a safe axiom, or two axioms, both safe or both unsafe, of a type its test takes for a proposition (`subsumesInfo`, lines 2633 to 2648, used by `finalizeImport` at lines 2697 to 2709). It then holds one of the two, the theorem where the other is an axiom, and records the name under the first of those modules in import order (`const2ModIdx.insertIfNew`, line 2709); it records the auxiliary names of a module's compiled code under that module in the same way (lines 2710 to 2712). So the declaration the environment holds under a name need not be the one the recorded module made. The reader therefore takes a listed constant's declaration from the recorded module's own data, as Lean loaded that module (`Read.ownDeclaration`), and reads it as a theorem only where that module declares it as a theorem, with the type and universe parameters of the constant the value names. What follows was each observed at v4.35.0, on the project the section on the worked example describes. A name a listed module declares only as an axiom is refused as not a theorem, naming that module, though a module imported after it proves a theorem of that name. A theorem that an unlisted module and a listed module imported after it both declare is recorded under the unlisted one and refused until the duplicate is removed (`sameName_refused` in the worked example states what the decision does with an entry so recorded). A theorem a listed module declares, with an axiom or a second theorem of its name in a module imported after it, is read as the listed module's and accepted, since that module holds the proof. A name recorded under a module that holds it only as an auxiliary name of its compiled code, such as `f._boxed` for a definition `f`, is an error naming the name and the module. Deliverables, values recording implementations and values of `Required` are found in each module's own data, so the module reported for one is a module that declares it.
- **An entry is a constant Lean records as a theorem, and nothing else.** A term could hold a proof under any wrapper, so the decision accepts this closed form and refuses every other by name rather than reading inside it.
- **A module counts as built only where the build's own list names it.** Lake also builds a module that a listed one imports from another library, but its list does not name it, and an import Lean resolves to a compiled file Lake does not manage is not built at all (see [the README's section on upgrading](../README.md#upgrading-from-import-leanintent)); so a theorem in a module of another library is refused unless the gate also gives that library's list, which it does only when the proof check builds that library's modules.

## What a gate reads

`LeanIntent.Required.Read.check built` reads the deliverables, the values recording implementations and the values of `Required` from every module the environment it runs in holds, the file being elaborated included, and decides them against `built`, the module names the build lists; the table below states how each input is read, and every program in `LeanIntent/Required/Read.lean` (`ownDeclaration`, `citedProof`, `citedOf`, `constantOf?`, `readO2Run`, `readDirection`, `readComparison`, `deliverableEntryOf`, `implEntryOf`, `entryOf`, `declaredAnywhere`, `check`) begins with `LeanIntent.asking` and throws if the environment's extensions are not loaded ([ADR-0009](adr/0009-environment-extension-loading-and-reader-guards.md)). It takes no list of modules to read. It finds a constant as the confirmation and implementation checks find theirs, by its type reduced through Lean's kernel, but over every definition, opaque constant and axiom that each module itself declares, read from that module's own data as Lean loaded it, so that the module reported for a constant is one that declares it; on a gate that imports all of Lean and Lake beside a small project this took about 0.2 seconds at Lean v4.35.0, and its cost on a project that imports a larger library, such as Mathlib, has not been measured.

| Input | How it is read |
|---|---|
| the modules whose declarations are read | every module the environment holds, the one being elaborated included: `check` takes no list of modules to read, so none can be left out of what it reads; each module's declarations are read from that module's own data, as Lean loaded it (`EnvironmentHeader.moduleData`), and the file's own from the constants it added, never from the environment's one map of constants |
| the project's deliverables | every definition, opaque constant or axiom of those modules whose type reduces through Lean's kernel (`Render.readWhnf`), unfolding every definition, to `LeanIntent.Deliverable _`, together with its record constant (`Deliverable.mk`'s second argument when reduced, else `none`) |
| the values that record implementations | every such constant whose type so reduces to `LeanIntent.Implementation _`, together with the deliverable its type names (`constOf? d`) |
| the values that name required theorems | every such constant whose type so reduces to `LeanIntent.Required _` |
| the deliverable such a value names | the second argument of that type, `d` of `@Required W d`, where it is a constant once its metadata is removed (`Expr.consumeMData`), and otherwise none |
| what such a value carries | its value, reduced by `Render.readWhnf` through the kernel to `Required.mk`'s application (arity 10): `o2`, `o3`, `o4`, and `o5` read directly by `citedProof`; `o2Run` reduced by `readO2Run` (`O2RunProof.proved` via `citedProof` or `O2RunProof.deferred` via `strLit`); `comparison` reduced by `readComparison` (`BlindComparison.records` reading `blind` via `constantOf?` and both directions via `readDirection`, or `BlindComparison.cases` reading its `List Proof` via `listElems`/`citedOf` and reason via `strLit`); and `additional` reduced via `listElems`/`citedOf`. Where Lean's elaborator abstracted a proof term into an auxiliary theorem of the value's own module, the value holds that theorem's constant, which is read as that theorem |
| whether a listed constant is a theorem | the declaration of its name in the data of the module the environment records for it (`ownDeclaration`), a theorem exactly when that declaration is `ConstantInfo.thmInfo` with the type and universe parameters of the declaration the environment holds, which the value's entry was checked against; the environment's map of constants does not decide it, since Lean puts a later module's theorem there over an earlier module's axiom of the same type (`subsumesInfo` and `finalizeImport` in Lean v4.36.0's `src/Lean/Environment.lean`, lines 2633 to 2648 and 2697 to 2709) |
| the module that declares a constant | for a deliverable, a value recording an implementation or a value of `Required`, the module in whose own data it was found, with an error where the environment holds another declaration under its name (`sameDeclaration`); for a listed constant, the module the environment records for the name (`Environment.getModuleIdxFor?`), the first in import order to declare it, provided that module's own data declares the name, and otherwise an error naming both, as where the module holds the name only as an auxiliary name of its compiled code (`const2ModIdx.insertIfNew`, lines 2709 and 2712 of the same file); a constant with no module index is declared in the file being elaborated |
| the module names the build lists | given by the caller; `queryModules` reads them from what `lake query --json` prints for `@/<library>:modules`, each line a JSON array of names, read by Lean's JSON parser, and each name decoded by `Required.moduleName?`, which gives a name only for a string of its closed form and for which distinct strings give distinct names (`Required.moduleName?_inj`); every other string is an error naming it |

Two conditions make that reading complete, and the check is an error where either fails. It runs only in a file that is not a `module` file (`Environment.header.isModule`, which `finalizeImport` sets in `src/Lean/Environment.lean` at line 2735): there Lean imports every module the file's imports reach, with everything each declares, whatever those modules' own imports say of visibility (`importModulesCore` in Lean v4.36.0's `src/Lean/Environment.lean`, lines 2485 to 2487 and 2547, with the level `Elab.processHeaderCore` gives it in `src/Lean/Elab/Import.lean`, lines 150 to 159), while a `module` file imports each module at the level the imports that reach it give it, and everything the module declares only along a chain of `import all` from the file, a private value being absent and a theorem shown as an axiom below that level, and a module reached only through a private import of a module not imported that way not loaded at all (`importModulesCore`, lines 2489 to 2539 and 2613 to 2616); it was observed to read a `private` value of a `module` file from a gate that is not one. And every module `built` names must be imported, so that no deliverable of a built module goes unasked about; the error names the first that is not. Each entry of a value of `Required` is reduced by `Render.readWhnf`, through Lean's kernel, to `Proof.mk`'s application, and its proof read as the value holds it: a constant once its metadata is removed, and otherwise a term. Where Lean's elaborator abstracted a proof term into an auxiliary theorem of the value's own module, such as `myRequired._proof_1`, the value holds that theorem's constant and the reader reads it as that theorem, declared in that module; this was observed at Lean v4.35.0 for an entry written as a theorem applied to an argument, while an entry written as a constructor's application was read as a term. A value that is an opaque constant or an axiom does not reduce to its constructor's application and is an error naming it, and an unsafe or partial one is an error too, since the reader's discovery (`Read.declaredAnywhere`) requires safety `safe` of every definition it finds, by the predicate the other readers share (`Confirmation.Read.proofSafe_iff`). It returns a `Report`:

| Field | What it holds |
|---|---|
| `findings` | what is wrong; empty exactly when every required theorem and blind record lies in a module the build lists, each deliverable has exactly one `Required` value, no implemented deliverable defers `O2Run`, and no comparison targets the deliverable's own record or omits proofs |
| `theorems` | each theorem a value cites across `o2`, `o2Run`, `o3`, `o4`, `o5`, `comparison`, and `additional`, with that value and the theorem's module and name: the account of which module holds each theorem, for the project's report |
| `deferredO2Run` | each `Required` value whose `o2Run` is `.deferred`, with its stated reason |
| `unprovedComparisons` | each `.records` comparison direction left `.unproved`, with the value, direction (`"forward"` or `"backward"`), and reason |
| `casesComparisons` | each `.cases` comparison, with the value and its stated reason |

### The module names the build lists

The check is only as good as `built`, which must be the modules the project's proof check compiles. A gate reads them from Lake, which owns them, through `Read.queryModules`, which reads what `lake query --json` prints:

- **Which libraries.** The proof check builds the targets its command names: `lake build` with no argument builds the package's default targets (`defaultTargets` in `lakefile.toml`, `@[default_target]` in `lakefile.lean`; `resolveDefaultPackageTarget` in `Lake/CLI/Build.lean`, lines 115 to 118, at Lean v4.36.0), and `lake build <target>` the targets it names. A library target given with no facet selects its `default` facet (`resolveConfigDeclTarget`, lines 89 to 103), which builds the facets in its `defaultFacets`, `#[LeanLib.leanArtsFacet]` unless its configuration says otherwise (`Lake/Config/LeanLibConfig.lean`, line 100; `LeanLib.recBuildDefaultFacets` in `Lake/Build/Library.lean`, lines 188 to 191). Of a library's built-in facets (`LeanLib.initFacetConfigs`, lines 201 to 211), six compile its modules, and each takes them from the one `modules` facet: `elabArts` (`LeanLib.recBuildElabArts`, lines 67 to 70), `irArts` (`LeanLib.recBuildIRArts`, lines 76 to 79), `leanArts`, which is `irArts` (lines 86 to 87), and `static`, `static.export` and `shared`, which build for each module the native facets the library's `nativeFacets` names, its object file unless the configuration says otherwise (`LeanLib.recBuildStatic`, lines 98 to 100; `LeanLib.recBuildShared`, lines 141 to 143, which also builds the `shared` facet of each library those modules import, lines 147 to 157; `Lake/Config/LeanLibConfig.lean`, lines 112 to 113). The other three compile none: `default` builds only what `defaultFacets` names, `modules` is not buildable, and `extraDep` builds the library's and its package's extra dependency targets (lines 174 to 181). For each library of which the proof check builds any of the six, through `defaultFacets` or because its command names the facet, the gate asks Lake for that library's modules, whichever of the six it is; only a library of which the check builds none of them, such as one whose `defaultFacets` is empty, is left out, and its modules are not built by it. A facet the project defines itself builds what its own definition says.
- **Which modules.** `lake query --json @/<library>:modules` prints the modules each of those six facets builds: those its `globs` name, read over the working tree (`LeanLib.getModuleArray`, `Lake/Config/Module.lean`, lines 63 to 67), and, recursively, the modules of the same library they import (`LeanLib.recCollectLocalModules`, `Lake/Build/Library.lean`, lines 36 to 61, the `modules` facet at lines 64 to 65), the list each of the six reads, at the lines given above. The query builds nothing, since the `modules` facet is not buildable. It prints one line for each target (`query` in `Lake/CLI/Main.lean`, lines 1007 to 1017), each a JSON array of the module names (`formatQuery`, `Lake/Config/OutFormat.lean`, lines 78 to 81; `ToJson Module`, `Lake/Config/Module.lean`, line 23), each name written by Lean's `ToJson Name` (`src/Lean/Data/Json/FromToJson/Basic.lean`, lines 174 to 187).
- **Reading them.** `Read.queryModules` reads each line with Lean's JSON parser and decodes each name only from a closed form (`Required.moduleName?`): dots between stretches that are each an ASCII letter followed by ASCII letters, digits, `_` or `'`, read as the name whose components are those stretches. Distinct accepted strings give distinct names (`moduleName?_inj`), and every other string is an error naming it, never a name. Lean's printing of a name is not one-to-one, which is why the form is closed: `Name.toString` writes a component that holds a dot between `«` and `»`, but writes one that already holds `»` as it stands (`escapePart`, `src/Init/Data/ToString/Name.lean`, lines 55 to 64, at Lean v4.36.0), so the name with the one component `a.b` and the name with the one component `«a.b»` are both printed `«a.b»`, as was observed, and a decoding that gave either back could count a module the build does not list as built. For a string of the closed form, the name the decoding gives is the name Lean printed: [Why the name `queryModules` gives is the name Lake printed](#why-the-name-querymodules-gives-is-the-name-lake-printed) sets the argument out from the lines of Lean's source it reads, and it is argued, not proved. A project with a module whose name is not of the form, such as one with a component Lean writes between `«` and `»`, a non-ASCII letter, or a component starting with `_`, gives `built` from Lake's own module values instead, for example by Lake's API in its gate. Output that lists no module at all is an error, since it would leave every theorem unbuilt.

Run the query in the proof check's own checkout, after its build. A glob finds every file in the working tree, committed or not, so in a working tree holding a file that is not committed Lake's list names its module; in a checkout of a commit, which a validation gate builds, the file does not exist, so a theorem in it is not found and a value listing it does not build.

A gate runs the three checks on the same build, from a file that is not a `module` file, with the build's module names as the modules the other two read:

```sh
lake build
```

```lean
import LeanIntent.Confirmation.Read
import LeanIntent.Implementation.Read
import LeanIntent.Required.Read
import MyProject.Deliverables
import MyProject.Implementations
import MyProject.Comparison

run_meta do
  let built ← match LeanIntent.Required.Read.queryModules
      (← IO.FS.readFile ".lake/built-modules.json") with
    | .ok built => pure built
    | .error e => throwError "the build's module list cannot be read: {e}"
  let confirmed ← LeanIntent.Confirmation.Read.check built
  let implemented ← LeanIntent.Implementation.Read.check built
  let required ← LeanIntent.Required.Read.check built
  unless confirmed.findings.isEmpty do
    throwError "the deliverables are not confirmed: {confirmed.findings.length} findings"
  unless implemented.findings.isEmpty do
    throwError "the deliverables are not implemented: {repr implemented.findings}"
  unless required.findings.isEmpty do
    throwError "required theorems lie outside the build:\n{"\n".intercalate (required.findings.map (·.message))}"
```

Each check refuses a module given that the gate does not import, so the gate imports every module the build lists, here through the modules that import the rest. The required-theorems check also reads whatever else those imports reach, so the gate imports nothing the project's own modules do not need: a scratch module imported only by the gate would be read, and a value in it refused.

### Why the name `queryModules` gives is the name Lake printed

Argued from Lean's source at v4.36.0, not proved here. Lake prints a module's name as Lean's `ToJson Name` writes it, the string `Name.toString` gives with its defaults (`src/Lean/Data/Json/FromToJson/Basic.lean`, lines 186 to 187; `src/Init/Data/ToString/Name.lean`, lines 123 to 127). Take a name `n` that Lean prints as a string `s` that `Required.moduleName?` accepts, so that `s` holds only dots, ASCII letters and digits, `_` and `'` (`Required.moduleName?_chars`) and each stretch between its dots starts with a letter (`Required.moduleName?_isPart`). Then:

- `n` is not the anonymous name, printed `[anonymous]`, and has no numeric component, which is printed as its digits and would start a stretch with a digit (`toStringWithSep`, lines 73 to 83).
- Escaping is on for `n`. It is off only for a name whose last string component holds `✝` or is `_inaccessible` (`Name.isInaccessibleUserName`, `src/Init/Meta/Defs.lean`, lines 152 to 155), a name with macro scopes, whose last string component is `_hyg` (`Name.hasMacroScopes`, `src/Init/Prelude.lean`), the name `_`, and a name whose first component starts with `#` or `?` (`toStringWithToken`, lines 100 to 112). Each component is then printed as it stands, so `s` would hold `✝`, or a stretch `_inaccessible`, `_hyg` or `_`, or would start with `#` or `?`.
- With escaping on, a string component is printed as it stands only where it is an identifier, a first character that `isIdFirst` accepts followed by characters that `isIdRest` accepts, none of which is a dot (`src/Init/Meta/Defs.lean`, lines 120 to 121 and 133 to 134), or where it holds `»`; every other component is printed between `«` and `»` (`escapePart`, lines 55 to 64). `s` holds neither `«` nor `»`, so every component of `n` is an identifier with no dot, printed as it stands.

So `s` is `n`'s components with a dot between each two, none holding a dot: the stretches of `s` are exactly `n`'s components, and `Required.nameOf` of them is `n`. A name Lean prints otherwise, such as one with a component that holds a dot, a non-ASCII letter, `!` or `?`, or that starts with `_`, is refused by name, never read as another.

## Worked example

[`LeanIntentExamples/Required.lean`](../LeanIntentExamples/Required.lean): the sorting deliverable of [the confirmation check's example](confirmation.md#worked-examples), with a typed `Required` value (`sortingRequired`) carrying `o2`, `o2Run`, `o3`, `o4`, `freedom := .eq`, `o5`, `comparison := .records sortedOnly (.implies sorting_narrower) (.separates nilSort nilSort_separates)`, and `additional := [⟨sorting_verdicts⟩]`; unrepresentability theorems for empty `.cases` (`emptyCases_unrepresentable`), blank `.deferred` reason (`blankDeferred_unrepresentable`), and both-directions-unproved `.records` (`bothUnproved_unrepresentable`); and decision theorems showing that a complete built entry finds nothing and lists every theorem, no `Required` entry passes unchanged (`undeclaredProject_accepted`), and refusals catch missing deliverables (`undeclared_refused`), duplicate `Required` values (`several_refused`), deferred `O2Run` on an implemented deliverable (`o2RunDeferred_implemented_refused`) while listing it when awaiting (`o2RunDeferred_awaiting_listed`), self-comparison (`selfComparison_refused`), unbuilt or non-constant blind records (`blindUnbuilt_refused`, `blindNotConstant_refused`), zero-proof comparisons (`noComparisonProof_refused`), unbuilt theorems/values/deliverables/implementations, untied values, non-constant proofs, and non-theorem constants, while surfacing `.unproved` directions (`unprovedDirection_listed`) and `.cases` comparisons (`casesComparison_listed`). A worked example holds no build, so the reader is not run by it.

## What is trusted

- That `built` is the list of modules the project's proof check builds. The gate gives it; read from Lake as above it is Lake's own list for the libraries named, and which libraries those are follows from the proof check's command, which the gate's author reads. A list naming a module the check does not build lets a theorem in it pass.
- That every value of `Required` the project has is in a module the gate's environment holds. The reader reads every module the gate imports and every module those reach, and refuses a value in one the build does not list; a value in a source file that none of them imports is not in the environment, so neither it nor the theorems it lists are read. Such a file is not built, and nothing read names it, which is the position of a project in whose environment no value is read. Reading it would mean reading the project's source tree, a route the library's checks do not take, so this remainder is accepted risk.
- That additional shape-dependent and consequence theorems beyond `O2`, `O2Run`, `O3`, `O4`, `O5`, and the blind comparison are listed in `additional`, and that a `.records` blind formalization came from a genuinely isolated blind session rather than a copy under a different name. Core obligations and at least one blind-comparison proof are now typed facts of `Required d` checked by Lean's kernel, while `additional` and `.cases` theorem statements and operational blind-session isolation remain the procedure's and review's responsibility.
- That a constant whose type is `Required _`, `Deliverable _` or `Implementation _` only inside another type, such as a function returning one or a structure holding one, declares no value: it is not found, here as in the other readers.
- That a theorem's proof rests only on axioms the project accepts, and that Lean's kernel checked it, as the confirmation and implementation checks trust for the proofs they read: `sorry` is an axiom (`sorryAx`) that a build with warnings as errors refuses and `#print axioms` lists, and the option `debug.skipKernelTC` skips the kernel's check. A project's gate audits the axioms as it audits its other proofs.
- That Lean's kernel reduction preserves the type and meaning of the admitted declaration, as [the implementation check's document](implementation.md#why-the-reader-requires-safe-definitions) sets out for the reader both share.
- That Lean prints a name as its source at v4.36.0 says, on which rests that the name `queryModules` gives for an accepted string is the name Lake printed: the argument is set out in [Why the name `queryModules` gives is the name Lake printed](#why-the-name-querymodules-gives-is-the-name-lake-printed), with the lines it reads, and is not proved. That distinct accepted strings give distinct names is proved (`moduleName?_inj`).
- That Lean imports, into a file that is not a `module` file, every module its imports reach with everything each declares, on which rests that the reader sees every value those modules declare: read from `importModulesCore` at v4.36.0, and observed for a `private` value of a `module` file.
- That every module a listed theorem's module imports was built from the project's committed source. A listed theorem's proof may use theorems of the modules it imports, as an entry written as a theorem applied to arguments does through the auxiliary theorem Lean makes of it; Lake builds those imports, but an import Lean resolves to a compiled file Lake does not manage, such as one left in a build directory, is not rebuilt, as [the README's section on upgrading](../README.md#upgrading-from-import-leanintent) sets out.
