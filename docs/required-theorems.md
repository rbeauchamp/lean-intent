# The theorems a deliverable relies on, where the proof check builds them

**The theorems a deliverable relies on** (`LeanIntent.Required`, `LeanIntent.Proof`, `LeanIntent.Required.Read`): a value a project declares that names, for one deliverable, theorems the intent-first procedure requires of it, each by its proof; and the decision a project's gate runs, with the confirmation and implementation checks, that reads every such value in every module the gate's environment holds and, once there is one, refuses the project unless each deliverable is named by one and each such value, each theorem it lists, each deliverable and each value recording an implementation is declared in a module its build lists, read from Lean's environment and from Lake's own list of the modules the build compiles, with theorems stating what it decides.

Modules: `LeanIntent/Required.lean` (the value, the decision and its theorems, which import no more of Lean than the rest of the core), `LeanIntent/Required/ModuleName.lean` (the closed form of module names the reader of Lake's list accepts, with its theorems) and `LeanIntent/Required/Read.lean` (reading the build and Lake's list of its modules, which imports all of Lean).

**Complete in this version:** the value, the decision with its theorems, and the reader a gate calls, with the reader of Lake's list. That every theorem the procedure requires is named is not established, and nor is what each named theorem states; a value in a source file that no module the gate imports reaches is not read. See [What is trusted](#what-is-trusted).

The intent-first procedure has a project prove theorems it then relies on: a record's adequacy obligations, the comparison between a second model's blind formalization and the record, the answers a deliverable keeps and the proof that its implementation fulfils the record. A theorem is checked only where the project's proof check, the check it runs on every change to establish its proofs, builds the module that declares it. In an adopting project the comparison theorems sat in an uncommitted scratch file that its proof check never ran, so the step read as done while nothing was checked. A written rule to commit them where the check builds them depends on whoever follows it; this check makes the failure a refusal.

## What a project declares

For each deliverable, at least one value, in a module the proof check builds that imports the deliverable and the theorems it lists:

```lean
import LeanIntent.Required

/-- The theorems the procedure requires of the sorting deliverable, each by its name. -/
def sortingRequired : LeanIntent.Required sortingDeliverable where
  theorems := [⟨sorting_o2⟩, ⟨sorting_o3⟩, ⟨sorting_o4⟩, ⟨sorting_o5_eq⟩, ⟨sorting_verdicts⟩,
    ⟨sorting_narrower⟩, ⟨nilSort_separates⟩]
```

Each entry is a `LeanIntent.Proof`, a proof of some proposition, written as the theorem's name, `⟨name⟩`, or `⟨@name⟩` where the theorem's first arguments are implicit, since Lean would otherwise apply it to arguments it infers. Lean checks, when the value is declared, that each entry is a proof and that its name is a constant the module imports. A value lists at least one theorem: the field `nonempty` holds the proof that the list is not empty, which its default, `simp`, proves of a list written out, so an empty list is no value of the type (`empty_unrepresentable` in the worked example). A deliverable may have several values, for example one beside its obligations and one beside the comparison with the blind formalization, each in the module that holds its theorems.

What to list is the procedure's to say: [intent-first](../skills/intent-first/SKILL.md) has a project list every theorem it asks for, its obligations, the comparison with the blind formalization and the consequences it states among them. The answers a deliverable keeps, and the proof that its implementation fulfils the record, need no entry: the deliverable and the value of `LeanIntent.Implementation` hold them, and the decision reads where each of those is declared.

## What it decides

The decision (`Required.findings`) reads the module names the build lists, the deliverables and the values recording implementations, each by the module Lean's environment records as declaring it (`Implementation.Constant`), and, for each value of `Required`, the module that declares it, the deliverable its type names and what it lists, each entry read as a theorem by its module and its name, a constant that is not a theorem, or a term (`Required.Entry`, `Required.Cited`). The reader gives it these from every module the gate's environment holds, not from a list of modules a caller chooses. Its verdict depends only on those declarations and on the module names given as built, never on which package a module belongs to, which Lean's environment does not record. Where no value of `Required` is read, the project is refused nothing, whatever deliverables and implementations are read and whatever the build lists (`findings_nothing`): a project's first such value is how it adopts the check, so a project that adopted lean-intent before it, and whose gate reads none, passes it unchanged until then. Once one is read, the project's own or another package's, the decision lists what is wrong, and `Finding.message` says, for each, what the project declares, moves or gives to clear it:

- **A deliverable declared in a module the build does not list** (`deliverableUnbuilt`), naming it and the module: the proof that its record keeps its answers is checked where that module is built.
- **A value recording an implementation declared in a module the build does not list** (`implementationUnbuilt`), naming it and the module: likewise, for the proof that the implementation fulfils the record.
- **A deliverable no value of `Required` names, where one is read** (`undeclared`), naming it: the refusal says to declare a value of `LeanIntent.Required` for it listing its theorems.
- **A value of `Required` declared in a module the build does not list** (`requiredUnbuilt`), naming it and the module: the proof check never checked that what it lists are proofs, so it is refused whatever it lists, and so is each theorem it lists that lies in such a module.
- **A value whose type names no deliverable of the project** (`untied`), naming it.
- **An entry that is a term rather than a constant** (`notConstant`), naming the value: a term names no declaration whose module can be read.
- **An entry that is a constant but not a theorem** (`notTheorem`), naming the value and the constant, such as a definition or an axiom.
- **A theorem declared in a module the build does not list** (`unbuilt`), naming the value, the theorem and the module: the proof check does not check it.

| Theorem | What it establishes |
|---|---|
| `findings_eq_nil_iff` | for every list of module names, deliverables, values recording implementations and entries, the decision finds nothing exactly when there is no entry, or each deliverable, each such value and each entry is declared in a module the list holds, each deliverable is named by an entry, each entry names a deliverable, and each thing an entry lists is a theorem declared in a module the list holds (`Located`, stated over the lists and sharing no definition with the decision) |
| `findings_nothing` | where there is no entry, so no value of `Required` is read, the decision finds nothing, whatever deliverables and values recording implementations there are and whatever the build lists |
| `undeclared_mem`, `requiredUnbuilt_mem`, `unbuilt_mem` | where there is an entry, a deliverable no entry names is refused, naming it; an entry declared in a module the list does not hold is refused, naming its value and the module; a theorem an entry lists, declared in a module the list does not hold, is refused, naming the value, the theorem and the module |
| `findings_sound` | each finding holds of the lists, and names the deliverable, value, theorem or module it is about |
| `mem_theorems` | the report lists a theorem with a value exactly when that value's entry lists it as a theorem |
| `Required.nonempty` | a value of `Required` lists at least one theorem |
| `moduleName?_inj` | for every two strings, if the decoding of module names gives both the same name, they are the same string: distinct accepted strings give distinct modules |
| `moduleName?_chars`, `moduleName?_isPart` | a string the decoding accepts holds only dots, ASCII letters and digits, `_` and `'`, and each stretch between its dots is an ASCII letter followed by such characters other than the dot; so every other string, one holding `«` or `»` among them, is given no name |
| `moduleName?_parts` | the name the decoding gives has exactly the string's stretches between dots as its components, each a string component |

The decisions, each made on the owner's behalf, which a later change can reverse:

- **The check starts with the first value of `Required` it reads, and from then on every deliverable names its theorems.** A project in whose gate environment no such value is read keeps the verdict it had: one that adopted lean-intent before this check, with deliverables and implementations but no value of `Required`, is refused nothing by it (`findings_nothing`), even where its deliverable lies outside the build's list (`undeclaredProject_accepted` in the worked example). Once one is read, the procedure requires each deliverable's obligations and comparison before it is confirmed, and a theorem nothing names is one no check finds, so a deliverable no value names is refused, and the refusal says what to declare. The procedure's skill has a project declare a value for each deliverable, so a project that follows it adopts the check with its first deliverable.
- **Every value of `Required` the gate's environment holds is read, and one outside the build's list is refused.** The reader takes no list of modules to read: it reads every module the environment holds, so a value cannot be hidden by leaving its module out of a list. A value in a module the build does not list, such as a scratch file that a module the gate imports happens to import, is refused by name with its module, and so is each theorem it lists there (`scratchValue_refused` in the worked example); it does not count as naming its deliverable for the proof check, since the proof check never built it. Deliverables and values recording implementations are read the same way, so one declared in a module the build does not list is refused too.
- **A declaration another package makes is read like the project's own.** The check cannot tell another package's module from the project's own unbuilt one: both are modules outside the names given as built, and an exemption the caller lists would let a scratch module named in it pass unseen. So where a module the gate imports reaches a module of a dependency that declares a deliverable, a value recording an implementation or a value of `Required`, each is refused by name with its module, whoever declared it, until the project gives that module among the built ones, where its proof check builds it: the list Lake prints for that library, when the gate imports all of it, or the modules it names itself, which is then its own claim that the proof check builds them. And since a value of `Required` is then read, the project is held to name each of its own deliverables too, even if it had declared no value itself. This holds for a project with no declaration of its own: what its imports hold decides, not what it wrote. Telling the two kinds of module apart by each module's package, as Lake records it, is rbeauchamp/lean-intent#78.
- **Where a theorem lies is the module Lean's environment records as declaring it**, never its name. One environment holds one declaration of a name: importing a second module that declares a name the environment already holds is an error (`throwAlreadyImported` in Lean v4.35.0's `src/Lean/Environment.lean`, lines 2069 to 2072, called at line 2344), so a theorem of the same name in a file the build does not list cannot pass for one in a module it lists (`sameName_refused` in the worked example).
- **An entry is a constant Lean records as a theorem, and nothing else.** A term could hold a proof under any wrapper, so the decision accepts this closed form and refuses every other by name rather than reading inside it.
- **A module counts as built only where the build's own list names it.** Lake also builds a module that a listed one imports from another library, but its list does not name it, and an import Lean resolves to a compiled file Lake does not manage is not built at all (see [the README's section on upgrading](../README.md#upgrading-from-import-leanintent)); so a theorem in a module of another library is refused unless the gate also gives that library's list, which it does only when the proof check builds that library's modules.

## What a gate reads

`LeanIntent.Required.Read.check built` reads the deliverables, the values recording implementations and the values of `Required` from every module the environment it runs in holds, the file being elaborated included, and decides them against `built`, the module names the build lists; its module comment's table states how each input is read. It takes no list of modules to read. It finds a constant as the confirmation and implementation checks find theirs, by its type reduced through Lean's kernel, but over every definition, opaque constant and axiom of the environment; on a gate that imports all of Lean and Lake beside a small project this took about 0.2 seconds at Lean v4.35.0, and its cost on a project that imports a larger library, such as Mathlib, has not been measured.

Two conditions make that reading complete, and the check is an error where either fails. It runs only in a file that is not a `module` file: there Lean imports every module the file's imports reach, with everything each declares, while a `module` file imports only what each module exports, in which a private value is absent and a theorem is shown as an axiom (`importModulesCore` in Lean v4.35.0's `src/Lean/Environment.lean`, lines 2121 to 2175); it was observed to read a `private` value of a `module` file from a gate that is not one. And every module `built` names must be imported, so that no deliverable of a built module goes unasked about; the error names the first that is not. Each entry of a value of `Required` is reduced by `Render.readWhnf`, through Lean's kernel, to `Proof.mk`'s application, and its proof read as the value holds it: a constant once its metadata is removed, and otherwise a term. Where Lean's elaborator abstracted a proof term into an auxiliary theorem of the value's own module, such as `myRequired._proof_1`, the value holds that theorem's constant and the reader reads it as that theorem, declared in that module; this was observed at Lean v4.35.0 for an entry written as a theorem applied to an argument, while an entry written as a constructor's application was read as a term. A value that is an opaque constant or an axiom does not reduce to its constructor's application and is an error naming it, and an unsafe or partial one is an error too, since the reader's discovery (`Read.declaredAnywhere`) requires safety `safe` of every definition it finds, by the predicate the other readers share (`Confirmation.Read.proofSafe_iff`). It returns a `Report`:

| Field | What it holds |
|---|---|
| `findings` | what is wrong; empty exactly when every required theorem lies in a module the build lists, as above |
| `theorems` | each theorem a value lists, with that value and the theorem's module and name: the account of which module holds each theorem, for the project's report |

### The module names the build lists

The check is only as good as `built`, which must be the modules the project's proof check compiles. A gate reads them from Lake, which owns them, through `Read.queryModules`, which reads what `lake query --json` prints:

- **Which libraries.** The proof check builds the targets its command names: `lake build` with no argument builds the package's default targets (`defaultTargets` in `lakefile.toml`, `@[default_target]` in `lakefile.lean`; `resolveDefaultPackageTarget` in `Lake/CLI/Build.lean`, lines 115 to 118, at Lean v4.35.0), and `lake build <target>` the targets it names. A library target given with no facet selects its `default` facet (`resolveConfigDeclTarget`, lines 89 to 103), which builds the facets in its `defaultFacets`, `#[LeanLib.leanArtsFacet]` unless its configuration says otherwise (`Lake/Config/LeanLibConfig.lean`, line 100; `LeanLib.recBuildDefaultFacets` in `Lake/Build/Library.lean`, lines 177 to 180). For each library whose `leanArts` facet the proof check builds this way, the gate asks Lake for that library's modules; a library whose configuration leaves `leanArts` out of what the check builds is not one of them, and its modules are not built by it.
- **Which modules.** `lake query --json @/<library>:modules` prints the modules that library's `leanArts` facet builds: those its `globs` name, read over the working tree (`LeanLib.getModuleArray`, `Lake/Config/Module.lean`, lines 61 to 66), and, recursively, the modules of the same library they import (`LeanLib.recCollectLocalModules`, `Lake/Build/Library.lean`, lines 31 to 61, the `modules` facet at lines 63 to 65); `LeanLib.recBuildLean` (lines 67 to 72) builds each module that facet lists. The query builds nothing, since the `modules` facet is not buildable. It prints one line for each target (`query` in `Lake/CLI/Main.lean`, lines 992 to 1002), each a JSON array of the module names (`formatQuery`, `Lake/Config/OutFormat.lean`, lines 76 to 80; `ToJson Module`, `Lake/Config/Module.lean`, line 22), each name written by Lean's `ToJson Name` (`src/Lean/Data/Json/FromToJson/Basic.lean`, lines 174 to 187).
- **Reading them.** `Read.queryModules` reads each line with Lean's JSON parser and decodes each name only from a closed form (`Required.moduleName?`): dots between stretches that are each an ASCII letter followed by ASCII letters, digits, `_` or `'`, read as the name whose components are those stretches. Distinct accepted strings give distinct names (`moduleName?_inj`), and every other string is an error naming it, never a name. Lean's printing of a name is not one-to-one, which is why the form is closed: `Name.toString` writes a component that holds a dot between `«` and `»`, but writes one that already holds `»` as it stands (`escapePart`, `src/Init/Data/ToString/Name.lean`, lines 55 to 64, at Lean v4.35.0), so the name with the one component `a.b` and the name with the one component `«a.b»` are both printed `«a.b»`, as was observed, and a decoding that gave either back could count a module the build does not list as built. For a string of the closed form, the name the decoding gives is the name Lean printed: the module comment of [`LeanIntent/Required/Read.lean`](../LeanIntent/Required/Read.lean) sets the argument out from the lines of Lean's source it reads, and it is argued, not proved. A project with a module whose name is not of the form, such as one with a component Lean writes between `«` and `»`, a non-ASCII letter, or a component starting with `_`, gives `built` from Lake's own module values instead, for example by Lake's API in its gate. Output that lists no module at all is an error, since it would leave every theorem unbuilt.

Run the query in the proof check's own checkout, after its build. A glob finds every file in the working tree, committed or not, so in a working tree holding a file that is not committed Lake's list names its module; in a checkout of a commit, which a validation gate builds, the file does not exist, so a theorem in it is not found and a value listing it does not build.

A gate runs the three checks on the same build, from a file that is not a `module` file, with the build's module names as the modules the other two read:

```sh
lake build
lake query --json @/MyProject:modules > .lake/built-modules.json
lake env lean Gate.lean
```

```lean
import LeanIntent.Confirmation.Read
import LeanIntent.Implementation.Read
import LeanIntent.Required.Read
import MyProject.Deliverables
import MyProject.Implementations
import MyProject.Comparison

run_meta do
  let built ← match LeanIntent.Required.Read.queryModules
      (← IO.FS.readFile ".lake/built-modules.json") with
    | .ok built => pure built
    | .error e => throwError "the build's module list cannot be read: {e}"
  let confirmed ← LeanIntent.Confirmation.Read.check built
  let implemented ← LeanIntent.Implementation.Read.check built
  let required ← LeanIntent.Required.Read.check built
  unless confirmed.findings.isEmpty do
    throwError "the deliverables are not confirmed: {confirmed.findings.length} findings"
  unless implemented.findings.isEmpty do
    throwError "the deliverables are not implemented: {repr implemented.findings}"
  unless required.findings.isEmpty do
    throwError "required theorems lie outside the build:\n{"\n".intercalate (required.findings.map (·.message))}"
```

Each check refuses a module given that the gate does not import, so the gate imports every module the build lists, here through the modules that import the rest. The required-theorems check also reads whatever else those imports reach, so the gate imports nothing the project's own modules do not need: a scratch module imported only by the gate would be read, and a value in it refused.

## Worked example

[`LeanIntentExamples/Required.lean`](../LeanIntentExamples/Required.lean): the sorting deliverable of [the confirmation check's example](confirmation.md#worked-examples), with a value naming its obligations, the verdicts of its degenerate subjects and two theorems comparing its record with another reading (`sortingRequired`); a value listing no theorem cannot be declared (`empty_unrepresentable`); and the decision, given what the build shows, finds nothing and lists each theorem by its module and its name, finds nothing where no value of `Required` is read, and refuses by name a deliverable no value names once another is named, a second value for the deliverable declared with its theorem in a scratch module the build does not list, beside the value the build does list, a theorem in such a module, a theorem of a listed one's name declared in such a module, the deliverable or the implementation's value declared in such a module, a value tied to a deliverable the project does not declare or to a term, a term, and a constant that is not a theorem. A worked example holds no build, so the reader is not run by it; it was observed at Lean v4.35.0 on a project depending on this library, whose gate read Lake's list for its default libraries with `queryModules`. With every value in a module the build lists it found nothing and listed each theorem by its module. It refused, each with the message above: a value and its theorem in a module of a library the default targets do not build, which the gate imported, and the same for a `private` value in a `module` file of such a library; a value in a built module that was left out of the names given; a theorem of this library, a dependency; this library's own worked example, its deliverable, its implementation's value and its value of `Required`, once the gate imported it; a definition; and a term. It gave an error in a gate that is a `module` file, on a name given as built whose module the gate did not import, and on an unsafe value, an opaque constant and an axiom of the type, while reading a list joined by `++` and an entry defined by name as the values they reduce to, and a theorem applied to an argument as the auxiliary theorem Lean made of it. `queryModules` read Lake's lines as printed, and gave an error naming `«a.b»`, a name with a numeric component, one with an empty stretch, one starting with `_`, and one holding a non-ASCII letter.

## What is trusted

- That `built` is the list of modules the project's proof check builds. The gate gives it; read from Lake as above it is Lake's own list for the libraries named, and which libraries those are follows from the proof check's command, which the gate's author reads. A list naming a module the check does not build lets a theorem in it pass.
- That every value of `Required` the project has is in a module the gate's environment holds. The reader reads every module the gate imports and every module those reach, and refuses a value in one the build does not list; a value in a source file that none of them imports is not in the environment, so neither it nor the theorems it lists are read. Such a file is not built, and nothing read names it, which is the position of a project in whose environment no value is read. Reading it would mean reading the project's source tree, a route the library's checks do not take, so this remainder is accepted risk.
- That every theorem the procedure requires is listed. The decision reads what the values list, and a theorem no value lists is not read; the procedure's skill says what to list, and review reads it. A design that makes the presence of each obligation a fact of the value's type is rbeauchamp/lean-intent#77.
- That a constant whose type is `Required _`, `Deliverable _` or `Implementation _` only inside another type, such as a function returning one or a structure holding one, declares no value: it is not found, here as in the other readers.
- That each listed theorem states what the procedure asks of it. The decision reads where a theorem lies, not its statement, which review reads.
- That a theorem's proof rests only on axioms the project accepts, and that Lean's kernel checked it, as the confirmation and implementation checks trust for the proofs they read: `sorry` is an axiom (`sorryAx`) that a build with warnings as errors refuses and `#print axioms` lists, and the option `debug.skipKernelTC` skips the kernel's check. A project's gate audits the axioms as it audits its other proofs.
- That Lean's kernel reduction preserves the type and meaning of the admitted declaration, as [the implementation check's document](implementation.md#why-the-reader-requires-safe-definitions) sets out for the reader both share.
- That Lean prints a name as its source at v4.35.0 says, on which rests that the name `queryModules` gives for an accepted string is the name Lake printed: the argument is in the module comment of `LeanIntent/Required/Read.lean`, with the lines it reads, and is not proved. That distinct accepted strings give distinct names is proved (`moduleName?_inj`).
- That Lean imports, into a file that is not a `module` file, every module its imports reach with everything each declares, on which rests that the reader sees every value those modules declare: read from `importModulesCore` at v4.35.0, and observed for a `private` value of a `module` file.
- That every module a listed theorem's module imports was built from the project's committed source. A listed theorem's proof may use theorems of the modules it imports, as an entry written as a theorem applied to arguments does through the auxiliary theorem Lean makes of it; Lake builds those imports, but an import Lean resolves to a compiled file Lake does not manage, such as one left in a build directory, is not rebuilt, as [the README's section on upgrading](../README.md#upgrading-from-import-leanintent) sets out.
