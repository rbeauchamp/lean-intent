# Showing a record to its owner

**A rendering for the owner** (`LeanIntent.Render`): whether an owner confirmed the record's restatement, then each statement of the record and each consequence shown with it printed with Lean's notation, as text Lean reads back as the very term, a consequence with who settled it, beside a plain-word explanation of what it requires, rules out, still allows, and the freedom it leaves, followed by every declaration the record's meaning reaches, printed in full, and the Lean release whose libraries the rest are. An exact form prints the same with every implicit argument, by a printer proved to parse back what it prints. The owner confirms the record by reading it, as the plain restatement of their intent, and each answer has a canonical text of the same kind.

Modules: `LeanIntent/Explain.lean` (explanations and their glosses), `LeanIntent/Print.lean` and the modules under `LeanIntent/Print/` (the audited printer, and the declarations a meaning reaches), and `LeanIntent/Render.lean` (the rendering). A generic record's rendering is described with [generic records](generic-records.md).

**Complete in this version:** the audited printer, the rendering of records and their consequences in its readable and exact forms with every declaration their meaning reaches, a definition by structural or well-founded recursion shown by the equation that determines it, and the rendering of a generic record, in general and at representative values. Its claims are theorems Lean's kernel checks, except the one the rendering checks each time it runs, that Lean reads each printed statement back as the term it is, and those listed under [What is trusted](#what-is-trusted) as argued, such as that the rendering prints each declaration it reaches in full.

The owner reads each statement of a record, and each consequence shown with it, in two forms side by side: printed, and explained in plain words. An explanation (`LeanIntent.Explanation r`) gives the record `r` a gloss (`LeanIntent.Gloss`) for its shape and for each domain hypothesis, property and vocabulary predicate, records whether an owner confirmed the record's restatement (`LeanIntent.Restatement`), and lists the consequences shown with it (`LeanIntent.Consequence`, see [the owner's answers](answers.md)): the forks the record leaves open that the owner decides, and any other consequence the explanation chooses to show, each with a gloss, a proof that it holds of `r` as shown (`Consequence.HoldsOf`): every model satisfies an entailment, and some model a possibility, and who settled it (`LeanIntent.Settled`, see [who settled each thing](who-settled.md)). Its type requires a gloss for every statement, and that proof and a status for every consequence, so no consequence is shown as entailed or as possible unless it is, and none without saying who settled it. A gloss has four parts: what the statement requires, what it rules out, what it still allows, and the freedom it leaves, the freedom obligation O5 shows the owner.

```lean
import LeanIntent.Render
import LeanIntentExamples.Sorting

#render_intent LeanIntentExamples.Sorting.sortingExplained
```

`#render_intent` shows the rendering, a Markdown document, and `LeanIntent.Render.renderExplanation` returns it as text. `#render_intent_exact` shows the same in the exact form. `LeanIntent.Render` imports all of Lean, so only the project or tool that renders needs it.

The readable form exists because the exact one cannot be read at the size of a real record: with every universe, instance and `@` application written out, the Acorn pilot's record of a world's day rendered as 625 lines (rbeauchamp/acorn, `docs/spec-first-pilot.md`). Observed at Lean v4.35.0 on the same record with its six consequences, `dayCycleExplained` in [`LeanIntentExamples/DayWorld.lean`](../LeanIntentExamples/DayWorld.lean), in general and not at representative values: in the text `#render_intent` shows, everything before the folded section of lean-intent's own definitions, which is the statements, their glosses and the project's definitions and what a reader checks against the source, takes 307 lines; the whole of that text, with the sections folded below counted, takes 634 lines and 24 KB, where the text `#render_intent_exact` shows takes 577 lines and 55 KB.

What the rendering establishes, and what it does not:

- **The readable form is read back.** `Reader.print` prints a term by Lean's own delaborator and formatter, keeping the notation the record's source uses and leaving out what Lean infers, under options it fixes whatever the options in force, and shows the text only when Lean's parser and elaborator read it back as the same term, binder names and metadata aside, in the namespace the text names with nothing opened. So a print that lost a binder, a hypothesis, or an argument Lean would not infer back is never shown: it elaborates to another term or to none. When a print is not read back a more explicit one is tried, and last the exact form; only what neither can print is refused. A term that holds a `match` is the one exception to reading back the same term, since Lean compiles a `match` anew each time it reads one, into a new auxiliary constant: such a term may read back as one Lean's kernel finds definitionally equal to it, which means the same. This is checked for each statement shown, not proved for every term.
- **The readable form names what it cannot show.** Lean's reading back fixes what a text means to Lean, not what a notation means to a reader, and no definition the rendering prints says that: a notation declared in a project is listed by name and module in a section of its own, and the exact form prints the statement without it. Lean's own notation is not listed.
- **In the exact form, the printed form determines the term.** `LeanIntent.Print.print` writes a term in a closed subset of Lean's syntax for terms, and `LeanIntent.Print.parse_print` proves that `LeanIntent.Print.parse` reads back from every text it writes the very term it printed, for every term; so two terms that print the same are equal (`print_injective`). `print_isSome_iff` proves which terms it prints (`LeanIntent.Print.Printable`): closed terms built from bound variables, constants, sorts, string and natural number literals, applications, `fun`, `∀` and `let`, written `let x : T := v; b`, or `have x : T := v; b` when the body does not depend on the value, as Lean reads each, whose names it can write and whose bound variables no binder of the same name shadows. It refuses every other term, such as one holding a projection, rather than print it lossily.
- **In the exact form, Lean reads it as that term too.** Before a statement is shown, Lean's own parser and elaborator must read its printed text, in the root namespace with nothing opened, as the same term, binder names and metadata aside. This is checked for each statement shown, not proved for every term: Lean's elaborator is a program outside this library. A statement that fails it is refused, and with it the rendering.
- **Binder names are kept where they can be written, in both forms.** A binder Lean named itself (`a✝`) cannot be written, and one that shadows another, or has the name of a constant's first component, would be misread; the rendering renames just those binders before printing (`LeanIntent.Print.canon`), which changes nothing but their names (`eraseNames_canon`), and a `∀` among them whose variable is unused becomes an arrow. The rendering also removes metadata (`Expr.mdata`, `LeanIntent.Print.eraseMData`), which Lean documents as definitionally equal to the term it annotates and the printer does not write. So the exact text parses back to the statement up to those binders' names, which Lean's kernel ignores, and its metadata.
- **Who settled each thing is printed as the record holds it.** Before its statements the rendering says whether an owner confirmed the restatement, and it prints each consequence with a `**Settled:**` line under the heading `Consequences, each with who settled it`; no other text the rendering writes itself says who confirmed or answered, and a gloss or a consequence's name is free text, printed as written. Those words are a function of the recorded status, and what they claim is proved ([who settled each thing](who-settled.md)); the rendering says itself that whether the record is true is not what it decides. This is what `#render_intent` prints, and `renderExplanation` by default: it takes what to say of who settled each thing (`LeanIntent.Render.Statuses`), so `LeanIntent.Confirmation.Read.renderChecked` prints the words of what the owners' log holds for this revision, and says so ([the confirmation check](confirmation.md)), and `LeanIntent.Render.revisionText` prints the exact form with no word of who settled what, as the text an answer is recorded against.
- **The plain words are trusted, not proved.** A gloss is written by a model; nothing checks that it says what the statement says. The printed statement beside it is what Lean checks, and the owner can read either.
- **Everything the meaning reaches.** After the statements, the rendering prints every declaration they reach outside Lean's own libraries, with lean-intent's `IntentRecord.Meets`, which says what it is to meet the record, and, when it shows consequences, `Consequence.HoldsOf`, which says what it is for one to hold as shown, so that each statement can be read to the end. Each is printed in full: a definition's type and value, except that a definition by structural or well-founded recursion is printed by its type and the equation that determines it (below), and a function that reads a field of a structure by its type and a description that determines its value up to the names, types and annotations of its `fun`s (see [What is trusted](#what-is-trusted)); an inductive type's type, its number of parameters and every constructor's type, which for a structure lists its fields; a theorem's or an opaque constant's type, which is all a term that uses one depends on. `LeanIntent.Print.meaning` collects them by following each declaration's type, a definition's value, and an inductive type's constructors and recursors: the relation of the cone that the check that a record does not depend on its implementation (#2) follows, used as that check defines it (`LeanIntent.Cone.RefersTo`, listed by `LeanIntent.Cone.declRefs`) and not restated, so the two follow one relation, except that a definition by recursion is followed through its type and its equation in place of its compiled value (`LeanIntent.Print.refsVia`); `meaning_ok` proves that it collects every declaration reached and nothing else. Lean's own libraries (`Init`, `Std`, `Lean`, `Lake`, the modules whose `.olean` files the process's search path finds really lying in the directory that holds `Init.Prelude` and each library's root file) are not printed: the rendering records the Lean release and commit they are from. A record whose meaning reaches what cannot be printed is refused, never printed in part: a name with no declaration, an axiom whose type is not a proposition (Lean's module system shows an imported definition whose body is not exposed that way), or a type, value or equation that neither form can print, such as one holding a projection. In the readable form the code Lean generated for each `match` (a matcher and the `casesOn` it uses) and lean-intent's own declarations, the same in every rendering, come last under headings of their own, folded with an HTML `<details>` element, not left out. These declarations are not statements of the record and have no gloss of their own.
- **A definition by recursion is shown by its equation.** Lean compiles a definition by structural or well-founded recursion into a value its syntax cannot write, so the rendering prints such a definition by its type and the equation Lean proves for it, `c.eq_def`, which states its value at every argument, `∀ x₁ … xₙ, c x₁ … xₙ = r`, and which Lean's kernel checked. The definitions shown this way are exactly those Lean's own records of the definitions it compiled by structural or by well-founded recursion hold (`Lean.Elab.Structural.eqnInfoExt`, `Lean.Elab.WF.eqnInfoExt`), whose equation has that form and rests, with the definition and its termination proof, on no axiom but Lean's own; such a definition whose equation fails either test is refused, naming it. The equation determines the definition: Lean accepts it only when `r` uses the values of `c`, and of any function defined together with it, only at structural subterms of its arguments or at arguments below them by a well-founded relation its termination proof shows, and any two functions that satisfy such an equation are equal (`LeanIntent.Render.eq_of_recursion_eqn`); see [What is trusted](#what-is-trusted) for what of this is proved. Every other definition is printed by its value: a definition by `partial_fixpoint`, whose equation need not determine it (`f n = f (n + 1)` holds of many functions), is printed by its value, and an `opaque` or `partial` one by its type, as for any opaque constant.

## Worked examples

- [`LeanIntentExamples/Recursion.lean`](../LeanIntentExamples/Recursion.lean): a record for a check digit whose meaning reaches a definition by well-founded recursion (`digitSum`), one by structural recursion (`total`) and one whose value holds a `let` (`checkDigit`); its rendering prints the first two by the equation that determines each, and the third by its value, `have` and all.
- [`LeanIntentExamples/Sorting.lean`](../LeanIntentExamples/Sorting.lean), described with [the obligations](obligations.md#worked-examples): both sorting records are explained for their owner (`sortedOnlyExplained`, `sortingExplained`).

## What is trusted

- That a gloss says what its statement says. Glosses are written by a model and are not checked; the statement printed beside each is.
- That Lean's parser and elaborator read every printed statement as the term it is: `LeanIntent.Render` checks this for each statement it shows, and no theorem states it for every term. The theorems about the audited printer (`parse_print`, `print_injective`) are about the exact form, not the readable one, whose only link to the term is that check.
- That a reader takes each notation of the readable form to mean what Lean's elaboration of it means. For Lean's own notation that is Lean's documentation; a project's notation is listed, not explained.
- That each section the rendering, an answer's text or a consequence's (`LeanIntent.Render.consequenceText`) writes for a declaration prints all of that declaration's meaning: a definition's value, or for a definition by structural or well-founded recursion the equation that determines it, an inductive type's constructors, and for a theorem, an opaque constant or an axiom of a proposition its type alone. A function that reads a field of a structure is printed by its type, the number of `fun`s of its value, its structure and its field's index, which determine its value up to the names, types and annotations of those `fun`s (`LeanIntent.Render.projShape_determines`, proved); that its printed type fixes those types up to definitional equality for a well-typed definition is argued. A definition by structural or well-founded recursion is printed by its type and its equation, which determines it: that two functions satisfying the equation of a well-founded recursion are equal is proved for one function of one argument (`LeanIntent.Render.eq_of_recursion_eqn`); that the equation Lean states for each definition its records hold has that form, its right side using the values of the definition, and of the functions defined with it, only at arguments below the left side's, for every function in their place, is argued from how Lean compiles and checks such definitions, and that its termination proof is a proof rests on the check that it uses no axiom but Lean's own. This is argued from `LeanIntent.Render`'s code and from Lean's kernel, which never unfolds an opaque constant, treats any two proofs of a proposition as equal, and derives a recursor from its inductive types; that every declaration reached is collected is proved (`meaning_ok`), and that the document as a whole, headings and prose included, determines what it prints is not.
- That Lean's own libraries, which the rendering does not print, mean the same wherever the Lean release and commit it records runs.
- That the process's search path holds Lean's own libraries where Lean's `lib/lean` directory has them, whatever kind of process it is. Which modules count as Lean's own is read from that path, never from where the running executable lies (`LeanIntent.Render.leanOwnModules`, `isLeanOwn_iff`), and a process whose path finds no such directory gets an error, never a text. A project that sets its search path by hand to a directory holding `Init.Prelude` and each library's root file as files of its own has those files counted as Lean's own, and their declarations are not printed. Accepted: that takes deliberately replacing Lean's prelude, which review of the project's build reads.
