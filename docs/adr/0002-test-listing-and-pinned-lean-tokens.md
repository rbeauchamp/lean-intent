# ADR-0002: Test listing (`--tests`), subprocess isolation, and pinned Lean v4.36.0 token audit

## Status

Accepted

## Context

`lean-intent` forbids tests as correctness evidence (`.no-mistakes.yaml`, `test.tests_as_evidence.policy: forbid`). A test is code whose verdict comes from running code on chosen inputs rather than from a proof or type-check over every input. The validation pipeline needs a deterministic listing of every test command in the repository (`lean --run tools/check.lean --tests`), returning empty output with exit `0` when none exist and failing loudly whenever a file cannot be analyzed.

## Decision

### Pinned Lean release and token classification (`testsLean := "4.36.0"`)

`--tests` refuses to run under any Lean release other than `testsLean` (`"4.36.0"`), because its token classification is audited directly from that release's elaborators and token table:

- **Audit provenance (v4.34.1 → v4.35.0 → v4.36.0)**: the classification was read from Lean 4.34.1, from 4.35.0 and again from 4.36.0. Lean 4.35.0's token table (with `Lean`, `Lake`, and `Std` imported) contains the same 29 tokens starting with `#` followed by a letter as 4.34.1. Across `Lean.Elab`, `Lean.Meta`, `Std`, and `Lake`, calls to `evalTerm`, `evalExpr`, `evalConst`, and `Meta.nativeEqTrue` differed from 4.34.1 only by one moved declaration, `constructor` tactic configuration evaluation, and removal of `Meta.reduceBoolNative` / `Lean.reduceBool`. Lean 4.36.0's token table holds the same 29 such tokens as 4.35.0's; the declarations of its modules under `Lean.Elab`, `Lean.Meta`, `Std` and `Lake` that use `evalTerm`, `evalExpr`, `evalConst` or `Meta.nativeEqTrue` are unchanged from 4.35.0's; and `DecideConfig` and `decide`'s elaborator are unchanged.
- **`testTokens`** (16 tokens):
  - Evaluators (`evalTerm`, `evalExpr`, `evalConst`, `Meta.nativeEqTrue`) whose verdict decides pass/fail on chosen inputs: `#eval`, `#eval!`, `#guard`, `run_cmd`, `run_elab`, `run_meta`, `run_tac`, `by_elab`, `test_extern`, `native_decide`.
  - Output/tactic/simp checkers on chosen inputs: `#guard_msgs`, `#guard_panic`, `#guard_expr`, `#check_simp`, `#check_tactic`, `#check_tactic_failure`.
- **Deliberate exclusions**: constructs that evaluate code to an end other than a test verdict (`include_str` path, `#widget`, tactic configuration values, `idbg`, `dbg_trace` which runs only at runtime) and `bv_decide` / `bv_check` (which prove universal goals via certificate checkers and whose added axiom `AXIOMS` rejects).
- **`otherTokens`** (20 tokens): the remaining `#<alpha>` tokens of Lean 4.36.0 — type-check verdicts (`#check`, `#check_failure`, `#check_assertions`, `#synth`, `#reduce`), printers/reporters (`#print`, `#where`, `#version`, `#exit`, `#import_path`, `#show_deprecated_modules`, `#dump_async_env_state`, `#discr_tree_key`, `#discr_tree_simp_key`, `#grind_lint`), command wrappers (`#time`, `#info_trees`, `#with_exporting`), `#widget`, and `#v[`.
- **Fail-closed allowlist**: any token starting with `#` followed by a letter that appears in neither `testTokens` nor `otherTokens` raises an error rather than passing unclassified.
- **`nativeConfig`**: conservatively flags any `decide` configuration item setting `native`, `+native`, or `(native := v)`, as well as any `decide` carrying `(config := c)`, because Lean evaluates `c` into the entire `DecideConfig` struct (including `native`, which routes `decide` through `Meta.nativeEqTrue`).
- **Project-declared elaborators**: any command whose elaboration info tree invokes a project-declared elaborator other than a `Macro`, or whose admitted or expanded syntax contains any syntax node kind with a non-`Macro` project-declared dispatch candidate in `commandElabAttribute`, `termElabAttribute`, `tacticElabAttribute`, `doElemElabAttribute`, `tryTacticElabAttribute`, `grindTacElabAttribute`, `symSimprocElabAttribute`, `symDischargerElabAttribute`, `symDSimprocElabAttribute`, `inductiveElabAttr`, `precheckAttribute`, or `controlInfoElemAttribute` across active elaboration environments (`prevEnv`, `cmdEnv`, and `InfoTree` `CommandContextInfo.env`), is listed as a test so fallback after `unsupportedSyntax` or tactic failure cannot hide a handler via `InfoTree` restoration. A `lakefile.toml` `testDriver` is listed as a test too.

### Execution architecture

- **Topological order and subprocess isolation**: `projectTests` reads each file's imports via `Parser.parseHeader`, sorts tracked Lean files topologically (failing on import cycles or empty file lists), and runs `--tests-module <file> <out>` in a fresh child process per file so no module's elaborated `Environment` stays resident in memory while the next file is elaborated (see [`.no-mistakes.yaml`](../../.no-mistakes.yaml) for current `--tests` resource measurements and bounds; earlier peaks were 2.965 GiB / 106.40 s under Lean v4.36.0 with `no-comments v0.2.0` before wiring `REGULA`, 3.065 GiB before the `v0.2.0` migration, and 4.76 GiB under v4.35.0). Each child writes its `.olean` to a temporary directory removed in `finally`.
- **Sidecar output channel**: `moduleTests` writes each file's test lines to a per-module `.tests` file inside the temporary directory, and `projectTests` reads those files rather than child stdout, because elaborated project commands may print arbitrary text to stdout.
- **Why `main` is `unsafe`**: `--tests-module` invokes Lean's `unsafe enableInitializersExecution` so imported modules run their `initialize` declarations and populate environment extensions (parser tables and elaborator extensions). `Check.check` is also `unsafe` because it calls `enableInitializersExecution` before `importModules ... (loadExts := true)` ([ADR-0009](0009-environment-extension-loading-and-reader-guards.md)), while `projectTests` and `--comments` remain safe (non-`unsafe`): `projectTests` reaches `--tests-module` only in child processes, `--comments` and `checkComments` invoke the pinned `no-comments` subprocess ([ADR-0004](0004-ratcheted-ban-on-lean-comments.md)), and `checkCodes` runs `tools/codes.lean`.
- **Stable line keys (`syntaxKey`).** Each test line encodes `<quoted path> <occurrence-index> <syntaxKey>`. The key records syntax node kinds and children, atom values and identifier names. It omits `SourceInfo`, including positions, whitespace, line comments and plain block comments stored there. Declaration and module docstrings contribute their parsed syntax. Lean's plain-text parser stores the body in an atom. When Verso is enabled for that docstring, Lean parses the body into document syntax and the key encodes that tree recursively. An edit that changes only source information leaves the key unchanged in either mode. See `Lean/Parser/Term.lean` (`docComment`, `commentBody`, `versoCommentBodyFn`) and `Lean/Parser/Command.lean` (`moduleDoc`) at the pinned release.

## Known limitations and consequences

- Kernel-checked `theorem`/`example` declarations on concrete inputs (e.g. `example : f 3 = 9 := by decide`) are not listed; avoiding value-pinning examples rests on review under [`README.md`](../../README.md#adding-a-feature) rather than a mechanical guard (#83 removed the count-only precedent theorems from `LeanIntentExamples/HigherOrder.lean` and `LeanIntentExamples/LargeFinite.lean`).
- `testsOfModule` elaborates `Prop`-typed `by` blocks in full without `debug.byAsSorry` (failing closed on `hasSorry` diagnostics or `debug.byAsSorry` `OptionInfo`), inspecting `CommandInfo`/`TermInfo`/`PartialTermInfo`/`DelabTermInfo`/`TacticInfo`/`ChoiceInfo`/`ChoiceResolutionInfo`/`MacroExpansionInfo` syntaxes, registered `KeyedDeclsAttribute` dispatch candidates across active command environments (`prevEnv`, `cmdEnv`, and `InfoTree` `CommandContextInfo.env`), and hygiene-stripped `nativeConfig` (`eraseMacroScopes`) across expanded tactic macros and custom tactic elaborators; see [`.no-mistakes.yaml`](../../.no-mistakes.yaml) for the measured `--tests` runtime (`196.90 s` and `201.49 s` after `#63`'s `LOADED` and `READERS` additions) and updated `660 s` limit.
- Project-declared deriving handlers are not elaborators and their generated commands use Lean's own elaborators, so `deriving` clauses are not listed (the library's `LeanIntent.Declared` and `LeanIntent.MachineDeclared` handlers generate kernel-checked codes and isomorphisms).
