# ADR-0009: Environment-extension loading (`LOADED`), reader guards (`READERS`), and `Loaded`/`Stored`

## Status

Accepted

## Context

In issue #63, `tools/codes.lean` imported the modules it audited with Lean's `importModules`, whose `loadExts` parameter defaults to `false`. Under `loadExts := false`, Lean leaves every environment extension at its initial value and reports no error (`src/Lean/Environment.lean` lines `2773–2774`, `2808–2819` at Lean `v4.36.0`). Because `LeanIntent.CodeAudit.isCarrier` queried Lean's `classExtension` via `isClass?`, every declaration returned `false`, so every code-audit refusal printed an empty dependent-instance list even when `HasCode` or `Covered` instances depended on the refused attestation. The same underlying cause had occurred once before in `LeanIntent.Execution.Read` during PR #60's review.

Furthermore, any downstream project gate that imports with `loadExts := false` and calls a library reader handed an `Environment` (such as `Confirmation.Read`, `Implementation.Read`, `Execution.Read`, `Required.Read`, `Render.Text`, `Declared.Handler`, `Cone.requireIndependent`, or `CodeAudit.audit`) would quietly compute texts or verdicts from unpopulated extension tables unless the library itself refuses unloaded environments and repository checks enforce proper imports and guards across all library modules and `tools/` scripts.

## Decision

### 1. Refusing unloaded environments (`LeanIntent/Loaded.lean`)

`LeanIntent/Loaded.lean` defines the guard mechanism for every library entry point handed an `Environment`:

- `Loaded (env : Environment) : Prop` holds when `isClass env ``Inhabited = true`, decided by `isLoaded` (`isLoaded_eq_true`). `Inhabited` is declared in `Init.Prelude` (`src/Init/Prelude.lean` line `823`), which every non-prelude module imports.
- Because `classExtension` (`Lean/Class.lean` lines `70–79`) stores classes uniformly across module export levels and populates its state from imported module entries (`Lean/EnvExtension.lean` lines `20–21`, `46–63`), `isLoaded env` is `false` whenever extensions were not loaded (`loadExts := false`) and `true` whenever Lean loaded extension state (either `Elab.processHeader` or `importModules ... (loadExts := true)`).
- `asking` and `askingIn` test `isLoaded (← getEnv)` first and throw `notLoaded` before asking anything of the environment (`asking_eq`, `askingIn_eq`).
- Functions taking an `Environment` outside a monad that cannot throw take `Loaded env` (`CodeAudit.axiomsIn`, `Render.bareConsts`, `Render.holdsMatch`, `Render.equalModuloMatch`, `Render.kernelReduction`, `Render.recursionKind`, `Render.importedModule?`) unless proved stateless below.
- Five pattern-matching handler/render helpers (`chainStx`, `chainGet`, `chainEq`, `withInsts`, `readDerived`) and fuel-bounded `where` helpers (`ctors.ctorFields`, `nameLit.go`, `listElems.go`, `withExplanationTelescope.go`) were rewritten into explicit `match` expressions wrapped directly by `asking do` / `asking <|` so `READERS` inspects one uniform head form.

### 2. Isolating unloaded executable queries (`LeanIntent/Imported.lean`) and Regula `RG1006` compliance

`LeanIntent.Execution.Read` must read an executable's built code without running the executable's `initialize` declarations in the checker's process (`loadExts := false`). `LeanIntent/Imported.lean` isolates that import inside `LeanIntent.Imported.stored`:

- `stored (root : Name) (opts : Options) : IO Stored` calls `importModules #[{ module := root }] opts` (default `loadExts := false`), keeps the `Environment` strictly private inside the closure, and returns only a `Stored` record exposing five stateless fields:
  - `contains : Name → Bool` (`Environment.contains`, `Environment.lean` lines `1306–1307`, reading `constants` built at lines `2694–2712`).
  - `moduleOf : Name → Option Name` (`Environment.getModuleIdxFor?`, lines `994–996`, and `env.header.modules`, lines `2726–2739`).
  - `modules : Array (Name × Array Name)` (`env.header.modules` paired with `ModuleData.imports` from `env.header.moduleData`).
  - `irDecl? : Name → Option IR.Decl` (`IR.findEnvDecl`, `Lean/Compiler/IR/CompilerM.lean` lines `142–143`, reading module IR/olean entries populated unconditionally by `setImportedEntries` / `setImportedIREntries` at `Environment.lean` lines `2273–2311`, `2742`, `2749`, plus `declMapExt` whose `addImportedFn` is `fun _ => {}` at `CompilerM.lean` line `85`).
  - `constCount : Nat` (`env.const2ModIdx.size`, `Environment.lean` lines `875–880`, populated at `2694–2712`, used as fuel by `Execution.Read.buildTable`).
- Accordingly, `Execution.Read.irRefs`, `importersOf`, `reachesIn`, and `executableIn` operate solely on `Stored` (with `reachesIn` and `executableIn` returning `Except String ...`), removing `importedModuleOf` while `nameLit`, `claimOf`, `claims`, and `check` remain guarded by `asking`.
- **Why loaded importing stays in `tools/` (`RG1006`)**: Calling `importModules ... (loadExts := true)` requires calling `Lean.enableInitializersExecution` (`Lean/Compiler/InitAttr.lean` lines `198–203`), which is `unsafe` (`Lean/ImportingFlag.lean` lines `18–32`). Regula `v0.16.0` (`RG1006`, added in #112) forbids all `unsafe` declarations inside claimed library modules (`LeanIntent.*`) and directs runtime entry points outside claimed modules. Therefore, `enableInitializersExecution` + `importModules ... (loadExts := true)` lives in the runtime entry points under `tools/` (`tools/codes.lean` and `tools/check.lean`), while `LeanIntent.Imported` contains only safe total code (`Stored`, `stored`) and no `LeanIntent.Imported.loaded` wrapper is placed in `LeanIntent/`.

### 3. `LOADED` and `READERS` rules in `tools/check.lean`

- **`LOADED`**: Inspects every declaration across all library modules (excluding `LeanIntent.Imported.stored` by name) and across every tracked Lean file selected by `isToolFile` (elaborated in child processes via `--loads` using `elaborate` / `Elab.processHeader`, `Lean/Elab/Import.lean` line `159`, with pinned signatures resolved against `Lean.Environment` imported via `enableInitializersExecution` and `importModules #[{ module := `Lean.Environment }] {} (loadExts := true)` so tools need not import Lean's module-loading API themselves). The total structurally recursive traversal `scanImports` visits every constructor of `Expr` across each declaration's type, value, and recursor rules (`declExprs`), passing spine arguments across `.app` and `.mdata` and resetting arguments when entering binder/projection bodies: any occurrence of `importModules` or `finalizeImport` must pass literal `Bool.true` at parameter `loadExts` (whose position is read dynamically from the constant's type via `loadExtsPosition`, linked to `nthForallName?` by `loadExtsPosition_eq_some` and `importChoices_eq_ok`, failing closed if expected Lean symbols or their `loadExts` parameter are missing, without rejecting unrelated declarations that happen to bind a parameter named `loadExts`), and any occurrence of `withImportModules` (`loadExts := false` at `Environment.lean` lines `2827–2830`) is refused (`loadsOf_names_iff`, `loadsOf_faults_empty_iff`, `loadsOf_ok_spec`). Checked at `v4.36.0`: `Lean.finalizeImport` and `Lean.importModules` are the pinned import functions taking `loadExts`.
- **`tools/check.lean` extension loading and question table (`v4.36.0`)**: `Check.check` imports the built library with `enableInitializersExecution` and `importModules ... (loadExts := true)` so `collectAxioms` reads precomputed `exportedAxiomsExt` records (`Lean/Util/CollectAxioms.lean` lines `120–146`, `149–154`) instead of walking every body from an empty table (`Environment.lean` lines `2338–2370`, `2773–2774`):

| Question in `tools/check.lean` | Extension state answered by | What loads it (`v4.36.0`) |
|---|---|---|
| Constants, modules, types, and values (`AXIOMS`, `PROCESS`, `LOADED`, `READERS`) | None: constant map and module headers | `finalizeImport` (`Environment.lean` lines `2694–2739`) on every import |
| Constant axioms (`AXIOMS`: `collectAxioms`) | `exportedAxiomsExt` (`CollectAxioms.lean` lines `120–146`, `149–154`) | `finalizePersistentExtensions` (`Environment.lean` lines `2338–2370`, `2773–2774`) via `loadExts := true` after `enableInitializersExecution` |
| Compiled IR & runtime calls (`PROCESS`: `IR.findEnvDecl`, `IR.collectUsedDecls`) | Module IR/`.olean` entries (`LCNF/Basic.lean` `1252–1262`, `InitAttr.lean` `112–127`, `Attributes.lean` `265–285`, `310–325`); `declMapExt` state (`CompilerM.lean` `83–118`) starts/stays empty | `setImportedEntries` / `setImportedIREntries` (`Environment.lean` lines `2273–2311`, `2742`, `2749`) on every import |
| Source-written declarations (`READERS`: `written` via `declRangeExt.find? (level := .exported)`) | Module entries for `declRangeExt` (`DeclarationRange.lean` lines `20–23`, `MapDeclarationExtension.find?` at `EnvExtension.lean` lines `192–199`) | `setImportedEntries` at private import level (`Environment.lean` line `2742`) |
| Tool file declarations (`--tests-module`, `--loads`) | All Lean frontend extension states | `Elab.processHeader` (`Lean/Elab/Import.lean` lines `141–169`, `loadExts := true` at line `159`) |

- **`READERS`**: Checks every library `.defnInfo` / `.opaqueInfo` whose type transitively holds `Environment` or `Kernel.Environment` (`holdsEnv`). A source-written (`written`) declaration passes only if it begins with `asking` / `askingIn` (checked on its body or recursive `._unsafe_rec` copy when no outright `Environment`/`Kernel.Environment` appears in its type), takes a `LeanIntent.Loaded` proof (`takesLoaded`), or appears in the closed 12-entry `stateless` list (failing closed if any `stateless` name is unused or zero readers are found). Compiler-generated declarations pass only if nested under a `written` prefix.

### 5. Exhaustive Reader Guard Inventory across Modules

- **`LeanIntent/Cone.lean`**: `requireIndependent` (`asking`); `lookupIn`, `checkRecord`, `firstUnknown` (`stateless`).

### 6. `LOADED` Scope & Indirect Callers (`v4.36.0`)

At Lean `v4.36.0`, indirect callers of `importModules` without `loadExts := true` in `Lean`/`Lake` are `Lean.Idbg.idbgLoadEnv` (`Lean/Elab/Idbg.lean` lines `212–216`, called by `idbgClientLoopImpl` at line `240`), `Lake.CLI.Shake` (`Lake/CLI/Shake.lean` lines `706–708`), `Lake.checkExport` (`Lake/CLI/Main.lean` line `1240`), `LeanIR` (`LeanIR.lean` line `100`), `LeanExport` (`LeanExport.lean` line `16`), and `LeanChecker` (`LeanChecker.lean` lines `33, 42`). `LOADED` checks direct mentions of `importFunctions` and `unloadedImport` rather than transitive call-graph closure across Lean/Lake because none of those debugging/CLI helpers are library dependencies and building a full transitive name closure would slow every `check.lean` run significantly.

## Trusted Base, Accepted Risks, and Consequences

- **Trusted & accepted risks**:
  1. `LOADED` inspects direct term occurrences of `importModules`, `finalizeImport`, and `withImportModules`, accepting the risk of indirect calls through another Lean/Lake function or runtime name lookup via Lean's evaluator.
  2. Deliberate bypass of Lean name privacy (for example extracting the closed-over `Environment` from `Imported.Stored`) or modifying the `storedImport` exemption in `tools/check.lean`.
  3. `READERS` recognizers (`holdsEnv`, `guardedValue`, `takesLoaded`) have no proved soundness equivalence against all evaluation semantics; in particular, `takesLoaded` accepts any `Loaded` binder without relating its argument to the `Environment` argument read (tracked as an open proof obligation).
  4. `Loaded` inspects one class extension (`Inhabited`) and relies on Lean loading either every registered persistent extension or none (`finalizePersistentExtensions` at `Environment.lean` lines `2338–2370`, `2773–2774`).
  5. `tools/codes.lean` and `tools/check.lean` execute `initialize` declarations of imported library modules in-process (`enableInitializersExecution` + `loadExts := true`), trusting that no library module's `initialize` subverts the audit or check.
  6. `READERS` excepts the 12 `stateless` declarations by name without machine-reading the table above.
- **Performance impact & observed `v4.36.0` counts**: Because `tools/check.lean` now imports the library with `loadExts := true`, `Lean.collectAxioms` reads `exportedAxiomsExt` instead of recursively walking every declaration body: with `REGULA_DIR` pinned locally on Apple M5 Max under Lean `v4.36.0`, clean no-`.lake` `tools/check.lean` exited `0` in `114.34 s` (built `82.34 s`), down from `369.32 s` clean (`320.25 s` built) on `main`. Because `LOADED` and `READERS` add definitions elaborated inside `tools/check.lean` during every `--tests` subprocess, `--tests` exited `0` empty in `196.90 s` and `201.49 s` (`3 × 201.49 = 604.47 s`), raising `.no-mistakes.yaml`'s `--tests` wall-clock limit from `540 s` to `660 s`. Across the library, `7` declarations take `Loaded env` (`CodeAudit.axiomsIn`, `Render.bareConsts`, `Render.holdsMatch`, `Render.equalModuloMatch`, `Render.kernelReduction`, `Render.recursionKind`, `Render.importedModule?`) and `12` remain `stateless` exceptions. See [`.no-mistakes.yaml`](../../.no-mistakes.yaml) and [ADR-0001](0001-repository-checks-and-trusted-base.md).
