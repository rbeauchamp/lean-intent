# ADR-0001: Repository checks (`tools/check.lean`, `tools/codes.lean`) and trusted base

## Status

Accepted

## Context

`lean-intent` establishes its claims about itself by machine-checked theorems rather than tests, and enforces repository-wide invariants through one check program (`tools/check.lean`) paired with a helper script (`tools/codes.lean`), the pinned `no-comments` CLI (`tools/no-comments.pin`, `.no-comments.json`), and out-of-tree strict `rbeauchamp/regula` proof-verdict checking (`tools/regula.pin`). Every input must be read through the system that owns it rather than by parsing source text by hand.

## Decision

### Invocation and module-file conventions

- `tools/check.lean` runs from the repository root as `lean --run tools/check.lean [--base-ref <ref>]` (all rules), `lean --run tools/check.lean --tests` (test listing; see [ADR-0002](0002-test-listing-and-pinned-lean-tokens.md)), or `lean --run tools/check.lean --comments [<file>]` (comment inventory guarded by `LAKE-CONFIG` and committed pin/config admission before delegating to the pinned `no-comments` binary; see [ADR-0004](0004-ratcheted-ban-on-lean-comments.md)), where `lean` is elan's shim selecting the toolchain named by `lean-toolchain`.
- It is not invoked through `lake env`, so that both full checks and `--comments` read and validate `lakefile.toml` (and reject `lakefile.lean`) before Lake loads the workspace.
- Both `tools/check.lean` and `tools/codes.lean` are Lean `module` files (satisfying `LEAN-MODULE`). Each declares `main` as `public` (`public unsafe def main` in `tools/check.lean`, see [ADR-0002](0002-test-listing-and-pinned-lean-tokens.md); `public def main` in `tools/codes.lean`), since a `module` file's declarations are private unless marked, and imports each library whose programs `lean --run` executes a second time with `meta import` (`Lake` and `Lake.Load.Package` in `tools/check.lean`; `LeanIntent.CodeAudit` in `tools/codes.lean`), because Lean loads compiled code for `lean --run` only where an import carries `meta`.
- `tools/check.lean` exits `0` when every rule holds and `1` when any rule rejects (printing `[RULE] message` lines to stdout). Uncaught errors print to stderr and also exit `1`.

### Owning-system inputs

Every input to `tools/check.lean` is read through its owning system:

- Tracked Lean files: Git's index (`git ls-files -z -- '*.lean'`); library files are those outside `tools/`.
- Project configuration: Lake's TOML parser (`Lake.Toml.loadToml`) and loader (`Lake.loadPackage` with `configLang? := some .toml`), which loads `lakefile.toml` without resolving dependencies and therefore runs no code of the project.
- Selected library modules: Lake's `Lake.LeanLib.getModuleArray`, reading each target's globs over the working tree as a build does.
- Module names, headers, and builds: Lean's `moduleNameOfFileName` and `Parser.parseHeader`, and `lake build --wfail`.
- Comment inventory and ratchet: the pinned compiled `no-comments` CLI (`rbeauchamp/lean-no-comments` `v0.2.0`, SHA-256-verified and staged through `.lake/cache/no-comments/<sha256>/no-comments` against `tools/no-comments.pin`, and configured by `.no-comments.json`), which inspects every tracked Lean file through Lean's frontend in isolated native child processes against Lake's workspace/tool setup. For `check`, `tools/check.lean` forwards an explicit `--base-ref <ref>` or resolves the exact default ref (`refs/remotes/origin/main` then `refs/heads/main`) to its commit SHA so `no-comments check` resolves Git's merge base of `HEAD` with that base without short-name tag ambiguity; `inventory` (`--comments`) inspects live comments without resolving a baseline ref. Measured `v4.36.0` + `no-comments v0.2.0` resource metrics (clean `check.lean` `328.00 s` / `4.733 GiB` peak, built `check.lean` `312.22 s` / `2.535 GiB` peak, standalone `no-comments check` `23.73 s` / `1.821 GiB` peak, `--tests` `106.40 s` / `2.965 GiB` peak) are recorded in [ADR-0004](0004-ratcheted-ban-on-lean-comments.md) and `.no-mistakes.yaml`.
- Axioms: Lean's `collectAxioms` over the imported environment of the built library modules.
- Compiled code call graph: Lean's `Lean.IR.findEnvDecl` and `Lean.IR.collectUsedDecls` ([ADR-0003](0003-runtime-process-audit-and-exemptions.md)).
- Declared-type code attestations: `LeanIntent.CodeAudit.audit` run via `tools/codes.lean` in a subprocess with `LEAN_PATH` set to Lake's library build directory (because `tools/check.lean` is not itself built against the library).
- Out-of-tree strict Regula proof verdict: `rbeauchamp/regula` `v0.16.0` (commit `e025e3e096fb085d0bc4a9c1a520f15eeb287581`, pinned in `tools/regula.pin`, staged as a clean source checkout under `.lake/cache/regula/<commit>/` or supplied via `REGULA_DIR` checked against the pinned commit SHA), extracting that verified commit tree into an isolated non-symlink temporary build directory with Lake caches disabled and running `REGULA_PROOF=<realDir> lake exe lint standard-logical` against the built zero-dependency `lean-intent` package without adding `regula` to `lakefile.toml`. Measured `v4.36.0` + `no-comments v0.2.0` + `regula v0.16.0` resource metrics on an Apple M5 Max (`0.1 s` descendant RSS sampling): clean empty-cache `tools/check.lean` `369.32 s` / `8.127 GiB` peak (during Regula `lake build lint`), built/warm-cache `tools/check.lean` `320.25 s` / `2.572 GiB` peak, and `--tests` `115.95 s` / `3.050 GiB` peak (`.no-mistakes.yaml` bounds raised to `11 GiB` / `1200 s` for `check.lean`).

### Check rules

- **`LAKE-CONFIG`**: `lakefile.toml` sets only `name`, `defaultTargets`, `leanOptions` (as a table with only `autoImplicit` and `relaxedAutoImplicit`), and `lean_lib` (as an array of tables with only `name`, `roots`, and `globs`), and no `lakefile.lean` exists. In `configExtraKeys`, a non-table `leanOptions`, a non-array `lean_lib`, or a non-table `lean_lib` entry counts as a disallowed key; checking the shapes of the remaining leaf values (`name`, `defaultTargets`, the allowed `leanOptions` values, and `lean_lib` entry values `name`, `roots`, `globs`) is left to Lake's `loadPackage`. This ensures zero external package dependencies and no project code execution during Lake configuration.
- **`LEAN-BUILD`**: The modules selected by Lake's library targets must be identical to the modules of the tracked library files without duplicates, every library target must select at least one module and appear in `defaultTargets` (with `defaultTargets` containing no duplicate or non-library targets), and `lake build --wfail` must build every library file with zero errors and zero warnings (`sorry` produces a warning). Refuses untracked selected modules, unselected tracked library files, omitted default library targets, and empty library file lists.
- **`LEAN-MODULE`**: Every tracked Lean file (`tools/` included) must begin with `module` as parsed by `Parser.parseHeader` (`Elab.HeaderSyntax.isModule`), so a downstream project's `module` file can import any library module. A header parse error is a hard error.
- **`AXIOMS`**: No library module declares an axiom, and every constant declared by a library module depends only on Lean's three axioms (`propext`, `Classical.choice`, `Quot.sound`), ruling out `sorryAx`, `native_decide`, and custom axioms. Fails if the library declares no constants.
- **`PROCESS`**: Compiled library code reaches no monitored process/environment runtime C function except through the exempted `Lean.manualRoot` ([ADR-0003](0003-runtime-process-audit-and-exemptions.md)).
- **`CODES`**: Every declared constant across all library modules (worked examples included) passes `LeanIntent.CodeAudit.audit` via `tools/codes.lean`. Fails if no constants are declared.
- **`NO-COMMENTS`**: `tools/no-comments.pin`, `.no-comments.json`, and `tools/comment-ratchet.json` are tracked regular files at those exact paths in Git's index (mode `100644` or `100755`, stage `0`, non-empty object ID, proved by `parseGitIndexEntry_regular_iff`) and non-symlink regular files in the working tree; every tracked Lean file holds exactly the comments recorded by fingerprint and distinct line count in `tools/comment-ratchet.json` (none where no entry exists); and `tools/comment-ratchet.json` records no new/modified comment fingerprint or increased line count relative to the merge base's manifest (invoking `no-comments check` without `--bootstrap` now that `tools/comment-ratchet.json` is committed on `main`, resolving default base refs via exact `refs/remotes/origin/main` then `refs/heads/main`, and failing closed whenever no merge base can be located; [ADR-0004](0004-ratcheted-ban-on-lean-comments.md)).
- **`REGULA`**: `tools/regula.pin` is a tracked regular stage-0 file in Git's index and a non-symlink regular file in the working tree pinning `VERSION=v0.16.0` and `COMMIT=e025e3e096fb085d0bc4a9c1a520f15eeb287581`. Whether resolved from `REGULA_DIR` (rejecting empty or symlink-traversing paths) or fetched into `.lake/cache/regula/<commit>/` (rejecting symlink cache components, verifying `refs/tags/<version>^{commit} == COMMIT`, and rejecting ignored files), the Regula checkout must have regular non-symlink `lakefile.toml` and `lean-toolchain`, no `lakefile.lean`, real directory `.git` (no symlink or gitfile), clean `git status`, and `HEAD^{commit} == COMMIT`. `tools/check.lean` exports the verified `COMMIT` tree via `git archive` into a fresh non-symlink temporary directory (verified free of symlinks), clears `REGULA_FULL`, `LEAN_PATH`, `LEAN_SRC_PATH`, `LEAN_GITHASH`, and Lake cache/config overrides while explicitly disabling Lake's system and artifact caches (`LAKE_CACHE_DIR=""`, `LAKE_NO_CACHE=true`, `LAKE_ARTIFACT_CACHE=false`, `LAKE_RESTORE_ARTIFACTS=false`, `LAKE_CONFIG=""`), and runs `REGULA_PROOF=<realDir> lake exe lint standard-logical` once, failing closed if Regula mutates any file, directory, symlink, or Git index/diff/ref in `lean-intent` (tracked, untracked, or ignored), exits non-zero, fails to report `  regula: read <mods.size> claimed modules and <decls> of their constants` (`decls > 0`) before the verdict, or omits the exact final stdout line `regula: proof verdict: pass, which says nothing about what ran during the build, on <realDir>` (without whitespace normalization).

### `tools/codes.lean` exit-code protocol

`tools/codes.lean` distinguishes audit refusal from runner failure using three exit codes:

- `0`: audit accepted every constant (prints nothing).
- `1`: audit refused one or more declarations, or the given modules declared zero constants (an empty audit would accept vacuously), printing one refusal line per reason to stdout.
- `2`: runner error (bad arguments, import failure, audit exception, or I/O error). Because Lean exits with status `1` when an uncaught exception escapes `main` — which `tools/check.lean` would misinterpret as an audit refusal — `tools/codes.lean` wraps its entire `main` in `try ... catch` (including catching errors from `IO.eprintln`) and returns `2` on any exception.

## Trusted base and consequences

- The rules read what the build produced, so they hold only if no build-time metaprogram was written to defeat them: elaborating a Lean file executes any metaprograms it invokes.
- Keeping `tools/check.lean` independent of the built library avoids bootstrap cycles at the cost of spawning `tools/codes.lean` as a child process for `CODES`.
- `NO-COMMENTS` trusts the SHA-256-verified `rbeauchamp/lean-no-comments` `v0.2.0` binary pinned in `tools/no-comments.pin` (staged and verified through `.lake/cache/no-comments/<sha256>/no-comments` with symlink-component rejection on both `NO_COMMENTS_BIN` overrides and cache paths), preserving `LAKE-CONFIG` (zero external Lake package dependencies in `lakefile.toml`).
- `REGULA` trusts `rbeauchamp/regula` `v0.16.0` (commit `e025e3e096fb085d0bc4a9c1a520f15eeb287581`, pinned in `tools/regula.pin`) and its out-of-tree `REGULA_PROOF` strict `standard-logical` proof verdict (`RG1001`–`RG1006`, `RG1011`–`RG1013`, and `RG2001` kernel replay), preserving `LAKE-CONFIG` without modifying `lakefile.toml` or `lake-manifest.json`.
