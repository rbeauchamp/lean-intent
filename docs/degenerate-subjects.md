# The degenerate-subject check

**The degenerate-subject check** (`LeanIntent.degenerate`, `LeanIntent.Verdicts`): the degenerate subjects of the record's type (each constant function, the identity, the empty output and each projection), computed from the type alone and never chosen per record (for a type the project declares, this rests on its deriving handler; see [What is trusted](#what-is-trusted)), with the constants of a type too large to list held by one member; for each, a proved verdict on whether it meets the record; and each that does reported as a possibility to confirm or decline: by the owner when it is a fork their intent does not settle that changes what they get, and otherwise as a decision made on the owner's behalf.

Modules: `LeanIntent/Codes.lean` (the codes of types), `LeanIntent/Degenerate.lean` (the class and its verdicts) and `LeanIntent/Declared.lean` (the deriving handler for the types a project declares).

**Complete in this version:** the degenerate-subject check with the theorems that fix its class, the codes of the structures and inductive types a project declares, written from each declaration by a deriving handler, and of function types and finite types too large to enumerate, found by Lean's instance resolution. Its claims are theorems Lean's kernel checks, except that the code of each type a project declares is the one its declaration fixes, which rests on the deriving handler reading the declaration in order and on nothing else applying the private constructor that marks a declared type's code (see [What is trusted](#what-is-trusted)).

**Not yet built**, each a separate issue of this repository: extending the degenerate check to recursive, nested and mutual declared types (#23), and an audit that each declared type's code is the one its declaration fixes (#24).

A record can have a model and still be met by a subject that does nothing useful: a sorting record that asks only for an ascending output is met by the function that returns the empty list. The degenerate check closes this with a closed class of degenerate subjects, fixed by the subject's type and never chosen per record. Here the class covers a subject of type `a₁ → … → aₙ → b`, a plain value when `n` is zero, whose argument and output types are built from `Unit`, `Bool`, `Nat`, `Int`, `String`, `Fin (n + 1)`, the machine types (`Char`, `UInt8` to `UInt64`, `USize`, `Int8` to `Int64`, `ISize`, `Float`, `Float32` and `BitVec w`) and the structures and inductive types the project declares, by `List`, `Array`, `Option`, `×`, `⊕` and `→` (`LeanIntent.Ty`). Lean's instance resolution finds the type's code (`LeanIntent.Covered`), so no code of a project runs to produce the code of such a type. A type it finds none for, such as a dependent function, `Fin 0`, `Fin n` for a variable `n`, a type constrained by proofs, indices or value parameters other than `Fin (n + 1)` and `BitVec w`, whose parameter only sizes a finite type, or a type in a higher universe, is not covered, and Lean reports that it cannot synthesize `Covered`, so no verdict about it can be stated. `Fin c` for a constant `c` that is not reducible is one such type: write `Fin 8`, which the definition of `c` makes the same type, or declare `c` with `abbrev`. Every `Covered W` carries the isomorphism through which its code stands for `W` and the proof that both are those the library fixes (`LeanIntent.Ty.Stands`), which for a declared type rests on the two assumptions [What is trusted](#what-is-trusted) states about its code; a member of the class stands for values of `W` itself, one subject or, for `.others`, a group of them (`LeanIntent.Degenerate.Is`).

A declared type gets its code from its declaration by `deriving LeanIntent.HasCode` (or `deriving instance LeanIntent.HasCode for T`), whose handler (`LeanIntent.Declared`) reads the constructors and their fields, in declaration order, through Lean's environment. The code holds the type's name, its type parameters' codes and its constructors' fields' codes; the isomorphism takes the `i`-th constructor to the `i`-th alternative of a sum of chains of its fields, and Lean's kernel checks each way undoes the other. So the type's empty value is its first constructor applied to its fields' empty values, its constants are taken at each constructor applied to values of its fields' rules, and the projections of a type with one constructor, such as a structure, reach into its fields. A subject a member names is the constant at its value or its projection, carried back through the isomorphism (`Degenerate.constantSubject`, `Degenerate.projSubject`): for a type built only from those `Ty` builds in that is the member itself, and where a declared type is inside, a projection can read as `HasCode.iso.inv (HasCode.iso.to x)` for the identity, which `Iso.inv_to` rewrites to `x`. The handler refuses, leaving the type not covered and saying why: a recursive, nested or mutual inductive type, which needs a code with a fixpoint and a rule for its constants (#23); a type whose values are constrained by proofs, indices or value parameters (an inductive family with indices, a parameter that is not a type of `Type`, a field that depends on an earlier field or whose type is not a type of `Type`, such as a proof), from whose fields alone no empty value follows; an unsafe type; a type with no constructor, which has no value; a type outside `Type`; a field whose type has no code; and a type that already has a code.

A function type inside a subject is a type like any other. Its empty value is the constant function at its result's empty value. It has finitely many values exactly when its result has one value, or its argument and its result have finitely many (`Ty.finite`, `Ty.exists_list_of_finite`, `Ty.infinite`). A function among the arguments is projected by applying it, one level deep, to the empty value of its argument type or to a component of an argument reached without applying a function (`ArgSource`): `(Nat → Nat) → Nat → Nat` has the constant at zero, `fun f _ => f 0`, `fun f n => f n` and `fun _ n => n`. A function in a field of a structure is reached through the field.

| Member | Which | Theorem |
|---|---|---|
| Constant functions | At every value of `b` when `b` has finitely many; otherwise, the constants being infinitely many, at the values the rule `Ty.Small` fixes: a number, string, list or array only at its empty value, the unit type, `Bool`, `Fin (n + 1)` and a machine type at every value, an option, pair or sum at each value built from its components' values under the rule, a declared type at each constructor applied to each combination of its fields' values under the rule, and a function type with infinitely many values at the constant function at each value of its result under the rule. Where these number at most 255 (`Ty.count`, `Ty.listBound`), each is a member. Above that, the constant at `b`'s empty value is a member and all the others are one member (`.others`) | `Sig.const_mem_of_small`, `Sig.others_mem`, `constant_covered`, `constant_covered_of_finite`, `Sig.constants_infinite`, `Ty.mem_part_iff` |
| The empty output | The constant at `b`'s empty value, always a member | `Sig.empty_output_mem` |
| Projections | Each function returning a component of type `b` of one of its arguments: the argument itself, a component of a pair inside it, a component of a field of a declared type with one constructor inside it, or a component of what a function inside it returns on a source | `Sig.proj_mem` |
| The identity | The projection of a function of one argument to its own type; for an argument that is a function, that function applied to the arguments that follow it | `Sig.identity_mem` |

**The rule for finite types too large to enumerate.** The class takes one constant at a time only up to 255 of them, one fewer than the 256 values of `UInt8`, the smallest type the check was asked to treat as too large; a type with no more keeps the class it had when every finite type's values were listed. Above that it counts constants, not type names, so `Fin 256` and a structure of eight `Bool`s are treated as `UInt64` is, and `Fin 255` is not. A machine type counts as above it whatever its values, so that no list of its values need be proved complete, and so does a function type, so that listing it never has to decide equality on its argument type; for `BitVec 3` or `Bool → Bool`, with few values, this only makes one verdict stand for what could have been several. No value is sampled: a fixed sample such as zero, one and the largest value would let through a record met only by the constant at 42, while one verdict on all the others costs one theorem and reports it (`fortyTwo_verdicts` in the examples). A verdict of `false` on `.others` is proved for every value at once; `true` is proved by one witness. That report is coarser than a listing, since it says that some other constant meets the record and not which; the witness is in its proof. So no function takes a member and returns one subject: `Degenerate.reading` reads `.others` as the group `.otherConstants`, which carries no value. So a class has at most 255 members besides its projections (`Sig.length_constants_le`, `Sig.length_degenerate_le`): `UInt64 → UInt64 → UInt64 → UInt64` has five members and a function from a structure to `Fin 8` with no field of that type eight. The number of projections grows with the number of a function's arguments and the sources of each, which this bound does not limit. Computing a long list can go deeper than Lean's default limit on the elaborator's recursion, as `Fin 255`'s does, and `set_option maxRecDepth` raises it.

`Sig.mem_degenerate_iff` states the class apart from the list that computes it, `Fn.apply_const` and `ArgProj.apply_fn` what a constant and a projection return, and `degenerate_ne_nil` that no class is empty. `Verdicts r bs` is the check: its goals (`verdicts`) state, for each member in order, that a subject it stands for (`Degenerate.Is`) meets `r` where `bs` says `true` and that none does where `bs` says `false`, so every verdict is part of a theorem's statement and proved, and a list of the wrong length is refused (`verdicts_correct`). `metBy W bs` lists the members the verdicts report as meeting the record, exactly those that do (`mem_metBy`). Read through `Degenerate.reading`, `(metBy W bs).map Degenerate.reading` shows each subject it names, which meets the record and is the one subject its member stands for (`meets_of_subject_mem_metBy`, `Degenerate.is_of_reading_eq_subject`), and shows `.otherConstants` exactly when the class holds that member and some constant among them meets the record (`otherConstants_mem_metBy_iff`), so a group that meets it is never dropped and never reads as one subject. `possibilities h`, from a proof `h : Verdicts r bs`, reports each as a `Consequence` of kind possibility, the predicate that the subject is one the member stands for, which holds of the record as shown (`mem_possibilities`, `possibilities_holdsOf`), so it can be shown with the record, with its gloss (`Shown`). A report exists only for proved verdicts. An answer to it is stored and kept as every other answer is ([the owner's answers](answers.md)); a declined one is kept by exactly the revisions no subject of the member meets (`Degenerate.declined_keptBy_iff`). Proved verdicts that report nothing refute every subject of every member (`not_meets_of_metBy_eq_nil`).

## Worked examples

- [`LeanIntentExamples/Decision.lean`](../LeanIntentExamples/Decision.lean): a procedure deciding evenness, `Nat → Bool`, whose output type has finitely many values, so the degenerate class holds the constant function at each; a record asking only for sound answers is met by the procedure that always answers `false`, which the check reports.
- [`LeanIntentExamples/Declared.lean`](../LeanIntentExamples/Declared.lean): a structure `Point`, an inductive type `Light`, a structure with a parameter and a structure with a field of a declared type, each coded by `deriving LeanIntent.HasCode`; the codes and isomorphisms follow the declarations (`point_code`, `light_iso`). A function from points to numbers has the constant at zero and the projections onto the coordinates, and a record asking only for a result at least the first coordinate is met by the projection onto it, which the check reports (`atLeastX_verdicts`); a function from lights to lights has the constant at each light and the identity, and a record asking only that red follow green is met by the constant at red.
- [`LeanIntentExamples/LargeFinite.lean`](../LeanIntentExamples/LargeFinite.lean): `UInt64 → UInt64 → UInt64 → UInt64`, whose class has five members and every constant of which is covered (`hash_length`, `hash_constant_covered`); a record asking the result to vary refutes all the constants in one theorem (`varies_verdicts`), and a record met only by the constant at 42 is reported (`fortyTwo_verdicts`). A function from a declared clock to `Fin 8` has the constant at each phase (`phase_subjects`, `reachesAll_verdicts`), and `Fin 255`, `Fin 256`, `Char` and a structure of eight `Bool`s show where the rule falls.
- [`LeanIntentExamples/HigherOrder.lean`](../LeanIntentExamples/HigherOrder.lean): a function taking a function (`apply_subjects`, `applies_verdicts`), a structure with a function in a field (`handler_subjects`), a function inside the output, among whose other constants is `not` (`not_is_other`), and which function types have finitely many values.
- The sorting and counter examples, described with [the obligations](obligations.md#worked-examples), state the degenerate check's verdicts too: it reports the empty-list function for the first sorting record (`sortedOnly_verdicts`, `sortedOnly_possibilities`) and the step that does nothing for the counter declared as a plain value (`neverDecreasesAsValue_verdicts`).

## What is trusted

- That a covered type has only the code the library's instances find for it, so that no record can be checked against a smaller class. Another instance would have to prove `Ty.Stands` of its code and isomorphism: for a type built only from those `Ty` builds in, its constructors admit only a code that denotes the type itself, through the cast along that equality or the type formers' maps of such casts, each of which maps every value to itself, and a different code would equate two different types, which Lean cannot prove without a further axiom; this is argued, not proved. A subject's code is computed from its type's code (`Sig.Stands`, `Sig.ofTy`), so an instance cannot present a function as a plain value and so avoid its projections (`Sig.Stands.out_ne_arrow`). For a declared type, the handler refuses a type that already has a code.
- That the code of a declared type follows its declaration: that the deriving handler reads the constructors and their fields in declaration order, which is its own code and not checked by Lean's kernel (the kernel checks only that the isomorphism it writes is one), and that nothing else applies the private constructor of `Ty.Stands` that admits a declared type. Lean's privacy is a rule of name resolution: it refuses `Ty.Stands.decl` written by name, `⟨…⟩` and `{ … }`, but the `constructor` tactic, which applies a constructor without resolving its name, or a metaprogram that builds the term directly, can still apply it and so pair a declared type with a code or isomorphism the record's author chose. No mechanism inside Lean's logic prevents this, since the logic cannot refer to the constructors of an arbitrary type; #24 tracks an audit that re-derives each declared type's code and isomorphism from the environment and compares them with every instance a theorem depends on, which removes the second assumption.
- That a constant function the class leaves out is not one the owner needed to see: where the output type has infinitely many values the class takes only the constants its rule fixes, so a record met by the function returning `[0]` for every input, and by no member, is not reported. No finite set of checked subjects closes this gap for every record; the freedom O5 shows the owner still spans it. Where the output type has finitely many values the class leaves out no constant, however many there are (`constant_covered_of_finite`).
- That a function the class leaves out, because it applies a function more than one level deep (`fun f n => f (f n)`) or combines projections, is not one the owner needed to see; the same freedom spans it. A function inside the output of a constant is a constant function only, where its type has infinitely many values, so `fun _ => id` at `Nat → (Nat → Nat) × Unit` is no member, as `fun _ => [0]` is none at `Nat → List Nat`.
- That every record about a covered type has its verdicts stated, and every record about another type is checked by other means: Lean refuses to state verdicts about a type the class does not cover, but nothing in the library requires verdicts of a record, as nothing requires O1 to O5.
