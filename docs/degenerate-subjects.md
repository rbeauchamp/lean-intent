# The degenerate-subject check

**The degenerate-subject check** (`LeanIntent.degenerate`, `LeanIntent.Verdicts`): the degenerate subjects of the record's type (each constant function, the identity, the empty output and each projection), computed from the type alone and never chosen per record (for a type the project declares, this rests on its deriving handler; see [What is trusted](#what-is-trusted)), with the constants of a type too large to list held by one member; for each, a proved verdict on whether it meets the record; and each that does reported as a possibility to confirm or decline: by the owner when it is a fork their intent does not settle that changes what they get, and otherwise as a decision made on the owner's behalf.

Modules: `LeanIntent/Codes.lean` (the codes of types), `LeanIntent/Degenerate.lean` (the class and its verdicts), `LeanIntent/Declared.lean` (the deriving handler for the types a project declares) and `LeanIntent/CodeAudit.lean` (the audit that no declaration a theorem depends on attests a declared type's code other than as the handler does).

**Complete in this version:** the degenerate-subject check with the theorems that fix its class, the codes of the structures and inductive types a project declares, recursive, nested and mutual ones included, those each of whose constructors holds a value of a type of their group among them, written from each declaration by a deriving handler, and of function types and finite types too large to enumerate, found by Lean's instance resolution. The audit of declared types' codes, which decides, for a declaration a project names, that nothing it depends on applies the private constructor that marks a declared type's code other than as the deriving handler does, with the theorem stating what its procedure decides. Its claims are theorems Lean's kernel checks, except that the code of each type a project declares is the one its declaration fixes, which rests on the deriving handler reading the declaration in order and, for a declaration the audit has not accepted, on nothing else applying that constructor (see [What is trusted](#what-is-trusted)).

**Not yet built**, a separate issue of this repository: covering subject types in a higher universe, such as an agent that carries its own memory type, in this check and [the trivial-witness check](trivial-witnesses.md) (#43).

A record can have a model and still be met by a subject that does nothing useful: a sorting record that asks only for an ascending output is met by the function that returns the empty list. The degenerate check closes this with a closed class of degenerate subjects, fixed by the subject's type and never chosen per record. Here the class covers a subject of type `a₁ → … → aₙ → b`, a plain value when `n` is zero, whose argument and output types are built from `Unit`, `Bool`, `Nat`, `Int`, `String`, `Fin (n + 1)`, the machine types (`Char`, `UInt8` to `UInt64`, `USize`, `Int8` to `Int64`, `ISize`, `Float`, `Float32` and `BitVec w`) and the structures and inductive types the project declares, recursive, nested and mutual ones included, by `List`, `Array`, `Option`, `×`, `⊕` and `→` (`LeanIntent.Ty`). Lean's instance resolution finds the type's code (`LeanIntent.Covered`), so no code of a project runs to produce the code of such a type. A type it finds none for, such as a dependent function, `Fin 0`, `Fin n` for a variable `n`, a type constrained by proofs, indices or value parameters other than `Fin (n + 1)` and `BitVec w`, whose parameter only sizes a finite type, or a type in a higher universe, is not covered, and Lean reports that it cannot synthesize `Covered`, so no verdict about it can be stated. `Fin c` for a constant `c` that is not reducible is one such type: write `Fin 8`, which the definition of `c` makes the same type, or declare `c` with `abbrev`. Every `Covered W` carries the isomorphism through which its code stands for `W` and the proof that both are those the library fixes (`LeanIntent.Ty.Stands`), which for a declared type rests on what [What is trusted](#what-is-trusted) states about its code; a member of the class stands for values of `W` itself, one subject or, for `.others`, a group of them (`LeanIntent.Degenerate.Is`).

A declared type gets its code from its declaration by `deriving LeanIntent.HasCode` (or `deriving instance LeanIntent.HasCode for T`), whose handler (`LeanIntent.Declared`) reads the constructors and their fields, in declaration order, through Lean's environment. The code holds the type's name, its type parameters' codes and its constructors' fields' codes; the isomorphism takes the `i`-th constructor to the `i`-th alternative of a sum of chains of its fields, and Lean's kernel checks each way undoes the other. So the type's empty value is its first constructor applied to its fields' empty values, its constants are taken at each constructor applied to values of its fields' rules, and the projections of a type with one constructor, such as a structure, reach into its fields. A subject a member names is the constant at its value or its projection, carried back through the isomorphism (`Degenerate.constantSubject`, `Degenerate.projSubject`): for a type built only from those `Ty` builds in that is the member itself, and where a declared type is inside, a projection can read as `HasCode.iso.inv (HasCode.iso.to x)` for the identity, which `Iso.inv_to` rewrites to `x`. A recursive type, one that reaches itself through the fields of its constructors, directly, through a type its nested occurrences make (such as `List T` for a field of that type) or through another type of its mutual declaration, gets its code the same way, read through Lean's recursor for it: the recursor's motives are the types of its *group*, those its declaration declares and then those its nested occurrences make, and its induction hypotheses mark each field that holds a value of one of them, or a function to one. The code is `Ty.decl` of its name, its type parameters' codes and `Ty.mu b g r i`: `b` the representation, as above, of its constructors whose fields hold no value of a type of the group (its *base* constructors), in declaration order; `g` the chain of the group's types, each with its other constructors in declaration order and, for each, the codes of its other fields and of its recursive fields' arguments (the unit code for a field that holds a value of the group itself, and the chain of the arguments' codes for a function of several); and `r` the same chain with, for each constructor, the types of the group its recursive fields hold (`ref l` for the `l`-th), which holds no field's code, so that whether the group grows evaluates alike whatever its type parameters are. It denotes trees (`LeanIntent.MuVal`): a base value, or a constructor with the data of its other fields and a child at each position of each recursive field. The isomorphism maps each type of the group to its trees by structural recursion over the group and back by a fold (`Ty.muFold`), and Lean's kernel checks that each map undoes the other. So, by analogy with `List`, whose only constant is `[]`, and `Nat`, whose only constant is `0`, the type's empty value is its first base constructor applied to its fields' empty values, its constants are taken at each base constructor applied to values of its fields' rules, it has infinitely many values (`Ty.mu_infinite`), and it has no projection but the identity. `Expr`, with `num (n : Nat)`, `add (a b : Expr)` and `neg (a : Expr)`, has the empty value `num 0` and that one constant.

A recursive type each of whose constructors holds a value of a type of its group has no base of its own, and takes its empty value from the types its constructors hold, as Lean's derivation of `Inhabited` takes a constructor whose fields all have default values, though from the declaration alone, whatever order its group's types are derived in. The types of the group get their empty values in rounds: in the first, each type with a constructor whose fields hold no value of the group, which takes the first such constructor, as above; in each later round, each type with a constructor whose recursive fields all hold types that got theirs in an earlier round, which takes the first such constructor, in declaration order, applied to its other fields' empty values and, at each position of each recursive field, to the empty value of the type that field holds (`Ty.IsMuEmpty`, stated apart from the function `Ty.muEmptyAt` that computes it, and fixing the value, `Ty.IsMuEmpty.unique`). Its code is `Ty.decl` of its name, its type parameters' codes and `Ty.muAt b g r j i`, whose trees are those of `Ty.mu` with the base `b` of its *root* `j`, the first type of its group, in the order of the recursor's motives, that it reaches and that has a base constructor, and `g` and `r` as above with the root's other constructors; its values are the trees of the group at its `i`-th type, each a node, where the group grows from the root's base values (`Ty.growsAt`), and its empty value is the one that rule states (`Ty.empty_muAt`), as a recursive type's with a base of its own is (`Ty.empty_mu`). So its constants are its empty value alone, by the rule above, which gives it no base value to take a constant at and always takes the empty value; it has infinitely many values (`Ty.muAt_infinite`) and no projection but the identity. A rose tree `inductive Rose | node (n : Nat) (cs : List Rose)` has the empty value `node 0 []`, from its root `List Rose`; the odd half of a mutual even and odd pair has `succ zero`; `structure S where next : Option S` has `⟨none⟩`; and a type of statements each of which holds an expression or statements, mutual with expressions one of which is a number, has `expr (lit 0)`.

The handler refuses, leaving the type not covered and saying why: a recursive type with no value, because each of its constructors has a field that holds a value of a type of its group that has none, such as `inductive Never | mk (n : Never)`, which no code can stand for, since every code denotes a type with a value and Lean's kernel checks the isomorphism; a recursive type whose recursive constructors build only finitely many values because a type of its group they need has none (`Ty.grows`, `Ty.growsAt`), though it may have values; a recursive field that is a function whose arguments depend on a field or on one another; a type whose values are constrained by proofs, indices or value parameters (an inductive family with indices, a group with a type nested through an inductive family with indices, a parameter that is not a type of `Type`, a field that depends on an earlier field or whose type is not a type of `Type`, such as a proof), from whose fields alone no empty value follows; an unsafe type; a type with no constructor, which has no value; a type outside `Type`; a field whose type has no code; and a type that already has a code. A type of a mutual declaration that does not reach itself is coded as a structure is, once the types of its fields have codes.

**The audit of declared types' codes** (`LeanIntent.CodeAudit`). Lean's privacy is a rule of name resolution, so the `constructor` tactic, which applies a constructor without resolving its name, can complete a hand-written instance of `HasCode` with the private constructor of `Ty.Stands` that admits a declared type, and so pair the type with a code or isomorphism its author chose, which changes the class the owner is shown. `LeanIntent.CodeAudit.requireCodes c` refuses the declaration `c`, a `Verdicts` theorem say, unless no declaration it depends on, transitively, applies that constructor other than as the deriving handler does, and it rests on no axiom but Lean's three. It reads the dependencies from Lean's environment, following everything Lean's `collectAxioms` follows (a declaration's type, the value of a definition, theorem or opaque constant, and an inductive type's constructors), and more, through every declaration of a module that is or imports `LeanIntent.Degenerate`, the only modules whose declarations can name the constructor; of a declaration of any other module it takes the axioms Lean's `collectAxioms` reports, since such a declaration can still prove `False` from `sorry` for one that names the constructor's type to use. A declaration that names it, other than the ones Lean generates for `Ty.Stands`, passes only as a theorem whose whole value applies it once, to a type the handler covers, never one `Ty` builds in such as `Bool` or a definition that reduces to it (`Declared.builtinHeads`), with the code and isomorphism the handler derives from that type's declaration: the code re-derived through the handler's own function (`Declared.codeWith`), the isomorphism by where it takes each constructor applied to its fields, which fixes it, and each compared by Lean's kernel, never through a mark the instance carries (`Declared.checkAttestation`). For a recursive, nested or mutual type the code is re-derived through the handler's own reading of its group (`Declared.readGroup`, `Declared.recCodeWith`), and the isomorphism is read by where its forward map, and the map of each other type of the group that map's children reach, take each constructor applied to its fields: the base or node the handler writes, each child the map of its type at the field. Maps that meet those equations for every constructor are the handler's by structural recursion over the group, so this fixes the isomorphism as well (`Declared.checkRecMaps`). Each refusal names the declaration that holds the attestation (for an instance completed by `by constructor`, the proof Lean abstracts out of it, `inst._proof_1`), the type it attests and the instances of `HasCode` or `Covered` among the dependencies that depend on it. It refuses as well an attestation that no instance carries, a proof that names the constructor while it takes a `Ty.Stands` proof apart, which forges nothing but which no declaration of the library writes, and a dependency on `sorry` or on any other axiom, which could state an attestation without naming the constructor. A declaration whose dependencies hold no declared type's attestation is accepted; a name with no declaration is refused. `decide_eq_none_iff` states what its procedure decides, and `verified_of_decide_eq_none` that an acceptance leaves no reached attestation it has not read as the handler's. The handler reads what it writes in the same way and fails rather than write a code the audit refuses, so the two agree on every type the handler covers. `audit` takes a first declaration and a list of the rest, and `requireCodes` one declaration, so no audit is of an empty scope, which would accept anything; a check program whose scope comes from a search refuses when the search finds nothing, as `tools/codes.lean` does. A project runs the audit with its own checks, in a file or from a check program that calls `LeanIntent.CodeAudit.audit`, as `tools/codes.lean` does:

```lean
import LeanIntent.CodeAudit
import LeanIntentExamples.Declared

run_meta LeanIntent.CodeAudit.requireCodes ``LeanIntentExamples.Declared.atLeastX_verdicts
```

`tools/check.lean` runs it over every declaration of lean-intent's modules, the worked examples included (its rule `CODES`). In a module of Lean's module system an imported theorem is shown as an axiom, so run the audit where every module is imported in full, such as in a file outside the module system.

A function type inside a subject is a type like any other. Its empty value is the constant function at its result's empty value. It has finitely many values exactly when its result has one value, or its argument and its result have finitely many (`Ty.finite`, `Ty.exists_list_of_finite`, `Ty.infinite`). A function among the arguments is projected by applying it, one level deep, to the empty value of its argument type or to a component of an argument reached without applying a function (`ArgSource`): `(Nat → Nat) → Nat → Nat` has the constant at zero, `fun f _ => f 0`, `fun f n => f n` and `fun _ n => n`. A function in a field of a structure is reached through the field.

| Member | Which | Theorem |
|---|---|---|
| Constant functions | At every value of `b` when `b` has finitely many; otherwise, the constants being infinitely many, at the values the rule `Ty.Small` fixes: a number, string, list or array only at its empty value, the unit type, `Bool`, `Fin (n + 1)` and a machine type at every value, an option, pair or sum at each value built from its components' values under the rule, a declared type at each constructor applied to each combination of its fields' values under the rule, a recursive declared type at each of its base constructors so applied, one without a base constructor of its own at its empty value alone, and a function type with infinitely many values at the constant function at each value of its result under the rule. Where these number at most 255 (`Ty.count`, `Ty.listBound`), each is a member. Above that, the constant at `b`'s empty value is a member and all the others are one member (`.others`) | `Sig.const_mem_of_small`, `Sig.others_mem`, `constant_covered`, `constant_covered_of_finite`, `Sig.constants_infinite`, `Ty.mem_part_iff` |
| The empty output | The constant at `b`'s empty value, always a member | `Sig.empty_output_mem` |
| Projections | Each function returning a component of type `b` of one of its arguments: the argument itself, a component of a pair inside it, a component of a field of a declared type with one constructor inside it, or a component of what a function inside it returns on a source | `Sig.proj_mem` |
| The identity | The projection of a function of one argument to its own type; for an argument that is a function, that function applied to the arguments that follow it | `Sig.identity_mem` |

**The rule for finite types too large to enumerate.** The class takes one constant at a time only up to 255 of them, one fewer than the 256 values of `UInt8`, the smallest type the check was asked to treat as too large; a type with no more keeps the class it had when every finite type's values were listed. Above that it counts constants, not type names, so `Fin 256` and a structure of eight `Bool`s are treated as `UInt64` is, and `Fin 255` is not. A machine type counts as above it whatever its values, so that no list of its values need be proved complete, and so does a function type, so that listing it never has to decide equality on its argument type; for `BitVec 3` or `Bool → Bool`, with few values, this only makes one verdict stand for what could have been several. No value is sampled: a fixed sample such as zero, one and the largest value would let through a record met only by the constant at 42, while one verdict on all the others costs one theorem and reports it (`fortyTwo_verdicts` in the examples). A verdict of `false` on `.others` is proved for every value at once; `true` is proved by one witness. That report is coarser than a listing, since it says that some other constant meets the record and not which; the witness is in its proof. So no function takes a member and returns one subject: `Degenerate.reading` reads `.others` as the group `.otherConstants`, which carries no value. A class has at most 255 members besides its projections (`Sig.length_constants_le`, `Sig.length_degenerate_le`): `UInt64 → UInt64 → UInt64 → UInt64` has five members and a function from a structure to `Fin 8` with no field of that type eight. The number of projections grows with the number of a function's arguments and the sources of each, which this bound does not limit. Computing a long list can go deeper than Lean's default limit on the elaborator's recursion, as `Fin 255`'s does, and `set_option maxRecDepth` raises it.

`Sig.mem_degenerate_iff` states the class apart from the list that computes it, `Fn.apply_const` and `ArgProj.apply_fn` what a constant and a projection return, and `degenerate_ne_nil` that no class is empty. `Verdicts r bs` is the check: its goals (`verdicts`) state, for each member in order, that a subject it stands for (`Degenerate.Is`) meets `r` where `bs` says `true` and that none does where `bs` says `false`, so every verdict is part of a theorem's statement and proved, and a list of the wrong length is refused (`verdicts_correct`). `metBy W bs` lists the members the verdicts report as meeting the record, exactly those that do (`mem_metBy`). Read through `Degenerate.reading`, `(metBy W bs).map Degenerate.reading` shows each subject it names, which meets the record and is the one subject its member stands for (`meets_of_subject_mem_metBy`, `Degenerate.is_of_reading_eq_subject`), and shows `.otherConstants` exactly when the class holds that member and some constant among them meets the record (`otherConstants_mem_metBy_iff`), so a group that meets it is never dropped and never reads as one subject. `possibilities h`, from a proof `h : Verdicts r bs`, reports each as a `Consequence` of kind possibility, the predicate that the subject is one the member stands for, which holds of the record as shown (`mem_possibilities`, `possibilities_holdsOf`), so it can be shown with the record, with its gloss (`Shown`). A report exists only for proved verdicts. An answer to it is stored and kept as every other answer is ([the owner's answers](answers.md)); a declined one is kept by exactly the revisions no subject of the member meets (`Degenerate.declined_keptBy_iff`). Proved verdicts that report nothing refute every subject of every member (`not_meets_of_metBy_eq_nil`).

## Worked examples

- [`LeanIntentExamples/Decision.lean`](../LeanIntentExamples/Decision.lean): a procedure deciding evenness, `Nat → Bool`, whose output type has finitely many values, so the degenerate class holds the constant function at each; a record asking only for sound answers is met by the procedure that always answers `false`, which the check reports.
- [`LeanIntentExamples/Declared.lean`](../LeanIntentExamples/Declared.lean): a structure `Point`, an inductive type `Light`, a structure with a parameter and a structure with a field of a declared type, each coded by `deriving LeanIntent.HasCode`; the codes and isomorphisms follow the declarations (`point_code`, `light_iso`). A function from points to numbers has the constant at zero and the projections onto the coordinates, and a record asking only for a result at least the first coordinate is met by the projection onto it, which the check reports (`atLeastX_verdicts`); a function from lights to lights has the constant at each light and the identity, and a record asking only that red follow green is met by the constant at red.
- [`LeanIntentExamples/Recursive.lean`](../LeanIntentExamples/Recursive.lean): a recursive type of arithmetic expressions coded by `deriving LeanIntent.HasCode` (`expr_code`), whose empty value and one constant is `num 0` (`expr_empty`, `expr_part`) and which has infinitely many values (`expr_infinite`); a function from expressions to expressions has the constant at `num 0` and the identity, and a record asking a simplifier only to keep each expression's value is met by the identity, the simplifier that does nothing, which the check reports (`keepsValue_verdicts`, `keepsValue_possibilities`). A JSON type nested through `Array`, `List` and `×` (`json_degenerate`), a tree with a parameter (`tree_degenerate`), a term type with a function in a field (`term_empty`) and one of mutually inductive types (`even_degenerate`) are coded too.
- [`LeanIntentExamples/WithoutBase.lean`](../LeanIntentExamples/WithoutBase.lean): recursive types without a base constructor of their own, coded by `deriving LeanIntent.HasCode`: a rose tree, whose root is `List Rose` (`rose_root`) and whose empty value and one constant is `node 0 []` (`rose_empty`, `rose_part`), a directory of named directories nested through `Array` (`dir_empty`), the odd half of the mutual pair of `LeanIntentExamples/Recursive.lean` (`odd_empty`), a structure whose only field is an option of itself (`link_empty`), and statements mutual with expressions, whose empty value is `expr (lit 0)` (`stmt_empty`); a function from statements to statements has the constant at `expr (lit 0)` and the identity, and a record asking an optimizer only to keep each statement's value is met by the identity, which the check reports (`keepsValue_verdicts`, `keepsValue_possibilities`).
- [`LeanIntentExamples/LargeFinite.lean`](../LeanIntentExamples/LargeFinite.lean): `UInt64 → UInt64 → UInt64 → UInt64`, whose class has five members and every constant of which is covered (`hash_length`, `hash_constant_covered`); a record asking the result to vary refutes all the constants in one theorem (`varies_verdicts`), and a record met only by the constant at 42 is reported (`fortyTwo_verdicts`). A function from a declared clock to `Fin 8` has the constant at each phase (`phase_subjects`, `reachesAll_verdicts`), and `Fin 255`, `Fin 256`, `Char` and a structure of eight `Bool`s show where the rule falls.
- [`LeanIntentExamples/HigherOrder.lean`](../LeanIntentExamples/HigherOrder.lean): a function taking a function (`apply_subjects`, `applies_verdicts`), a structure with a function in a field (`handler_subjects`), a function inside the output, among whose other constants is `not` (`not_is_other`), and which function types have finitely many values.
- The sorting and counter examples, described with [the obligations](obligations.md#worked-examples), state the degenerate check's verdicts too: it reports the empty-list function for the first sorting record (`sortedOnly_verdicts`, `sortedOnly_possibilities`) and the step that does nothing for the counter declared as a plain value (`neverDecreasesAsValue_verdicts`).

## What is trusted

- That a covered type has only the code the library's instances find for it, so that no record can be checked against a smaller class. Another instance would have to prove `Ty.Stands` of its code and isomorphism: for a type built only from those `Ty` builds in, its constructors admit only a code that denotes the type itself, through the cast along that equality or the type formers' maps of such casts, each of which maps every value to itself, and a different code would equate two different types, which Lean cannot prove without a further axiom; this is argued, not proved. A subject's code is computed from its type's code (`Sig.Stands`, `Sig.ofTy`), so an instance cannot present a function as a plain value and so avoid its projections (`Sig.Stands.out_ne_arrow`). For a declared type, the handler refuses a type that already has a code.
- That the code of a declared type follows its declaration. That the deriving handler reads the constructors and their fields in declaration order, and for a recursive type its group and recursive fields from Lean's recursor, and the root it takes from them (`Declared.rootOf`), is its own code and not checked by Lean's kernel (the kernel checks only that the isomorphism it writes is one); the audit derives the code through the same functions, so it does not check that reading. That nothing else applies the private constructor of `Ty.Stands` that admits a declared type is decided by the audit of declared types' codes for each declaration it accepts, and is trusted of every declaration a project does not audit: Lean's privacy is a rule of name resolution, which the `constructor` tactic, or a metaprogram that builds the term directly, passes, and no mechanism inside Lean's logic prevents it, since the logic cannot refer to the constructors of an arbitrary type. What the audit rests on is argued, not proved: that `Declared.checkAttestation` refuses every attestation whose type, code or isomorphism is not the one the handler derives, an attestation of a type `Ty` builds in included, from its code, which leaves each equality to Lean's kernel; that a declaration whose dependencies name the constructor only in attestations and rest on no axiom but Lean's three proves `Ty.Stands` of a declared type's code only for a code and isomorphism equal to those of one of those attestations, from Lean's logic, in which the private constructor is the only rule that concludes it and none of the three axioms proves a proposition without a proof of one equivalent to it; that a declaration of a module that does not import `LeanIntent.Degenerate` cannot name the constructor, since Lean's kernel checks each declaration in its module's environment, and that Lean's `collectAxioms` reports every axiom such a declaration rests on, which the audit refuses unless they are Lean's three; and that the declarations Lean v4.35.0 generates for `Ty.Stands` that name the constructor are its recursor, `casesOn`, `recOn`, and `below` with the declarations under it, as observed of that release, which the audit exempts only when the module that declares `Ty.Stands` declares them. That its procedure decides what `decide_eq_none_iff` states is proved.
- That a recursive type the handler refuses as having no value has none. The handler decides it by the rounds of `Ty.inhabited`, taken as many times as the group has types and one more: a type with a value has one built from constructors whose recursive fields hold values of types that got theirs in earlier rounds, so it is marked, and the marks grow by at least one type each round until they stop changing, so that many rounds reach every type they ever reach. This is argued, not proved; `Ty.inhabited_sound` proves the other direction for the group's trees, that every type the rounds mark has one. Refusing a type with a value would leave it not covered, which the refusal shows, and never give it a wrong code. The other direction needs no trust: every code denotes a type with a value, since every code has an empty value, and Lean's kernel checks the isomorphism between a declared type and its code, so a type with no value has no code.
- That a constant function the class leaves out is not one the owner needed to see: where the output type has infinitely many values the class takes only the constants its rule fixes, so a record met by the function returning `[0]` for every input, and by no member, is not reported, nor, for a recursive type, one met only by the constant at a value its recursive constructors build, such as `add (num 0) (num 0)`. No finite set of checked subjects closes this gap for every record; the freedom O5 shows the owner still spans it. Where the output type has finitely many values the class leaves out no constant, however many there are (`constant_covered_of_finite`).
- That a function the class leaves out, because it applies a function more than one level deep (`fun f n => f (f n)`) or combines projections, is not one the owner needed to see; the same freedom spans it. A function inside the output of a constant is a constant function only, where its type has infinitely many values, so `fun _ => id` at `Nat → (Nat → Nat) × Unit` is no member, as `fun _ => [0]` is none at `Nat → List Nat`.
- That every record about a covered type has its verdicts stated, and every record about another type is checked by other means: Lean refuses to state verdicts about a type the class does not cover, but nothing in the library requires verdicts of a record, as nothing requires O1 to O5.
