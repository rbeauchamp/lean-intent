# The degenerate-subject check

**The degenerate-subject check** (`LeanIntent.degenerate`, `LeanIntent.Verdicts`): the degenerate subjects of the record's type (each constant function, the identity, the empty output and each projection), computed from the type alone and never chosen per record (for a type the project declares, this rests on its deriving handler; see [What is trusted](#what-is-trusted)); for each, a proved verdict on whether it meets the record; and each that does reported as a possibility to confirm or decline: by the owner when it is a fork their intent does not settle that changes what they get, and otherwise as a decision made on the owner's behalf.

Modules: `LeanIntent/Codes.lean` (the codes of types), `LeanIntent/Degenerate.lean` (the class and its verdicts) and `LeanIntent/Declared.lean` (the deriving handler for the types a project declares).

**Complete in this version:** the degenerate-subject check with the theorems that fix its class, and the codes of the structures and inductive types a project declares, written from each declaration by a deriving handler. Its claims are theorems Lean's kernel checks, except that the code of each type a project declares is the one its declaration fixes, which rests on the deriving handler reading the declaration in order and on nothing else applying the private constructor that marks a declared type's code (see [What is trusted](#what-is-trusted)).

**Not yet built**, each a separate issue of this repository: extending the degenerate check to recursive, nested and mutual declared types (#23) and to higher-order subjects and large finite types (#11), and an audit that each declared type's code is the one its declaration fixes (#24).

A record can have a model and still be met by a subject that does nothing useful: a sorting record that asks only for an ascending output is met by the function that returns the empty list. The degenerate check closes this with a closed class of degenerate subjects, fixed by the subject's type and never chosen per record. Here the class covers a subject of type `a₁ → … → aₙ → b`, a plain value when `n` is zero, whose argument and output types are built from `Unit`, `Bool`, `Nat`, `Int`, `String` and the structures and inductive types the project declares, by `List`, `Array`, `Option`, `×` and `⊕` (`LeanIntent.Ty`). Lean's instance resolution finds the type's code (`LeanIntent.Covered`); a type it finds none for, such as a dependent or higher-order function, or a type in a higher universe, is not covered, and Lean reports that it cannot synthesize `Covered`, so no verdict about it can be stated; wider coverage is #11. Every `Covered W` carries the isomorphism through which its code stands for `W` and the proof that both are those the library fixes (`LeanIntent.Ty.Stands`), which for a declared type rests on the two assumptions [What is trusted](#what-is-trusted) states about its code; each degenerate subject is a value of `W` itself.

A declared type gets its code from its declaration by `deriving LeanIntent.HasCode` (or `deriving instance LeanIntent.HasCode for T`), whose handler (`LeanIntent.Declared`) reads the constructors and their fields, in declaration order, through Lean's environment. The code holds the type's name, its type parameters' codes and its constructors' fields' codes; the isomorphism takes the `i`-th constructor to the `i`-th alternative of a sum of chains of its fields, and Lean's kernel checks each way undoes the other. So the type's empty value is its first constructor applied to its fields' empty values, its constants are taken at each constructor applied to its fields' parts, and the projections of a type with one constructor, such as a structure, reach into its fields. A degenerate subject is its member carried back through the isomorphism: for a type built only from those `Ty` builds in that is the member itself, and where a declared type is inside, a projection can read as `HasCode.iso.inv (HasCode.iso.to x)` for the identity, which `Iso.inv_to` rewrites to `x`. The handler refuses, leaving the type not covered and saying why: a recursive, nested or mutual inductive type, which needs a code with a fixpoint and a rule for its constants (#23); a type whose values are constrained by proofs, indices or value parameters (an inductive family with indices, a parameter that is not a type of `Type`, a field that depends on an earlier field or whose type is not a type of `Type`, such as a proof), from whose fields alone no empty value follows; an unsafe type; a type with no constructor, which has no value; a type outside `Type`; a field whose type has no code; and a type that already has a code.

| Member | Which | Theorem |
|---|---|---|
| Constant functions | At every value of `b` when `b` has finitely many; otherwise, the constants being infinitely many, at the values the rule `Ty.Small` fixes: a number, string, list or array only at its empty value, the unit type and `Bool` at every value, an option, pair or sum at each value built from its components' parts, and a declared type at each constructor applied to each combination of its fields' parts | `Sig.const_mem_of_finite`, `Sig.constants_infinite`, `Ty.mem_part_iff` |
| The empty output | The constant at `b`'s empty value, always a member | `Sig.empty_output_mem` |
| Projections | Each function returning a component of type `b` of one of its arguments: the argument itself, a component of a pair inside it, or a component of a field of a declared type with one constructor inside it | `Sig.proj_mem` |
| The identity | The projection of a function of one argument to its own type | `Sig.identity_mem` |

`Sig.mem_degenerate_iff` states the class apart from the list that computes it, `Degenerate.apply_fn` what each member returns, and `degenerate_ne_nil` that no class is empty. `Verdicts r bs` is the check: its goals (`verdicts`) state, for each degenerate subject in order, that it meets `r` where `bs` says `true` and that it does not where `bs` says `false`, so every verdict is part of a theorem's statement and proved, and a list of the wrong length is refused (`verdicts_correct`). `metBy W bs` lists the subjects the verdicts report as meeting the record, exactly those that do (`mem_metBy`), and `possibilities h`, from a proof `h : Verdicts r bs`, reports each as a `Consequence` of kind possibility, the predicate that the subject is that degenerate subject, which holds of the record as shown (`mem_possibilities`, `possibilities_holdsOf`), so it can be shown to the owner with its gloss (`Shown`). A report exists only for proved verdicts. The owner's answer to it is stored and kept as every other answer is ([the owner's answers](answers.md)); a declined one is kept by exactly the revisions the degenerate subject does not meet (`Degenerate.declined_keptBy_iff`).

## Worked examples

- [`LeanIntentExamples/Decision.lean`](../LeanIntentExamples/Decision.lean): a procedure deciding evenness, `Nat → Bool`, whose output type has finitely many values, so the degenerate class holds the constant function at each; a record asking only for sound answers is met by the procedure that always answers `false`, which the check reports.
- [`LeanIntentExamples/Declared.lean`](../LeanIntentExamples/Declared.lean): a structure `Point`, an inductive type `Light`, a structure with a parameter and a structure with a field of a declared type, each coded by `deriving LeanIntent.HasCode`; the codes and isomorphisms follow the declarations (`point_code`, `light_iso`). A function from points to numbers has the constant at zero and the projections onto the coordinates, and a record asking only for a result at least the first coordinate is met by the projection onto it, which the check reports (`atLeastX_verdicts`); a function from lights to lights has the constant at each light and the identity, and a record asking only that red follow green is met by the constant at red.
- The sorting and counter examples, described with [the obligations](obligations.md#worked-examples), state the degenerate check's verdicts too: it reports the empty-list function for the first sorting record (`sortedOnly_verdicts`, `sortedOnly_possibilities`) and the step that does nothing for the counter declared as a plain value (`neverDecreasesAsValue_verdicts`).

## What is trusted

- That a covered type has only the code the library's instances find for it, so that no record can be checked against a smaller class. Another instance would have to prove `Ty.Stands` of its code and isomorphism: for a type built only from those `Ty` builds in, its constructors admit only a code that denotes the type itself, through the cast along that equality or the type formers' maps of such casts, each of which maps every value to itself, and a different code would equate two different types, which Lean cannot prove without a further axiom; this is argued, not proved. For a declared type, the handler refuses a type that already has a code.
- That the code of a declared type follows its declaration: that the deriving handler reads the constructors and their fields in declaration order, which is its own code and not checked by Lean's kernel (the kernel checks only that the isomorphism it writes is one), and that nothing else applies the private constructor of `Ty.Stands` that admits a declared type. Lean's privacy is a rule of name resolution: it refuses `Ty.Stands.decl` written by name, `⟨…⟩` and `{ … }`, but the `constructor` tactic, which applies a constructor without resolving its name, or a metaprogram that builds the term directly, can still apply it and so pair a declared type with a code or isomorphism the record's author chose. No mechanism inside Lean's logic prevents this, since the logic cannot refer to the constructors of an arbitrary type; #24 tracks an audit that re-derives each declared type's code and isomorphism from the environment and compares them with every instance a theorem depends on, which removes the second assumption.
- That a constant function the class leaves out is not one the owner needed to see: where the output type has infinitely many values the class takes only the constants its rule fixes, so a record met by the function returning `[0]` for every input, and by no member, is not reported. No finite set of checked subjects closes this gap for every record; the freedom O5 shows the owner still spans it.
- That every record about a covered type has its verdicts stated, and every record about another type is checked by other means: Lean refuses to state verdicts about a type the class does not cover, but nothing in the library requires verdicts of a record, as nothing requires O1 to O5.
