## Toolchain and checks

`lean-intent` pins its Lean release in [`lean-toolchain`](lean-toolchain) (`v4.36.0`) and permits no external Lake dependencies ([`lakefile.toml`](lakefile.toml)). Before opening or updating a pull request, run the full repository check and test-listing verification from the repository root:

```sh
lean --run tools/check.lean
lean --run tools/check.lean --tests
```

- `lean --run tools/check.lean` checks `LAKE-CONFIG`, `LEAN-BUILD` (`lake build --wfail` over every library target and tracked library file, requiring `defaultTargets` to cover every library target), `LEAN-MODULE`, `AXIOMS`, `PROCESS`, `CODES` (via `tools/codes.lean`), `NO-COMMENTS` (verifying Git-index and working-tree admission for `tools/no-comments.pin`, `.no-comments.json`, and `tools/comment-ratchet.json`, staging and SHA-256-verifying the pinned `rbeauchamp/lean-no-comments` `v0.3.1` binary, and invoking `no-comments check` with `--base-ref <ref>` — defaulting via exact ref selection to `refs/remotes/origin/main` then `refs/heads/main` and passing the resolved commit), `REGULA` (verifying `tools/regula.pin`, staging/verifying `rbeauchamp/regula` `v0.16.0` at commit `e025e3e096fb085d0bc4a9c1a520f15eeb287581` or validating `REGULA_DIR`, extracting that commit's clean tree into an isolated temporary build directory with Lake caches disabled, and running `REGULA_PROOF=<lean-intent-dir> lake exe lint standard-logical` there while verifying exact claimed-module coverage, the exact final verdict line, and zero mutations across the `lean-intent` workspace), `LOADED` (refusing declarations of the library or under `tools/` that import modules with environment extensions left unloaded, except `LeanIntent.Imported.stored`), and `READERS` (refusing library declarations handed an `Environment` unless guarded with `LeanIntent.asking`/`askingIn`, requiring `LeanIntent.Loaded`, or listed in `stateless`). Run `lean --run tools/check.lean` from the `lean-intent` repository root rather than invoking `lake exe lint` inside `lean-intent` (which defines no `lint` executable). It must exit with status `0`. See [`.no-mistakes.yaml`](.no-mistakes.yaml) for measured resource costs and bounds, and [ADR-0001](docs/adr/0001-repository-checks-and-trusted-base.md) through [ADR-0004](docs/adr/0004-ratcheted-ban-on-lean-comments.md) and [ADR-0009](docs/adr/0009-environment-extension-loading-and-reader-guards.md) for what each rule checks.
- `lean --run tools/check.lean --tests` must exit with status `0` and print nothing to standard output.
- Because `NO-COMMENTS` verifies monotonicity against the merge base's `tools/comment-ratchet.json`, run checks in a checkout with full history (not a shallow clone without a base commit). If `refs/remotes/origin/main` points to your own fork or equals `HEAD`, pass `--base-ref <ref>` (for example, `lean --run tools/check.lean --base-ref upstream/main` or the pre-change base commit SHA) so the ratchet compares against upstream `main` rather than a stale fork branch or the commit itself.

## Deductive and formal engineering standards

`lean-intent` is a proof-driven library: replace trial-and-error implementation and scenario-based verification with derivation, correct-by-construction types, and machine-checked universal proofs.

- **5-rung enforcement ladder and cost bound:** Prefer, in order: (1) types making illegal states unrepresentable; (2) relations true by construction or derivation; (3) exhaustive compiler checks over genuinely closed finite domains; (4) machine-checked universal proofs; and (5) guards derived from the invariant where stronger enforcement is unavailable. Enforce invariants at state and admission/write boundaries, not only where values are observed. Spend code enforcement where breaking a rule causes serious or hard-to-undo harm (such as silent vacuous acceptance, crossed trust boundaries, or unverified declarations passing a gate); keep cheap, easily reversible rules documented as accepted risk in the trusted base. Every decision guard added to the library gets a theorem characterizing its decision (e.g., `findings_eq_nil_iff`, `findings_sound`) or stays written as accepted risk. Any discovery guard must read through the owning system's own mechanism (Lean's environment/kernel, Lake's package loader or `lake query`) or accept only a closed, provably injective subset and reject everything else, treating empty discovery as failure unless emptiness is established.
- **Design and attack first:** Record which enforcement rung each invariant reaches and why no higher rung is available; confirm language and tool capabilities directly from Lean or Lake source/documentation rather than assuming. Define each guarded boundary by its closed class (every constructor, exit, rejection, and failure mode), never by a remembered list. Attack every design before coding by constructing inputs, declarations, or environments it admits that intent forbids or refuses that intent needs, and revise until none remain.
- **Guard-removal caller-route derivation:** Before removing or narrowing any guard or refusal, derive everything it refused across every route through the owning system (all callers, configuration fields, commands, and import levels), not only the motivating examples. State in the PR description what now happens on each route: refused by another contract, moved outside the published contract with its consequence documented, or fixed in the same change. A precondition is insufficient if breaching it requires no attacker and yields a wrong result under exit `0` — a wrong result under a success code is never cheap under the cost bound.
- **Proof-to-execution linkage and proof economy:** Connect proofs to actual executable definitions and compiled code rather than independent shadow models (`Implementation`, `Execution`, `Refines`), and distinguish kernel-checked theorems from trusted external boundaries (`What is trusted`). Apply proof economy: prefer structural and analytic arguments over brute-force enumeration or certified re-execution, weighing both initial and recurring verification costs, and choose the simplest sound proof without unnecessary proof volume. Report evidence honestly (machine-checked, argued from source, observed, assumed, or open), read every affected module in full, and report unreadable relevant sources immediately rather than guessing.
- **3-part defect closure:** Close every defect by fixing the instance, closing the defect class at the highest practical rung within the cost bound, and fixing the upstream check, specification, or instruction link that let it pass undetected, recording Mission & TCB accounting and root cause under [`.github/pull_request_template.md`](.github/pull_request_template.md).

## Coding and verification standards

- **Module files (`LEAN-MODULE`):** Every `.lean` file in `LeanIntent/`, `LeanIntentExamples/`, and `tools/` must be a `module` file following [`README.md`](README.md#module-files) and [`README.md`](README.md#adding-a-feature).
- **No Lean comments (`NO-COMMENTS`):** All four Lean comment forms (`--`, `/- ... -/`, `/-- ... -/`, `/-! ... -/`) are banned across every tracked `.lean` file (`tools/comment-ratchet.json` is drained to `[]`); keep non-obvious architectural and trusted-base rationale in `docs/` or [`docs/adr/`](docs/adr/README.md). To inspect comments through the guarded inventory command (which checks `LAKE-CONFIG`, committed pin/config admission, and the pinned binary's SHA-256 before running `no-comments inventory`), run `lean --run tools/check.lean --comments [<file>]` ([ADR-0004](docs/adr/0004-ratcheted-ban-on-lean-comments.md)).
- **No tests (`--tests`):** `lean-intent` establishes its claims by machine-checked Lean theorems resting only on Lean's three standard axioms (`propext`, `Classical.choice`, `Quot.sound`), never by tests (`#eval`, `#guard`, `native_decide`, `testDriver`, or project-declared test elaborators). See [`README.md`](README.md#checks) and [ADR-0002](docs/adr/0002-test-listing-and-pinned-lean-tokens.md).
- **Adding a feature:** Place new modules under `LeanIntent/`, worked examples under `LeanIntentExamples/`, and documentation under `docs/` without modifying shared module lists; `lakefile.toml` selects modules by glob ([`README.md`](README.md#adding-a-feature)).

## Pull requests, commits, and triage

- Coding agents working on `lean-intent` itself must read [`AGENTS.md`](AGENTS.md) (projects depending on `lean-intent` use [`skills/`](skills/) instead).
- Pull requests are squash-merged onto `main` using the PR title and body; `main` refuses direct pushes, force-pushes, and commits without a verified signature.
- Title each pull request as a [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) header (`type(scope)!: summary`). Keep issue and pull-request descriptions to single-line paragraphs and list items, fill every top-level heading of [`.github/pull_request_template.md`](.github/pull_request_template.md), link each resolved issue on its own line (`Closes #N.`), and include no AI/assistant `Co-Authored-By:` trailers.
- [`.github/workflows/check.yml`](.github/workflows/check.yml) runs `lean --run tools/check.lean` and verifies empty `lean --run tools/check.lean --tests` output on every pull request, push to `main`, `workflow_call`, and `workflow_dispatch`: it checks out full history (`fetch-depth: 0`, `persist-credentials: false`), populates `refs/remotes/origin/main` from `origin`'s verified exact `refs/heads/main` when absent or not a commit, distinguishes reusable `workflow_call` runs from direct runs via `github.workflow_ref != job.workflow_ref` (read from `toJSON(job)`, failing closed if absent), and passes `--base-ref` with `refs/remotes/origin/main` on every `workflow_call` run (regardless of caller event), tag push, or `workflow_dispatch`, the PR base SHA on direct pull requests, and a non-zero `before` SHA on direct branch pushes (failing closed otherwise). The `lean` check (alongside `Analyze (actions)` and `CodeQL`, with the branch up to date) is required to merge into `main`.
- Pushing a `v*` tag triggers [`.github/workflows/release.yml`](.github/workflows/release.yml), which runs `.github/workflows/check.yml` via `workflow_call` (`verify-check`) and then `publish-release` (with `contents: write` scoped solely to that job) verifies `refs/remotes/origin/main` ancestry, tag `ref_type`, strict SemVer `v<MAJOR.MINOR.PATCH>` tag format (no leading zeros) and `git check-ref-format`, `HEAD == GITHUB_SHA`, and exact remote `refs/tags/$TAG` commit binding via `git ls-remote`, `git fetch --no-tags`, `FETCH_HEAD`, and `FETCH_HEAD^{commit}` before publishing a source-only GitHub Release with `gh release create --notes "" --verify-tag` (empty notes with no auto-generated changelog, zero binary assets, and zero third-party release actions; protected against tag updates or deletions between verification and publication by the active `release-tags` ruleset on `refs/tags/v*`).
- `lean-intent` is maintained by [@rbeauchamp](https://github.com/rbeauchamp) without a promised response SLA. Pull requests touching the paths listed in [`.github/CODEOWNERS`](.github/CODEOWNERS) automatically request review from `@rbeauchamp`.
